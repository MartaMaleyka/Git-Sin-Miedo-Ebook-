Chapter 13. Versions, Tags and Forks

Tags mark important moments in the project, like "this is version 1.0 that was published". Forks let you contribute to projects that aren't yours. And Markdown is the format you will write READMEs, Merge Requests, issues and the wiki in. These three tools complete your daily work with Git.

Why mark versions

Imagine the system your team maintains is published every two weeks. One day a user reports a bug and says: "this worked in last month's version". Which commit was that version?

If nobody marked it, you have to search through hundreds of commits by date and guess. If the team used tags, you write v1.3.0 and get there directly.

A tag is a fixed name given to a commit. Unlike a branch, it doesn't move: it always points to the same commit. It is like putting a bookmark on a page of the book.

How to number versions: semantic versioning

The most used convention is called semantic versioning. The number has three parts: MAJOR.MINOR.PATCH.

PartWhen it goes upExample
PATCHBug fixes, with no change in how it is used1.4.2 → 1.4.3
MINORNew features that don't break what came before1.4.3 → 1.5.0
MAJORChanges that force users to adapt1.5.0 → 2.0.0

When one part goes up, the ones to its right go back to zero. And versions that start with 0 (like 0.3.1) indicate the project is still in development and may change a lot.

By custom, tags carry a v in front: v1.5.0.

Creating and publishing tags

There are two types. Almost always use the annotated one, which stores the author, the date and a message:

git switch main
git pull
git tag -a v1.0.0 -m "First stable version of the site"

This tags the latest commit of main. To tag an earlier commit, add its code at the end: git tag -a v0.9.0 -m "…" 7b2e104.

Tags don't travel on their own with the push. You have to publish them:

git push origin v1.0.0     # One tag
git push origin --tags     # All local tags

Other useful commands:

CommandWhat it does
git tagLists the tags
git tag -l "v1.*"Lists only those starting with v1
git show v1.0.0Shows the tag and its commit
git switch --detach v1.0.0Takes you to see the project as it was in that version
git tag -d v1.0.0Deletes the tag on your computer
git push origin --delete v1.0.0Deletes the tag on GitLab

About --detach. When you go to a tag, Git warns you that you are in detached HEAD mode: you are not on any branch. You can look and try things, but if you make commits there they are left "loose". To return, run git switch main. If you need to fix something in that version, create a branch from it: git switch -c hotfix/v1.0.1 v1.0.0.

An important rule: don't change a tag that has already been published. If version v1.0.0 had a bug, the fix is v1.0.1. Moving a tag confuses everyone who already downloaded it.

Releases in GitLab

A release is a tag with presentation: a title, notes explaining what the version brings and, if needed, files to download. It is created in Deploy > Releases > New release (or from Code > Tags).

Good release notes answer what matters to whoever is going to use it:

## v1.5.0 — October 8, 2026

### New
- Contact form with email validation.
- Date filter in search.

### Fixed
- The footer phone number showed an old number.

### Breaking changes
- None. This version is compatible with the previous one.

Many projects also keep a CHANGELOG.md file at the root of the repository with these notes, from the newest version to the oldest. If your Merge Requests have good titles (chapter 5), writing the notes is almost copying and sorting.

Forks: contributing to projects that aren't yours

Until now you have worked on projects where you had permission to create branches. But what if you want to propose an improvement to a public project, or to one from another department, where you don't have write permission?

That is what the fork is for: a complete copy of the project in your own account on GitLab. In your copy you can do whatever you want. When you have something ready, you open a Merge Request from your fork to the original project. Its maintainers decide whether to accept it.

BranchFork
Where it livesInside the same projectIn your account, as a separate project
You need write permissionYesNo
When it is usedWork within your teamContributing to other people's or open source projects

The path of a contribution with a fork

  1. In the original project, press Fork and choose your account.

  2. Clone your fork, not the original:

git clone git@gitlab.com:your-username/project.git
cd project

  1. Also connect the original project, so you can bring in its updates. By custom it is called upstream:

git remote add upstream git@gitlab.com:original-team/project.git
git remote -v

Now you have two remotes: origin (your fork) and upstream (the original).

  1. Create a branch, make your changes and publish them to your fork:

git switch -c fix/documentation-error
# you make the changes and commits
git push -u origin fix/documentation-error

  1. In GitLab, open a Merge Request from your fork to the original project. Check the project and the target branch carefully.

  2. Respond to comments as in chapter 5: every push to your branch updates the Merge Request.

Keeping your fork up to date

The original project keeps moving forward. To bring its changes into your fork:

git switch main
git fetch upstream
git merge upstream/main
git push origin main

Do it before starting each new contribution, so you don't start from an old version.

Etiquette for contributing to other people's projects

  • Read the README and the CONTRIBUTING.md file first, if it exists. They explain how they prefer to receive changes.

  • For big changes, open an issue first and ask if they are interested. That way you don't spend days on something they won't accept.

  • Make small, well-described Merge Requests. The people who maintain open projects are often volunteers with little time.

  • Be patient. A reply can take days. A friendly reminder after a week is fine.

On GitHub it is called… The same: Fork. A Merge Request from a fork is a Pull Request.

Basic Markdown: the format you will write every day

Markdown is a simple way to format text using symbols. GitLab and GitHub turn it into titles, lists and links. You will use it in the README, Merge Request descriptions, comments, issues and the wiki. Files end in .md.

What you writeWhat you see
# TitleA large title
## SubtitleA medium title
**bold**bold
*italic*italic
- itemA bulleted list
1. stepA numbered list
- [ ] taskA checkbox to tick
[text](https://link.com)A link
`command`Code text inline
> noteA quote block
![description](image.png)An image

For multi-line code blocks, write three backticks before and after, optionally with the language:

```bash
git status
```

And tables are written with pipes and hyphens:

| Command | What for |
| --- | --- |
| git status | See the state |
| git log | See the history |

In GitLab, inside issues and Merge Requests, there are extra shortcuts that are very useful:

  • #42 links issue 42.

  • !15 links Merge Request 15.

  • @username mentions a person and sends them a notification.

  • Pasting a commit's code turns it into a link to that commit.

A good README

The README is the entry door to the project. This structure works for almost all of them:

# Project name

One or two sentences about what it does and for whom.

## How to start
Steps to download it and get it running.

## How to use it
Basic examples.

## How to contribute
How to name branches, how to open Merge Requests, who to ask.

## Contact
Project owners.

A clear README saves dozens of repeated questions for your team, and for yourself a year from now.

Real example: the version that had to be fixed

Ana's team publishes the site and tags the commit as v2.0.0, with a release listing what's new. Two days later a bug appears in the form.

Instead of mixing the fix with the new work already entering main, Ana creates a branch from the tag: git switch -c hotfix/v2.0.1 v2.0.0. She fixes it, opens her Merge Request, it is merged, and it is tagged v2.0.1 with a note: "Fixed: the form didn't accept emails with a hyphen".

Weeks later, someone asks since when that fix exists. The answer is in Deploy > Releases, without searching through commits.

Practical exercise

  1. In practice-git, update main and create an annotated tag v0.1.0 with the message "First practice version". Publish it.

  2. Make a new commit on a branch, merge it with a Merge Request and create the tag v0.2.0.

  3. In GitLab, create a release for v0.2.0 with release notes in Markdown, using the New and Fixed sections.

  4. Use git switch --detach v0.1.0 to see how the project was. Return with git switch main.

  5. Rewrite the README.md of your project with this chapter's structure. Include at least a title, a list, a link, a code block and a table. See how it looks in GitLab.

  6. Find a small public project in GitLab or GitHub and make a fork. Clone it, add upstream and check both remotes with git remote -v. You don't need to send a contribution yet: read its README and its CONTRIBUTING.md and note how they prefer to receive changes.

Chapter 14. Final Practical Project

In this chapter you will go through the complete teamwork flow, from start to finish, as you would in a real project: clone, create an issue and a branch, make changes, open a Merge Request, fix a comment, check the pipeline and complete the merge. There are no new topics. It is time to put everything you learned together.

The scenario

Your team maintains a small internal guide for new people: a page with the welcome, the team's contacts and the frequently asked questions. You are asked to add a new section of frequently asked questions about Git, because the people who arrive always ask the same things.

It is a small change on purpose. What matters is not the content, but doing each step of the process well.

How to do it: in pairs, or alone

In pairs (recommended). One person is the author and the other the reviewer. When you finish, you swap roles and repeat with another task. That way you live both sides of the Merge Request.

Alone. You play both roles. For the review, leave a few hours between writing and reviewing: you will see your work with fresher eyes. If you can, ask someone with a GitLab account to do only the review.

Project setup

You need a project that has a pipeline, to practice reading it. There are three paths, in this order of preference:

  1. Your organization or your instructor gives you a project already prepared, with a pipeline. Use it.

  2. Create it from a GitLab template that already includes a pipeline. In New project > Create from template, choose a simple website template, such as Pages/Plain HTML. You don't have to configure anything: the .gitlab-ci.yml file is already included.

  3. Use your practice-git project. It won't have a pipeline, so in phase 6 you will only verify that there is none and review how it would be read.

On GitLab.com, for pipelines to run, the platform may ask you to verify your account. If you can't or don't want to do it, follow path 3: the rest of the project works the same way.

We will call the project team-guide. If you are the owner, add your partner as Developer (chapter 10) and protect main: merge only by Maintainers, direct push No one.

Phase 1: clone the project

Goal: have the project on your computer, up to date.

cd Documents
git clone git@gitlab.com:your-username/team-guide.git
cd team-guide
git status
git log --oneline -5

Checkpoint:

  • git status says you are on main and everything is clean.

  • You read the README to understand the project.

  • git config user.email shows the email of your GitLab account.

If something fails: check the table of common problems in chapter 2.

Phase 2: create the issue and the branch

Goal: have the task exist in GitLab before touching the code.

  1. In GitLab, create an issue (chapter 8):

Title: Add frequently asked questions about Git to the guide

## What is needed
A section with frequently asked questions about Git for new people.

## Why
People who arrive always ask the same questions.

## When we consider it done
- [ ] There are at least five questions with their answers.
- [ ] The section is linked from the home page.
- [ ] The text has no spelling mistakes.

  1. Add the label documentation, assign it to yourself and, if you have one, add it to a milestone.

  2. Note its number. In the examples we will use #7.

  3. Create the branch. You can use the Create merge request button of the issue, or do it from the terminal:

git switch main
git pull
git switch -c docs/7-git-faq

Checkpoint:

  • The issue has a clear title, description and done criteria.

  • The branch follows the convention type/number-description.

  • You started from an updated main.

  • You moved the issue to In progress on the board, if you use one.

Phase 3: make the changes and the commits

Goal: small changes, reviewed before saving, with clear messages.

  1. Create the file for the section. If the project is in HTML, create git-faq.html; if it is in Markdown, git-faq.md. Write at least five questions with short answers. Ideas: "What is a commit?", "Why don't I work on main?", "What do I do if a conflict appears?", "What is a Merge Request?", "What do I do if I uploaded a password?".

  2. Look before you save and make the first commit:

git status
git diff
git add git-faq.md
git diff --staged
git commit -m "Add frequently asked questions section about Git (#7)"

  1. Now link the section from the home page (the index.html or the README.md). It is a different idea, so it goes in another commit:

git add index.html
git commit -m "Link frequently asked questions from the home page (#7)"

  1. Review your history and publish the branch:

git log --oneline -3
git push -u origin docs/7-git-faq

Checkpoint:

  • You made at least two commits, one per idea.

  • Each message starts with a verb and mentions the issue.

  • You used git status and git diff before each commit.

  • No file unrelated to the task got in.

  • The branch appears in GitLab, under Code > Branches.

Optional: if you practice with an agent, do this phase with it following the rules of chapter 11, and verify everything manually.

Phase 4: open the Merge Request

Goal: ask for review with all the information the reviewer needs.

  1. Open the Merge Request from the link the push gave you.

  2. Verify: source docs/7-git-faq, target main.

  3. Title: Add frequently asked questions about Git to the guide.

  4. Description, using the chapter 5 template:

## What changes
Adds a section of frequently asked questions about Git and links it
from the home page.

## Why
New people always ask the same questions.

## How to test it
1. Open the home page.
2. Click "Frequently asked questions about Git".
3. Check that the questions and answers appear.

Closes #7

  1. Assign your partner as Reviewer, add the label documentation and tick Delete source branch.

  2. Before announcing it, review the whole Changes tab yourself.

Checkpoint:

  • Source and target are correct.

  • The description explains what, why and how to test.

  • It includes Closes #7.

  • You reviewed your own changes before asking for review.

Phase 5: review and fix a comment

Goal: live the cycle of comment, fix and resolution.

If you are the reviewer:

  1. Read the description and then the Changes tab.

  2. Leave at least two comments with Start a review: one marked as a suggestion, using Insert suggestion, and another that asks for a real change (for example, an answer that could be explained better, or a missing question).

  3. Remember: comments about the content, with the reason, and something positive if there is any.

  4. Submit the review.

If you are the author:

  1. Read each comment in full.

  2. Apply the suggestion with Apply suggestion.

  3. For the other comment, make the fix on your computer. Since you applied a suggestion in GitLab, first bring that change in:

git pull
# you make the fix
git status
git diff
git add git-faq.md
git commit -m "Clarify the answer about conflicts (#7)"
git push

  1. Verify that the Merge Request updated itself with your new commit.

  2. Reply to each thread with what you did and resolve them (or let the person who commented resolve them, according to your team's agreement).

  3. Request the review again.

Extra challenge: a conflict. While the Merge Request is open, have the other person make a small Merge Request that changes the same line with the link on the home page, and merge it first. Your Merge Request will show a conflict. Resolve it on your computer with git merge main (chapter 6), keeping both changes, and push.

Checkpoint:

  • There were at least two comments and both were addressed.

  • The fix arrived as a new commit on the same branch.

  • All threads were resolved.

  • If you did the challenge, the conflict was resolved without losing any change.

Phase 6: check the pipeline

Goal: read the traffic light before merging (chapter 9). Remember: you won't configure anything, only read.

  1. In the Merge Request, find the pipeline box. Each push you made ran it automatically.

  2. If it is running, wait.

  3. If it is passed, open the pipeline and look at its stages and jobs. Open the log of a job and read the last lines.

  4. If it is failed, apply the process from chapter 9: identify the job, read the end of the log, relate it to your change, fix it and push. If it has nothing to do with your change, use Retry once; if it still fails, ask for help with the link and the error lines.

  5. If your project has no pipeline (path 3), you will see no box. Go to Build > Pipelines and confirm it is empty. Then review, in a public project, how it would look.

Checkpoint:

  • I know what state the pipeline ended in and why.

  • I did not move on to the merge with the pipeline red.

Phase 7: complete the merge

Goal: close the cycle and leave everything tidy.

  1. Review the "What to check before merging" list from chapter 10.

  2. The reviewer approves with Approve.

  3. Whoever has merge permission presses Merge.

  4. Verify in GitLab:

    • Issue #7 closed on its own.

    • The branch was deleted.

    • In Code > Commits of main your commits appear (or just one, if squash was used).

    • The board and the milestone were updated.

  5. Update your computer:

git switch main
git pull
git branch -d docs/7-git-faq
git fetch --prune
git log --oneline --graph -10

  1. Optional: create the tag v1.1.0 with its release and release notes (chapter 13).

Checkpoint:

  • The Merge Request was merged with approval and with everything resolved.

  • The issue closed automatically.

  • Your local main is up to date and the local branch was deleted.

Phase 8: switch roles

If you work in pairs, repeat everything with the roles reversed and a different task. Ideas:

  • Add a section with the team's contacts.

  • Fix spelling mistakes on the home page (a fix/ type).

  • Create the page "How we work" in the wiki and link it from the README.
