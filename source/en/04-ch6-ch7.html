Chapter 6. Conflicts: Don't Erase Someone Else's Work

A conflict appears when two people changed the same part of a file and Git can't decide which version is the right one. It is not an error or a failure: it is Git being honest and asking you for help. In this chapter you will lose your fear of conflicts and learn to resolve them without erasing anyone's work.

My story: the giant conflict

The worst conflict I ever lived through was not caused by a complicated change. It was caused by keeping two branches apart for weeks. While I was moving forward on mine, main kept changing too. When I finally wanted to combine them, Git marked conflicts in file after file.

Each conflict on its own was simple. The problem was the quantity, and that I no longer remembered well why I had made each change weeks earlier. Joining the branches took me far longer than doing the original work.

That is where the rule I gave you in chapter 4 came from: short branches, integrate often. A small conflict today takes five minutes to resolve. Twenty accumulated conflicts can cost you a whole day.

What I see in others: resolving by deleting

As an instructor, and on the teams where I have worked, I have seen the same scene many times. The conflict appears, the person gets scared and picks the fastest way out: keep their own version and discard the other one without reading it.

The conflict disappears from the screen. Git is happy. But a teammate's change has just been lost in silence. Nobody finds out until days later, when something that was already fixed breaks again.

That is why this chapter has one golden rule: a conflict is resolved by understanding both changes, not by picking yours by default.

Why conflicts appear

Git is very good at combining changes. If Ana changes line 10 of a file and Luis changes line 50, Git combines both without asking. If Ana changes index.html and Luis changes contact.html, there is no problem either.

A conflict only appears in these cases:

SituationExample
Two people change the same linesAna sets the hours until 5:00 and Luis sets them until 4:30
One person deletes a file and another modifies itLuis deleted old.md and Ana added a paragraph to it
Two people create a file with the same nameBoth added guide.md with different content

In all those cases there are two human decisions that clash. Git can't guess which one is right, and it is right not to guess.

When a conflict can show up

  • When you run git pull, if someone published changes to the same lines you changed.

  • When you run git merge main on your branch, to update it.

  • In a Merge Request, when GitLab warns that your branch conflicts with main and won't let you merge.

In every case it is resolved the same way. Let's see how.

What a conflict looks like

When there is a conflict, Git warns you in the terminal:

Auto-merging contact.md
CONFLICT (content): Merge conflict in contact.md
Automatic merge failed; fix conflicts and then commit the result.

And if you look at the status:

git status
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
        both modified:   contact.md

both modified means "both sides changed this file". That is the one you have to review.

When you open contact.md you will see something like this:

# Contact

<<<<<<< HEAD
Hours: Monday to Friday, 8:00 to 5:00
=======
Hours: Monday to Friday, 8:00 to 4:30
>>>>>>> fix/friday-hours

Phone: 500-0000

Those odd markers were put there by Git to show you both sides:

  • Between <<<<<<< HEAD and ======= is your version, the one on the branch you are on.

  • Between ======= and >>>>>>> fix/friday-hours is the version you are bringing in, from the other branch.

  • Everything outside the markers (like the phone number) has no conflict.

How to resolve it, step by step

1. Don't panic, and don't delete anything yet

The conflict hasn't broken anything. Your work and your teammate's work are safe. If you need to step away and think, you can cancel everything and return to how it was before:

git merge --abort

It is your emergency button. Use it without guilt.

2. Understand both changes

Before touching the file, ask yourself:

  • What was my change trying to do?

  • What was the other change trying to do?

  • Are they incompatible, or can they be combined?

To find out who made the other change and why:

git log --oneline main -- contact.md

Read the commit message. If it is still unclear, ask that person. A quick message like "Hey, we both changed the hours, which one is correct?" prevents losing work. This is the part people skip most often, and the most important one.

3. Decide how it should look

You have four options:

OptionWhenResult in the example
Keep your versionThe other change is obsolete, and you confirmed it8:00 to 5:00
Keep the other versionTheir change is the correct one8:00 to 4:30
Keep bothBoth lines should existBoth lines, one below the other
CombineEach change has a correct partFor example: Monday to Thursday 8:00 to 5:00, Friday 8:00 to 4:30

In real life, the right option is often combining. Rarely is one of the two changes completely unnecessary.

4. Edit the file and remove the markers

Leave the text exactly as it should be and delete the three markers (<<<<<<<, ======= and >>>>>>>). For example:

# Contact

Hours: Monday to Thursday 8:00 to 5:00, Friday 8:00 to 4:30

Phone: 500-0000

A very common mistake is forgetting one of the markers. Before going on, search the file for <<<<<<<. There should be none left.

5. Mark the conflict as resolved and save

git add contact.md
git status

When git status no longer shows files in conflict:

git commit

Git opens the editor with a message already written, such as Merge branch 'main' into fix/friday-hours. You can leave it like that or add a line explaining how you resolved it. Save and close. Then run git push.

6. Check that everything works

Resolving a conflict means changing code. Open the result, test it and make sure it does what both changes were meant to do. If the project has automatic tests, the pipeline will help you (chapter 9).

Resolving conflicts in VS Code or Cursor

The editor makes all of this more visual. When you open a file with a conflict you will see the two blocks colored, and above them some links:

  • Accept Current Change: keep your version.

  • Accept Incoming Change: keep the version that is coming in.

  • Accept Both Changes: keep both.

  • Compare Changes: see them side by side.

You can also use the Resolve in Merge Editor button, which shows three panels: your version, the incoming one, and the final result at the bottom. You can tick boxes and edit the result by hand.

Be careful: these buttons are convenient, but they make it easy to make the "accept mine" mistake without reading. Read both blocks before clicking. When you are done, save the file and continue with git add and git commit, or use the buttons in the Git panel.

Resolving conflicts in GitLab

If a Merge Request has simple conflicts, GitLab shows a Resolve conflicts button. It lets you choose, block by block, between your version (ours) and the other one (theirs), or edit the file directly in the browser.

It is useful for small text conflicts. For larger conflicts, or if you need to test the result, it is better to resolve them on your computer:

git switch main
git pull
git switch your-branch
git merge main
# you resolve the conflicts
git add resolved-files
git commit
git push

When you push, the Merge Request updates and the conflict warning disappears.

Special cases

One side deleted the file and the other modified it. git status will say deleted by them or deleted by us. Decide whether the file should exist. If it should stay, use git add file. If it should be deleted, use git rm file. Before deleting it, check whether the other side's change should have been moved somewhere else.

Conflicts in files that are not text (images, Word, PDF). Git can't show you the differences inside. You have to choose a complete version:

git checkout --ours logo.png     # I keep my version
git checkout --theirs logo.png   # I keep the other one
git add logo.png

Talk to the other person before choosing. One of you is going to lose their version.

Lots of conflicts at once. If it happens to you what happened to me, don't try to resolve everything in one go. Run git merge --abort and ask for help: the person who made the other changes, or someone with more experience. Sometimes it is better to integrate the changes in parts, or to create a new branch from an updated main and bring your changes in gradually.

How to prevent conflicts

You can't avoid all of them, and it is not bad that they appear. But you can make them few and small:

  • Short branches. Days, not weeks.

  • Bring main into your branch often if your work drags on.

  • git pull before you start working each day.

  • Small commits and Merge Requests. Fewer lines touched, fewer possible clashes.

  • Coordinate with your team. If two people are going to touch the same file, they should know. One line in the team chat saves hours.

  • Don't reformat whole files (changing spaces, sorting lines) mixed with real changes. It creates conflicts across the whole file. If needed, do it in a separate Merge Request.

Common mistakes when resolving conflicts

MistakeConsequenceHow to avoid it

Real example: a conflict well resolved

Ana is on feature/new-hours, where she changed the hours to 8:00 to 5:00. Meanwhile, Luis's branch was merged into main, which set Friday until 4:30.

Ana brings main into her branch with git merge main and the conflict appears in contact.md. Instead of accepting her version, Ana checks Luis's commit with git log: "Adjust Friday hours for new schedule". She messages Luis to confirm. Both changes were correct: the general hours changed, and Friday changed too.

Ana combines the two versions, removes the markers, checks that none are left, runs git add, git commit and git push. In the commit message she adds: "Combine new hours with Luis's Friday adjustment". Nobody lost work, and there is a record of how it was resolved.

Practical exercise: cause a conflict on purpose

The best way to lose your fear is to create one yourself, in a safe place.

  1. In practice-git, go to main and update it: git switch main and git pull.

  2. Create a file hours.md with the line Hours: 8:00 to 4:00. Commit and push on main (it is your practice project, here you are allowed to).

  3. Create a branch: git switch -c fix/afternoon-hours. Change the line to Hours: 8:00 to 5:00. Commit.

  4. Go back to main: git switch main. Change the same line to Hours: 7:00 to 4:00. Commit.

  5. Go back to your branch and bring in main: git switch fix/afternoon-hours and git merge main.

  6. Read the conflict warning and run git status.

  7. Open hours.md and identify the three markers and the two blocks.

  8. Try git merge --abort and check with git status that everything is back to normal.

  9. Repeat step 5 and this time resolve it by combining: Hours: 7:00 to 5:00. Remove the markers.

  10. Finish with git add hours.md, git commit and git push -u origin fix/afternoon-hours.

  11. Challenge: repeat the exercise resolving with the VS Code or Cursor buttons, and once more with the Resolve conflicts button of a Merge Request in GitLab.

Chapter 7. Emergency Kit: Undo Without Losing Work

Almost everything in Git can be undone. The key is knowing what you want to undo and whether you already published it. This chapter gives you the four commands to repair mistakes (restore, revert, reset and stash), a safety net for when everything seems lost (reflog), and ready-made recipes for the most common accidents.

Before touching anything: the two questions

When something goes wrong, take a breath and ask yourself:

1. Where is the mistake?

  • In files I changed but haven't committed.

  • In the box (git add), but without a commit.

  • In a commit that only exists on my computer.

  • In a commit I already published with push.

2. Do I want to lose that change or keep it?

With those two answers, you choose the tool. This is the map:

Where the mistake isToolDo I lose the change?
Modified file, without addgit restore fileYes, it is discarded
In the box, without commitgit restore --staged fileNo, it only leaves the box
Local commit, without pushgit resetDepends on the option
Commit already publishedgit revertNo, a commit that cancels it is created
Half-finished work I want to set asidegit stashNo, it is kept aside

And one rule that saves you from many problems: what you already published is not rewritten, it is corrected with a new commit.

git restore: discard changes you haven't saved

You edited a file, made a mess, and want to go back to how it was in the last commit:

git restore contact.md

The file returns to its last saved version.

Warning: this command discards your changes forever. Since you never committed them, Git has no copy. Before using it, check with git diff contact.md what you are about to lose.

To discard the changes of all the files in the folder:

git restore .

Use it with even more care. Check git status first.

To take a file out of the box without losing what you changed (you saw this in chapter 3):

git restore --staged contact.md

This one is harmless: the change stays in your file, it just stops being ready for the commit.

You can also recover a file as it was in an earlier commit:

git restore --source a3f9c21 contact.md

The file is left as it was in that commit. Review it, and if it is useful, make a new commit with that version.

git revert: undo a published commit

You already pushed and discover that a commit has a mistake. Your teammates have already downloaded it. You can't delete it from history without causing them problems. The right thing is to create a new commit that does the opposite:

git log --oneline
git revert a3f9c21

Git creates a commit with a message like Revert "Update opening hours". If the original commit added a line, the revert removes it. If it removed one, the revert puts it back. Then you run git push as usual.

Why it is the safe option:

  • It doesn't erase history. The commit with the mistake is still there, and so is the one that cancelled it. Anyone can see what happened.

  • It doesn't affect your teammates. They just download a new commit, like any other.

  • It can be undone. If you made a mistake while reverting, you can revert the revert.

In GitLab you can also do it with buttons: open the commit or the already merged Merge Request and use the Revert button. GitLab offers to create a Merge Request with the reversal.

git reset: redo commits that only exist on your computer

reset moves your branch backward, as if certain commits had never been made. It is powerful, which is why it has a strict rule: use it only with commits you have not published.

HEAD~1 means "one commit before the current one". HEAD~2, two commits before, and so on.

The three forms of reset

Imagine your last commit was a mistake and you want to undo it. What happens to the changes it had?

OptionThe commitThe changesWhen to use it
--softUndoneThey stay in the box, ready for another commitI want to redo the commit with another message or add something
--mixed (default)UndoneThey stay in your files, outside the boxI want to reorganize what goes into each commit
--hardUndoneDeletedI want to throw all that work away

Examples:

git reset --soft HEAD~1    # Undoes the commit, keeps everything in the box
git reset HEAD~1           # Undoes the commit, keeps the changes in your files
git reset --hard HEAD~1    # Undoes the commit and DELETES its changes

Warning about --hard: it deletes changes from your files without asking for confirmation. Before using it, run git status and git log --oneline and make sure of what you are about to lose. If in doubt, use --soft or --mixed: you can always discard afterward.

And if I already pushed?

If you undo with reset a commit that was already on GitLab, your local branch and the GitLab one become different. Git will reject your push. Forcing it (git push --force) rewrites shared history and can delete your teammates' work. On protected branches, like main, GitLab doesn't even allow it.

For published commits, use revert. The only reasonable exception is your own branch, where nobody else works, and even then it is better to ask the team.

revert, reset and restore: the difference in one sentence

  • restore works with files: it returns them to a saved version.

  • reset works with local commits: it moves your branch backward, as if they had never been made.

  • revert works with published commits: it creates a new commit that cancels another one.

If you only remember one thing: did you already push? Then revert.

git stash: set aside half-finished work

You are in the middle of something, unfinished, and you need to switch branches to handle an emergency. You don't want to commit something incomplete. That is what stash is for: a drawer where you keep your changes temporarily.

git stash push -m "Half-finished form"

Your folder is left clean, as at the last commit. You can switch branches calmly now.

When you come back:

git stash list
stash@{0}: On feature/form: Half-finished form

To recover your changes:

git stash pop

pop takes the changes out of the drawer and applies them to your folder. Other useful options:

CommandWhat it does
git stash applyApplies the changes but keeps them in the drawer too, just in case
git stash dropDeletes the last stash from the drawer
git stash show -pShows which changes are saved
git stash push -u -m "…"Also includes new files that Git was not tracking yet

Three tips:

  • Always give it a message with -m. With three unnamed stashes you won't know which is which.

  • Don't use it as a warehouse. Stash is for minutes or hours, not weeks. If the work is going to last, commit it on a branch.

  • Remember which branch you were on. You can apply a stash on another branch, but usually you want to return to the same one.

git reflog: the safety net

Here is the secret that reassures everyone: Git records every move you make, even the ones that "delete" commits. If you did a reset --hard you regret, or deleted a branch with commits, you can almost always get it back.

git reflog
7b2e104 HEAD@{0}: reset: moving to HEAD~1
a3f9c21 HEAD@{1}: commit: Update opening hours
1c8d3aa HEAD@{2}: checkout: moving from main to feature/hours

Each line is a moment your project went through. To go back to one:

git switch -c rescue a3f9c21

This creates a new branch called rescue exactly at the point you wanted to recover. Check that everything is there and then decide what to do with it.

Two limits you should know: the reflog exists only on your computer, and it keeps the movements for a while (usually several weeks), not forever. And it cannot recover changes that you never saved with a commit.

Recipes for the most common accidents

"I committed to the wrong branch" (without push)

You committed on main when it should have gone on a new branch:

git branch feature/my-change      # Creates the branch pointing at your commit
git reset --hard HEAD~1           # Removes the commit from main
git switch feature/my-change      # Your commit is safe here

If there were two commits, use HEAD~2. Check with git log --oneline before the reset.

"I want to change the message of my last commit" (without push)

git commit --amend -m "Correct message"

"I forgot to add a file to the last commit" (without push)

git add forgotten-file.md
git commit --amend --no-edit

--no-edit keeps the same message.

"I want to undo my last commit but keep the work" (without push)

git reset --soft HEAD~1

"A commit I already published broke something"

git revert commit-code
git push

"I want to throw away all my changes and match GitLab"

git fetch
git status                         # Check what you are about to lose
git reset --hard origin/main       # Your branch becomes identical to GitLab's

If you are on another branch, replace main with its name. Everything that was not published will be lost.

"I deleted a branch that had work"

git reflog                         # Find the last commit of that branch
git switch -c branch-name commit-code

"There are new files I don't know where they came from, and I want to delete them"

git clean -n      # Only shows what it would delete
git clean -f      # Deletes them for real

Always use -n first. git clean deletes files that Git doesn't track, and reflog cannot recover them.

"I uploaded a password or a token"

No command in this list fixes this. Even if you delete it with a new commit, it stays in the history. The first thing to do is change that password or revoke the token immediately, and notify the person responsible for security. We look at it in detail in chapter 10.

Commands that deserve respect

These commands can delete work. They are not forbidden, but before using them stop and check with git status and git log:

CommandWhat it can deleteRecoverable with reflog?
git restore fileUncommitted changesNo
git reset --hardUncommitted changes and local commitsCommits yes; uncommitted changes no
git clean -fFiles Git doesn't trackNo
git branch -DAn unmerged branchYes, for a while
git push --forceOther people's commits on GitLabHard, and it affects the whole team

Real example: the afternoon of three scares

Luis has a complicated afternoon:

  1. He commits on main instead of on his branch. He hasn't pushed. He creates the branch with git branch, removes the commit from main with reset --hard HEAD~1 and keeps working on his branch.

  2. While he works, he is asked to review something urgent on another branch. He saves his half-finished work with git stash push -m "Report adjustments", switches branches, handles the urgent task, comes back and recovers everything with git stash pop.

  3. At the end of the day he discovers that a commit he published in the morning broke the total calculation. Since it is already on GitLab, he doesn't use reset: he runs git revert, pushes, and tells the team.

Three scares, zero work lost, and a history that tells exactly what happened.

Practical exercise: break things on purpose

In your practice-git project, on a new branch called practice/first-aid:

  1. Restore. Modify README.md, look at the change with git diff and discard it with git restore README.md.

  2. Restore --staged. Modify a file, add it with git add and take it out of the box with git restore --staged. Check that the change is still in the file.

  3. Reset --soft. Make a commit with an ugly message. Undo it with git reset --soft HEAD~1 and redo it with a good message.

  4. Stash. Make an uncommitted change, save it with git stash push -m "test", switch to main, come back and recover it with git stash pop.

  5. Revert. Make a commit, publish it with push and then cancel it with git revert. Look at both commits in GitLab.

  6. Reflog. Make a commit, delete it with git reset --hard HEAD~1 and recover it with git reflog and git switch -c rescue commit-code.

  7. Wrong branch. On main of your practice project, make a commit without pushing and move it to a new branch using the recipe from this chapter.

Note on paper which command you used in each case and why. That sheet is your personal first-aid kit.
