Chapter 11. Git with an Agent: You Decide, the AI Executes

An AI agent or a script can do the repetitive parts of Git for you: pulling changes, preparing commits, publishing them and opening Merge Requests. Used well, it saves you time and mistakes. Used badly, it can publish something nobody reviewed. The rule of this chapter is the one in the title: automation executes, but you make the decisions.

My workflow

I work this way every day: I use Claude to plan the change, Cursor to run it on the code, and I review every commit before I push. The AI proposes and writes. I read, understand, correct and decide what gets published.

That last step is not optional. An agent can write code that looks right and isn't, touch files you didn't ask for, or solve a problem in a way that doesn't fit the rest of the project. If you publish without looking, the person responsible for the change is still you, not the tool.

That is why this chapter is at the end of the book, and not at the beginning. To supervise an agent you need to understand everything before: what each command does, how to read a diff, when there is a conflict and how to undo a mistake.

The five rules of safe automation

1. Validate before acting

Before any command, the automation checks:

  • That it is inside a Git repository.

  • Which branch it is on, and that it is not main or another protected branch.

  • That there is no half-done merge or conflict.

  • Which files changed, and whether any look suspicious (.env, keys, huge files).

If something doesn't add up, it stops and warns you. It never "fixes it" on its own.

2. Preview and confirmation

Before committing, pushing or opening a Merge Request, the automation shows you exactly what it is going to do:

  • The list of files and the diff.

  • The proposed commit message.

  • The branch it is going to publish to.

And it waits for you to confirm explicitly. A "yes" typed by you, not a "continue automatically".

3. Mandatory human review at critical points

There are three moments when the automation always stops and hands control back to you:

  • Conflicts. It tells you which files clash, and you resolve them.

  • Protected branches. It never pushes or merges to them.

  • Merge Requests. It can open them, but review, approval and merging belong to people.

4. Log of every command and result

Every action is recorded in a log file: date, project, branch, command and result. That way you can audit what the automation did and, if something went wrong, know exactly what to revert (chapter 7). A log like this one:

2026-10-08 10:42:11 | practice-git | git pull (branch feature/about-me) | ok
2026-10-08 10:43:02 | practice-git | commit a3f9c21: Add about me section | ok
2026-10-08 10:43:05 | practice-git | push to origin/feature/about-me | ok

With the commit code (a3f9c21) you can run git show to review it or git revert to cancel it.

5. Least privilege

The automation uses your credentials with just the right permissions: it can write to branches, but not merge into main (that is what the protected branches of chapter 10 are for). If you use a token for it, give it an expiration date and only the permissions it needs.

Option A: a simple script with confirmation

A script is a list of commands saved in a file that runs in one go. It isn't clever: it always does the same thing. That is exactly why it is predictable.

This script applies the five rules. It takes what you put in the box with git add, shows it to you, looks for sensitive files, asks for the message and the confirmation, commits and pushes to your branch, and logs everything:

#!/usr/bin/env bash
# publish.sh: saves and publishes what is in the box, with human review
set -euo pipefail

LOG="$HOME/.git-assistant.log"
log() { echo "$(date '+%Y-%m-%d %H:%M:%S') | $(basename "$PWD") | $*" | tee -a "$LOG"; }

# 1. Validate: repository, branch and state
if ! git rev-parse --is-inside-work-tree >/dev/null 2>&1; then
  echo "You are not inside a Git repository."; exit 1
fi

BRANCH=$(git branch --show-current)
if [[ -z "$BRANCH" || "$BRANCH" == "main" || "$BRANCH" == "master" ]]; then
  echo "You are on '$BRANCH'. Create a branch before publishing."; exit 1
fi

if [[ -f "$(git rev-parse --git-dir)/MERGE_HEAD" ]]; then
  echo "There is a half-done merge. Resolve it first (chapter 6)."; exit 1
fi

# 2. Bring in changes from GitLab if the branch is already published
if git rev-parse --abbrev-ref '@{u}' >/dev/null 2>&1; then
  if git pull --no-rebase; then
    log "git pull (branch $BRANCH) | ok"
  else
    log "git pull (branch $BRANCH) | conflict or error, stopping"
    echo "There are conflicts or errors. Resolve them yourself and run it again."; exit 1
  fi
fi

# 3. Preview of what is going to be saved
if git diff --cached --quiet; then
  echo "Nothing is in the box. Use git add with the files you want to save."; exit 1
fi
echo "===== Files to be saved ====="
git --no-pager diff --cached --stat
echo "===== Changes ====="
git --no-pager diff --cached

# 4. Alert for sensitive files
if git diff --cached --name-only | grep -Eiq '(^|/)\.env$|\.pem$|\.key$|id_rsa|id_ed25519'; then
  log "ALERT: sensitive file in the box, stopping"
  echo "Some files look like secrets. Take them out of the box (chapter 10)."; exit 1
fi

# 5. Message and human confirmation
read -r -p "Commit message: " MSG
if [[ -z "$MSG" ]]; then echo "The message cannot be empty."; exit 1; fi

read -r -p "Save and publish to '$BRANCH'? Type yes to confirm: " OK
if [[ "$OK" != "yes" ]]; then log "cancelled by the person"; echo "Cancelled."; exit 0; fi

git commit -m "$MSG"
log "commit $(git rev-parse --short HEAD): $MSG | ok"

git push -u origin "$BRANCH"
log "push to origin/$BRANCH | ok"

echo "Done. Open or review the Merge Request in GitLab. A person decides the merge."

How to use it:

  1. Save the text in a file publish.sh, in a folder outside your projects (for example, ~/scripts/).

  2. Give it execution permission once: chmod +x ~/scripts/publish.sh.

  3. In your project, look and choose your changes as usual: git status, git diff, git add file.

  4. Run ~/scripts/publish.sh and follow the questions.

  5. Review the log whenever you like: cat ~/.git-assistant.log.

Notice what the script does not do: it doesn't pick files for you, doesn't merge, doesn't resolve conflicts, doesn't force anything and doesn't touch main. Those decisions are still yours. On Windows, run it from Git Bash.

Option B: an AI agent with clear rules

An AI agent, like the ones built into editors such as Cursor or into coding assistants, is more flexible than a script: it understands instructions in natural language ("add a date filter and push it to a branch"), writes code and runs commands. That flexibility is exactly what demands more control.

Give it written rules

Most agents let you leave permanent instructions in a file in the project (depending on the tool, it may be called AGENTS.md, an editor rules file or another name its documentation indicates). The agent reads those instructions before working. An example you can adapt:

# Rules for working with Git in this project

## Before acting
- Run git status and tell me which branch you are on and what changed.
- Never work on main. If you are on main, create a branch with the format
  type/number-description (for example fix/42-empty-date) and ask me to confirm.
- Run git pull before starting.

## Commits
- One commit per idea. Message in English, starting with a verb.
- Before each commit, show me the diff and the proposed message, and wait for my "yes".
- Never add .env files, keys, credentials or files outside the task.

## Publishing
- Only push to the working branch, never to main or protected branches.
- Before pushing, ask me for confirmation.
- You can draft the Merge Request description, but do not merge it.

## Forbidden without my explicit authorization
- git push --force, git reset --hard, git clean, deleting branches.
- Resolving conflicts: if one appears, stop and tell me which files clash.
- Modifying .gitlab-ci.yml or the project configuration.

## Log
- When you finish, give me the list of commands you ran and their results.

How to ask for things

A good request to the agent describes what you want and what the limits are:

"Add required date validation to the contact form, for issue #42. Work on a new branch. When you finish, show me the diff and the commit message before saving. Don't push without my confirmation."

Compare that with "fix the form and push it". The first makes the scope, the branch and the checkpoints clear. The second gives the agent too much freedom.

Review what the agent did

When the agent shows you the diff, read it as if a new colleague wrote it on their first day (chapter 5):

  • Did it do only what you asked, or did it touch other files?

  • Do you understand every line that changed? If you don't, don't approve it: ask it to explain.

  • Does it work? Test it yourself, don't rely on "the agent says it works".

  • Does the commit message describe the change well?

  • Is there anything that looks like a secret, personal data or a temporary file?

If something doesn't convince you, ask for the change or make it yourself. Approving without understanding is exactly the "save everything without looking" mistake of chapter 3, only faster.

What you must understand even when it is automated

Automation doesn't free you from knowing Git. It frees you from typing the commands, not from understanding them. Before using an agent or a script, you should be able to answer:

  • What is the difference between commit and push? (chapter 1)

  • How do I read a diff and what changed? (chapter 3)

  • Which branch am I on, and why must I not be on main? (chapter 4)

  • What happens in a Merge Request and who decides the merge? (chapter 5)

  • What is a conflict and how is it resolved without losing work? (chapter 6)

  • How do I undo a published commit? (chapter 7)

  • Why does a secret never enter the repository? (chapter 10)

If the automation fails halfway through, and one day it will, you are the one who has to understand what state the repository was left in and how to continue.

Real example: one change from start to finish with an agent

Ana receives issue #45 Add date filter to search. She asks the agent: "Work on issue #45 on a new branch. Show me the plan before touching code."

The agent checks the state: Ana is on main, up to date and with no changes. It proposes creating feature/45-date-filter and Ana confirms. Then it proposes a three-step plan; Ana asks it to remove one step that wasn't needed. The agent writes the code and shows her the diff: it touched the search file and, without being asked, a styles file. Ana asks it to revert that second change.

With a clean diff, Ana tests the filter on her computer and it works. The agent proposes the message Add date filter to search (#45). Ana approves it, confirms the push, and the agent prepares the Merge Request description with Closes #45. Ana reviews it, adjusts it and assigns Luis as reviewer.

Luis reviews and approves. Ana merges. The agent saved time writing code and commands; every decision was Ana's.

Practical exercise

In your practice-git project:

  1. Create the rules file for your agent (or the one your editor uses) with the example from this chapter, adapted to how you work. Publish it with a normal Merge Request.

  2. Create an issue: "Add a hobbies section to the about-me.md file".

  3. Ask your agent to work on that issue following the rules: new branch, diff and message before the commit, confirmation before the push.

  4. When it shows you the diff, review it with this chapter's list. Ask for at least one correction, even a small one.

  5. Confirm the commit and the push. Ask it for the list of commands it ran.

  6. Verify manually in GitLab: that the branch exists with the right name, that the commit has a good message, that the diff in the Merge Request is the one you approved, and that the description includes Closes #number.

  7. Also verify from the terminal with git log --oneline and git show.

  8. Merge the Merge Request yourself and check that the issue closed.

  9. If you prefer the script, repeat the steps with publish.sh and check the log file at the end.

Chapter 12. Investigating History: Git as a Detective

Git's history is not just a record: it is the tool for answering questions like "who changed this?", "when did it start failing?" or "what is the difference between my branch and main?". In this chapter you will learn to search the history, compare versions and understand how branches are combined inside.

Why it is worth learning to investigate

When something fails in a system, the first question is almost never "how do I fix it?". It is "what changed?". If you know how to search the history, you find the responsible commit, who made it and why in minutes. Without that, you have to guess.

It is also useful for calmer things: understanding why a part of the project is written a certain way, remembering what you did last week, or preparing a summary of changes for your manager.

This is where the value of the good commit messages from chapter 3 shows. A history full of changes and fixes is no use to any detective.

Filtering the history with git log

You already know git log --oneline. These variations let you search for something specific:

QuestionCommand
What did Ana do?git log --oneline --author="Ana"
What changed this week?git log --oneline --since="1 week ago"
What changed between two dates?git log --oneline --since="2026-09-01" --until="2026-09-30"
Which commits touched this file?git log --oneline -- contact.md
Which commits mention "hours" in the message?git log --oneline --grep="hours"
Which commit added or removed this text?git log --oneline -S "500-0000"
How many files did each commit change?git log --stat

You can combine them. For example, Ana's commits that touched contact.md this month:

git log --oneline --author="Ana" --since="1 month ago" -- contact.md

The most powerful one for investigating errors is -S. It finds the commits where a text appeared or disappeared. If a phone number changed and nobody knows when, git log -S "old-number" takes you straight to the commit.

Seeing a file as it was before

To see a complete file exactly as it was in a commit, without changing anything in your folder:

git show a3f9c21:contact.md

It is like opening an old photo of the file. If what you want is to recover it, use git restore --source from chapter 7.

git blame: who wrote each line?

git blame contact.md

It shows the file line by line and, next to each one, the commit, the author and the date of the last change:

a3f9c21 (Ana Pérez  2026-10-01) Hours: Monday to Friday, 8:00 to 5:00
7b2e104 (Luis Gómez 2026-09-15) Phone: 500-0000

To see only some lines, for example lines 10 to 20:

git blame -L 10,20 contact.md

In GitLab you have the same thing more comfortably: open the file and press the Blame button. You can click each commit to see the full change.

About the name. Blame means "to blame" in English, but don't use it to hunt for culprits. Use it to find who to ask and to understand the context. The person who wrote that line is the best one to explain why it is like that. And that person may be you, six months ago.

Comparing versions and branches

git diff is not only for your unsaved changes. It also compares any pair of moments:

git diff a3f9c21 7b2e104                 # Between two commits
git diff main feature/form               # Between two branches
git diff main feature/form --stat        # Only which files change and how much
git diff main -- contact.md              # One file against main

To know which commits your branch has that main doesn't have yet:

git log --oneline main..feature/form

And the other way around, what main has that your branch is missing:

git log --oneline feature/form..main

If the second command shows many commits, it is a sign that your branch is falling behind and it is time to bring in main (chapter 4).

In GitLab, the equivalent option is under Code > Compare revisions: you choose two branches, tags or commits and see all the differences.

git fetch and git pull: look before you combine

Until now you have used git pull to bring in changes. Actually pull does two things in a row:

  1. git fetch: downloads the new information from GitLab, without touching your files or your branch.

  2. git merge: combines that information with your branch.

Sometimes it is good to do only the first part, to look before combining:

git fetch
git log --oneline main..origin/main     # What is new on GitLab?
git diff main origin/main --stat        # Which files changed?

origin/main is the copy your computer keeps of how main is on GitLab. After reviewing, if everything is fine, run git pull (or git merge origin/main).

It is like the mailbox from chapter 4: fetch brings the letters in, and you decide when to open them.

How branches are combined inside

In chapter 5 you saw the squash option. It is worth understanding the four ways Git can combine one branch with another, because each leaves a different history.

Fast-forward

If main hasn't changed since you created your branch, Git only has to move the label of main to your last commit. No new commit is created:

Before:   main: A --- B
                      \
         branch:       C --- D

After:    main: A --- B --- C --- D

Merge commit

If main did change, Git creates a special commit that joins the two lines. That commit has two "parents":

main: A --- B --- E ------- M
             \             /
branch:       C --- D ----

Advantage: the history shows exactly when work happened in parallel and when it was joined. Disadvantage: with many branches, the drawing becomes a tangle.

Squash

All the commits of your branch become one when they enter main:

main: A --- B --- E --- S     (S contains C + D together)

Advantage: main stays clean, one commit per task. Disadvantage: the detail of the intermediate steps is lost.

Rebase

Instead of joining the lines, Git "rewrites" your commits as if you had made them after the latest changes in main:

main: A --- B --- E --- C' --- D'

Advantage: a straight-line history, very easy to read. Disadvantage: it rewrites your commits (that is why they carry an apostrophe: they are new copies, with other identifiers).

The golden rule of rebase: never rebase commits that other people have already downloaded. If you do, your history and theirs stop matching and you cause them serious problems. Use it only on your own branch, before sharing it, and when you feel confident with everything above.

Which one to use?

Usually you don't decide this yourself: your team defines it in the project configuration on GitLab (Settings > Merge requests > Merge method). What matters is that you understand why your project's history looks the way it does.

MethodResulting historyCommon in
Merge commitShows branches and mergesTeams that want full traceability
SquashOne commit per task in mainTeams that prioritize a clean main
Fast-forward / rebaseStraight lineExperienced teams with short branches

Finding when an error started

When you know something worked before and doesn't now, you can search for the culprit commit step by step:

  1. Find a moment when it worked (an old commit or tag).

  2. Review the intermediate commits with git log --oneline good-commit..main.

  3. If there are few, read their messages and changes with git show.

  4. If there are many, test the project at a commit from the middle. Depending on whether it works or not, you will know which half has the error. Repeat.

Git automates this "split in half" method with a command called git bisect. We won't look at it in depth, but now you know it exists and what it is for: when you need it someday, the idea will already feel familiar.

Real example: the phone number that changed by itself

A user reports that the site's contact phone number is wrong. Nobody remembers changing it.

Ana searches for the correct number in the history:

git log --oneline -S "500-0000"

Two commits appear: the one that added the number months ago, and one from last week that removed it, with the message Update footer. Ana opens it with git show and sees that, while reorganizing the footer, an old phone number was copied by mistake.

With git blame she confirms that the current line comes from that commit. She writes to the person who made it, they figure out together what happened, and Ana corrects the number on a branch fix/contact-phone with her Merge Request. Everything in fifteen minutes and without blaming anyone.

Practical exercise

In your practice-git project, which by now has several commits:

  1. List only your commits from this week using --author and --since.

  2. Search with --grep for a commit whose word you remember.

  3. Use git log -S to find the commit that added a specific line of README.md.

  4. Open hours.md (from chapter 6) with git blame and then with GitLab's Blame button.

  5. Show how README.md looked in your first commit with git show code:README.md.

  6. Create a branch, make two commits and compare it with main using git diff main your-branch --stat and git log --oneline main..your-branch.

  7. Run git fetch and compare main with origin/main before running git pull.

  8. Run git log --oneline --graph --all and find a merge commit from the earlier chapters. How many parents does it have?

  9. Check in GitLab, under Settings > Merge requests, which merge method your project uses.
