Introduction

This book is for you if you ever lost a file, overwrote a teammate's work, or felt scared to touch a shared project. You don't need to know how to program. You only need the willingness to work with more order and fewer scares.

Why I wrote this book

I learned Git on my own, with tutorials, trial and error. For a long time I did something I laugh about today: I saved everything at once, without looking at what I was saving. What was ready and what wasn't, everything went into the same package.

I also lived through Git's other great scare: a huge conflict caused by keeping two versions of the work apart for weeks. When I finally wanted to bring them together, there were crossed changes everywhere. It took me far longer to fix that than to do the original work.

And as an instructor and a teammate, I have seen a mistake that repeats a lot: when a conflict appears, people panic and "solve" it by deleting someone else's work. The problem disappears from the screen, but someone's work is gone.

None of this happens because people are careless. It happens because nobody explained Git calmly, with real examples and without strange words. That is what I try to do here.

Who I am

I am Marta Magallón, a systems programmer analyst. Today I work with GitLab at my job and with GitHub on my personal projects. I write code in Cursor and use artificial intelligence as a support tool, but I review every change before I publish it. I was a Python instructor at the Technological University of Panama, and there I learned that almost everything makes sense when it is explained with a good example.

How this book is organized

Every chapter has the same structure, so you always know what to expect:

  1. A real story that shows the problem.

  2. The explanation, step by step and in plain language.

  3. Examples you can copy and try.

  4. A practical exercise for you to do.

  5. A checklist to confirm that you understood.

At the end you will find a 7-day action plan, a glossary and a cheat sheet with all the commands.

How to read the commands

You will see blocks like this:

git status

That is something you type in the terminal: a window where you give orders to your computer by typing instead of clicking. Don't be scared. In chapter 2 I show you how to open it, and you will see it is easier than it looks.

We will use GitLab, but it also works for GitHub

The examples use GitLab, which is what many institutions and companies use. If you use GitHub, almost everything works the same way. When something has a different name, you will see a box like this one:

On GitHub it is called… What GitLab calls a Merge Request, GitHub calls a Pull Request. It is the same thing with a different name.

What you will achieve by the end

When you finish this book you will be able to:

  • Download a project from GitLab and work on it without fear of breaking anything.

  • Save your changes with clear messages your team understands.

  • Work in branches to try things without touching the main version.

  • Ask for your work to be reviewed with a Merge Request and respond to comments.

  • Resolve conflicts without erasing anyone's work.

  • Undo mistakes calmly, knowing which command to use in each case.

  • Organize tasks in GitLab and read whether a pipeline passed or failed.

  • Use an AI agent or script to help you, without losing control of what gets published.

What you need to get started

  • A computer with Windows, Mac or Linux.

  • An internet connection.

  • A free GitLab account (I explain how in chapter 1).

  • A text editor. A plain notepad will do, but I recommend VS Code or Cursor, which are free and show Git changes in colors.

  • About two or three hours per chapter if you do the exercises at a calm pace.

You don't need to know how to program. The exercises use simple text files so you can focus on Git and not on code.

How to get the most out of it

  • Read with the terminal open. Git is learned by doing. Every time you see a command, try it in your practice project.

  • Don't skip the exercises. They are designed so you can make mistakes in a safe place, before making them in a real project.

  • Use the checklists honestly. If you can't tick a point, go back to that part of the chapter before moving on.

A promise

You are going to make mistakes while you learn. That is fine. One of the best things about Git is that almost everything can be undone. Chapter 7 is dedicated exactly to that. So take a breath, open your computer, and let's begin.

Chapter 0. The Chaos Before Git

Saving versions by hand works when you work alone and with few files. As soon as another person joins, or the project grows, it becomes a mess you cannot control. This chapter shows you why, and what problem Git comes to solve.

The folder everyone has had

You surely recognize something like this:

Report/
├── report.docx
├── report_v2.docx
├── report_v2_reviewed.docx
├── report_final.docx
├── report_final_REALLY_FINAL.docx
└── report_final_v3_DEFINITIVE_Carlos.docx

Now answer yourself honestly:

  • Which is the good version?

  • What changed between report_v2 and report_final?

  • Who made each change, and why?

  • If Carlos and you edited at the same time, how do you combine what both of you did?

Nobody knows for sure. And that is with a single document. Imagine a system with hundreds of files and five people working at the same time.

The four problems of saving by hand

1. You don't know what changed. You have two almost identical files and you would have to read them line by line to find the difference.

2. You don't know who or why. Even if you find the change, there is no note saying who made it or what they were trying to solve.

3. You can't safely go back. If something breaks, which copy do you return to? And what do you lose by doing it?

4. Teamwork is a lottery. Two people edit the same file, send it by email or chat, and one of them ends up overwriting the other's work without noticing.

What version control is

Version control is a system that keeps the complete history of your project for you. Think of it as an automatic logbook.

Every time you finish a step, you tell the system: "save this moment". And the system records:

  • What changed, exactly, line by line.

  • Who changed it.

  • When it changed.

  • Why, with a short message that you write.

Instead of having six copies of the report, you have one single file with its whole history stored behind it. You can see any past version whenever you want, without filling the folder with copies.

A comparison that helps: save points

If you have played video games, you know save points. Before facing the final boss, you save the game. If you lose, you return to that point without starting from zero.

Git works the same way. Each "save" is a snapshot of your project at that moment. If something goes wrong, you return to the previous snapshot. The difference is that in Git every snapshot carries a note explaining what you did.

And teamwork

The most powerful part is not saving your history. It is that several people can work on the same project at the same time without stepping on each other.

Each person works on their own copy. When they finish, the system helps combine the changes. If two people touched the same line, the system does not decide on its own: it warns you and asks you to choose. That is called a conflict, and we dedicate all of chapter 6 to it.

It is not only for programmers

Git was born for code, but it works for any work done with plain text files:

  • Technical documentation and manuals.

  • Websites.

  • Server configuration files.

  • Books and documents written in text format.

  • Data analysis scripts.

If you work in technology, in any role, sooner or later you will touch a repository. It is better to do it without fear.

A little history: where Git came from

Linus Torvalds created Git in 2005, the same person who created Linux. Thousands of people around the world worked on the Linux code and needed a fast tool to combine their changes without depending on a central server. The tool they had used stopped being available to them, so Torvalds wrote his own in a few weeks.

Today Git is the standard. It is used from students with their first project to banks, governments and the largest technology companies in the world. Learning it is not learning a fashionable tool: it is learning the common language of work in technology.

Centralized or distributed: why it matters

Before Git there were other version control systems. Many were centralized: the history lived on a single server. If the server went down, nobody could save anything. And if it got damaged without a backup, everything was lost.

Git is distributed: every person who downloads the project has a complete copy of the whole history. That gives three very practical advantages:

  1. You can work without internet. You save your progress on your computer and share it when you reconnect.

  2. It is fast. Viewing the history or comparing versions doesn't depend on the network.

  3. There are many copies. If the server has a problem, any copy held by a team member can help recover the project.

What Git is not

So you don't get any surprises, let's clear up some common confusions:

  • Git is not an automatic backup. It only saves what you tell it to save, and it only shares what you publish. If you never push, your work lives only on your computer.

  • Git is not Google Drive or Dropbox. Those programs sync your files on their own, at every moment. Git saves moments that you choose, with an explanation. It takes more work, but it gives you full control.

  • Git is not ideal for heavy files like videos or databases. It works wonderfully with text files. With large or binary files (Word, Excel, images) it can store them, but it won't show you what changed inside.

  • Git does not decide for you. If two people change the same thing, it doesn't pick a version at random: it asks you. That is an advantage, even though it scares people at first.

Myths that hold people back

"Git is only for expert programmers." False. The basics are learned in an afternoon. The advanced parts you learn when you need them.

"If I use Git, I can break everyone's project." Very hard, if you follow the practices in this book. You will work in your own copy and on your own branch, and changes are reviewed before they enter the main version.

"The terminal is dangerous." Most of the commands you will use only look or save. The few that can delete something I will mark with a warning.

"If I make a mistake, I lose everything." Quite the opposite. Git keeps so much history that almost everything can be recovered. It is harder to lose work with Git than without it.

What it costs not to have version control

In teams and institutions where version control is not used, the same scenes repeat:

  • A system stops working after a change and nobody knows what was touched.

  • The only person who knew where the good version was went on vacation, or quit.

  • An old version is deployed to production because someone uploaded the wrong copy.

  • To find out who made a change, you have to dig through emails and chat messages from months ago.

None of that is the fault of the people. It is a lack of tools and process. Git plus a platform like GitLab solves both.

Real example: the same problem, with and without Git

Without Git. Ana and Luis maintain the website of their office. Ana changes the opening hours. Luis, at the same time, corrects the phone number. Luis uploads his version to the server after Ana. Result: the phone number is right, but the opening hours went back to the old ones. Nobody notices until a customer arrives at a closed office.

With Git. Ana saves her change with the message "Update opening hours". Luis saves his: "Fix contact phone number". When Luis tries to publish, Git warns him that there are new changes from Ana. Luis pulls them first, Git combines both changes because they touch different parts, and everything is published together. In addition, anyone can later see who changed the opening hours and when.

Exercise

You don't need to install anything yet.

  1. Open the folder of some project or work of yours (documents, presentations, code).

  2. Look for repeated files with names like final, v2, copy or new.

  3. Choose one and answer on a sheet of paper: which is the good version, what changed between versions, and who made each change?

  4. Write down how long it took you to answer, and how sure you really are of each answer.

Keep that sheet. When you finish the book, look at it again and compare it with what Git would let you answer in seconds.

Chapter 1. Git, GitLab and GitHub Without the Confusion

Git is the tool that keeps the history of your project on your computer. GitLab and GitHub are websites where you keep a copy of that project to share it with your team. Confusing them is the number one mistake when starting out, so let's separate them clearly.

A comparison: the notebook and the library

Imagine that Git is your notebook. In it you note every step of your work, with date and explanation. The notebook is yours, lives on your computer, and works even without internet.

GitLab and GitHub are the library. It is a shared place where you leave a copy of your notebook so your team can see it, copy it and add things to it. The library also has meeting rooms, bulletin boards, and people who review what comes in.

GitGitLabGitHub
What it isA program you installA website / platformA website / platform
Where it livesYour computerOn the internet or on your company's own serverOn the internet
Works without internetYesNoNo
What it is forSaving the history of changesSharing, reviewing and organizing teamworkSharing, reviewing and organizing teamwork
Typical useAlways, with either of the twoCompanies and institutions that want their own controlPersonal projects and open source

An important detail: GitLab can be installed on your own company's servers. That is why it is very common in public institutions and organizations that don't want their code to leave their network. GitHub, on the other hand, is widely used for personal and open source projects.

In my case I use both: GitLab at work and GitHub for my personal projects. What you learn here serves you for both.

The words you will hear all the time

Repository (or "repo"). The folder of your project with its whole history saved. From the outside it looks like a normal folder. Inside it has a hidden folder called .git where Git keeps the logbook. Never touch that folder by hand.

Local repository. The copy of the project that is on your computer.

Remote repository. The copy that is on GitLab or GitHub. It is the one the whole team shares.

Commit. A save point. A snapshot of the project at a moment, with a message that explains what you changed. It is the basic unit of Git.

History. The list of all the commits, from the most recent to the oldest. It is the complete story of the project.

Branch. A parallel line of work. It lets you try things without touching the main version. We look at it in depth in chapter 4.

Local and remote: the idea that confuses the most

Here is the key that many people find hard at first: saving a change on your computer is not the same as publishing it for the team.

The path of a change is like this:

  1. You edit a file on your computer.

  2. You make a commit: the change is saved in your notebook, only on your computer.

  3. You make a push (send): you send your commits to GitLab. Now the team can see them.

  4. Your teammates do a pull (fetch and combine): they bring your changes to their computers.

If you commit but never push, your work exists only on your computer. If your disk fails, it is lost. And your team never saw it. This misunderstanding causes a huge number of "but I did save it!" problems.

Why this makes teamwork possible

Each person on the team has their own complete copy of the project, with the whole history. They work calmly on their computer. When they finish something, they send it to the shared copy on GitLab.

GitLab acts as the meeting point. That is where everyone's changes come together, are reviewed before being accepted, and a record of every decision is kept. Nobody sends files to anyone by email.

What is inside a commit

Each commit stores five things. Knowing them helps you read any history:

PartWhat it isExample
IdentifierA unique code, generated by Gita3f9c21 (short version)
AuthorName and email of whoever made the changeAna Pérez ana@ejemplo.com
DateWhen it was madeOctober 8, 10:42 a.m.
MessageThe explanation of the changeFix contact phone number
Previous commitThe commit it starts from7b2e104

That last point is key: each commit points to the previous one. That forms a chain, like the links of a chain or the numbered pages of a diary. Thanks to that chain, Git can rebuild the project exactly as it was at any moment.

That is also why a commit cannot be "edited" in secret. If you change something in an old commit, its identifier changes, and so does every commit that comes after it. It is a protection: the history can be trusted.

Other platforms you will hear about

GitLab and GitHub are the best known, but not the only ones. All of them use Git underneath, so what you learn here works on any of them:

  • Bitbucket: common in companies that use other Atlassian tools, such as Jira.

  • Azure DevOps: widely used in organizations that work with Microsoft technologies.

  • Gitea and Forgejo: lightweight options to install on your own server.

The menus and some names change. Git is the same.

Terminal or buttons: what is better to use?

You can use Git in three ways, and they are not mutually exclusive:

  1. The terminal. You type the commands. It is what we will use most in this book, because it forces you to understand what is happening and it works the same on any computer.

  2. Your code editor. VS Code and Cursor have a Git panel with buttons to view changes, commit, push and pull. It is comfortable and visual.

  3. The GitLab website. You can edit files and make commits directly in the browser. It is good for small changes, such as correcting a text in the README.

My recommendation: learn with the terminal and then use whatever feels most comfortable to you. When something fails, knowing what each command does will get you out of the problem. The editor's buttons only run those same commands for you.

Public, private and internal projects

When you create a project in GitLab, you choose who can see it:

VisibilityWho can see itWhen to use it
PrivateOnly the people you inviteYour company's work, personal projects in progress
InternalAnyone with an account on that GitLabProjects the whole organization may consult
PublicAnyone on the internetOpen source projects, portfolios, educational material

When in doubt, start with private. You can always open it later. The reverse is more delicate: what was public may already have been copied.

Frequently asked questions

Is Git free? Yes. Git is free software. GitLab and GitHub have free plans that are more than enough for learning and for small teams.

Do I need internet to use Git? To save commits, no. To share them (push) or bring in other people's (pull), yes.

Can I use Git with Word or Excel documents? You can store them, but Git won't be able to show you what changed inside, nor help you combine changes from two people. It works best with plain text files: code, Markdown, configuration files.

What happens if I delete the project folder on my computer? If you had pushed, nothing serious: you clone it again from GitLab. What you had not published is lost.

Real example: reading a project's history

Open any public project on GitLab or GitHub and go to the commits section. You will see something like this:

Fix the total calculation in the monthly report
Ana Pérez · 2 hours ago

Add date filter to the search
Luis Gómez · yesterday

Update installation instructions in the README
Ana Pérez · 3 days ago

Without opening a single file you already know what has happened in the project, who did it and when. If you click on a commit, GitLab shows you exactly which lines were added (in green) and which were removed (in red).

Practical exercise

  1. Create a free GitLab account (gitlab.com) if you don't have one yet. If your organization has its own GitLab, use that one.

  2. Find any public project that interests you and open it.

  3. Read its README and write in one sentence what the project does.

  4. Go to the commits section. Choose three commits and note: who made it, when, and what its message says.

  5. Open one of those commits and look at the lines in green and red. Do you understand what changed?

  6. Browse the menu on the left and locate: Issues, Merge requests and Pipelines. Just look at them, don't touch anything.
