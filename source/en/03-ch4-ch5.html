Chapter 4. Branches: Work Without Fear

A branch is a parallel working copy inside the same project. It lets you try things, make mistakes and finish a change without touching the main version, which is the one the whole team uses. If you learn only one habit from this chapter, let it be this one: never work directly on main.

Why branches exist

Imagine your team maintains the office website. The version on main is the one that works and the one that gets published. Now you are asked to redesign the contact form, which will take you three days.

If you work directly on main:

  • For three days, the main version has a half-finished form.

  • If in the meantime someone needs to fix an urgent bug, they would have to publish your unfinished work too.

  • If halfway through you decide your idea doesn't work, undoing it is complicated.

With a branch, you do the whole redesign separately. main stays intact and stable. When you finish and someone reviews your work, you combine it with main. If your idea didn't work, you delete the branch and nobody ever knew.

A comparison: the draft

Think of main as the official document that has been published. A branch is a draft that you take from that document. You write, cross out and rewrite whatever you want in your draft. The official document doesn't change.

When your draft is ready, you ask for it to be reviewed. If it is approved, its changes go into the official document. That is called merging.

And the best part: each person on the team can have their own drafts at the same time, each one for a different task.

What a branch looks like inside

Remember from chapter 1 that each commit points to the previous one, forming a chain. A branch is simply a label that points to the latest commit of a line of work. When you make a commit on that branch, the label moves forward.

main:            A --- B --- C
                        \
contact-form:            D --- E

Here, main has commits A, B and C. The branch contact-form left from commit B and has its own commits, D and E. The two lines move forward without getting in each other's way. When you merge, the changes from D and E enter main.

That is why creating a branch is instant and takes no space: Git doesn't copy files, it just creates a new label.

Branch commands

See your branches

git branch

It shows your local branches. The one with an asterisk (*) is the one you are on now. To also see the branches that exist in GitLab:

git branch -a

The ones that start with remotes/origin/ are the GitLab ones.

Create a branch and switch to it

First, make sure you start from the latest version of main:

git switch main
git pull

Now create your branch and enter it with a single command:

git switch -c feature/contact-form

The -c means create. From this moment on, all your commits go to this branch.

And git checkout? In older tutorials you will see git checkout -b branch-name. It does the same thing. git switch is the modern and clearer way, because checkout does too many different things. In this book we use switch.

Switch between branches

git switch main
git switch feature/contact-form

When you switch branches, the files in your folder change to show the state of that branch. Don't be alarmed if a file "disappears": it is still saved in the other branch.

Publish your branch to GitLab

The first time you push a new branch:

git push -u origin feature/contact-form

After that first time, git push is enough. Publishing your branch has two advantages: your work is backed up on GitLab and your teammates can see it.

Keep your branch up to date with main

While you work on your branch, others keep merging changes into main. If your branch falls behind for a long time, joining it at the end will be harder. That is why it is good to bring the new changes from main into your branch every so often:

git switch main
git pull
git switch feature/contact-form
git merge main

This brings the new changes from main into your branch. If nobody touched the same things you did, it combines on its own. If there were changes on the same lines, a conflict will appear, and we solve it in chapter 6. It is better to solve a small conflict today than a huge one in a month.

You will hear about rebase. It is another way to update your branch that leaves a more linear history. It is useful, but it carries more risks for beginners. Stick with merge until you feel confident with everything in this book.

Delete a branch

When your branch has already been merged into main, you no longer need it:

git switch main
git branch -d feature/contact-form

If Git refuses with a message like not fully merged, it is protecting you: that branch has commits that are not in main. Check before deleting. If you are completely sure you want to throw that work away, use -D in capitals. Use it with great care.

To delete the branch on GitLab:

git push origin --delete feature/contact-form

Usually it is not necessary: GitLab can delete it automatically when you complete the Merge Request (we see this in chapter 5).

What happens to unsaved changes when you switch branches

This is a very common question. If you have modified files without a commit and switch branches, one of two things can happen:

  1. The changes travel with you to the new branch, if they don't clash with anything. This is confusing, because it looks as if the change "moved" to another branch.

  2. Git won't let you switch and tells you your changes would be overwritten. It is protecting you.

The simple rule: before switching branches, leave your folder clean. Commit what you have, or save it temporarily with git stash (we see it in chapter 7). Always check with git status before switching.

How to name branches

A good name says what kind of change it is and what it is about. The most used convention is type/short-description:

PrefixWhat forExample
feature/Something newfeature/contact-form
fix/Fixing a bugfix/footer-phone
hotfix/Urgent fix for productionhotfix/login-crash
docs/Documentation onlydocs/install-instructions
refactor/Reorganizing without changing what it doesrefactor/folder-structure
chore/Maintenance, configurationchore/update-dependencies

Rules for the name:

  • Everything in lowercase.

  • Words separated with hyphens, no spaces.

  • No accents or special letters: write installation, not instalación.

  • Short but clear: three or four words are enough.

  • If you work with issues (chapter 8), include their number: fix/42-footer-phone. That way anyone knows which task it belongs to.

The most important thing is that the whole team uses the same convention. If your team already has one, follow it even if it is different from this one.

Short-lived branches: the rule I learned the hard way

A branch should live days, not weeks. The longer it lives apart from main, the more changes both accumulate, and the harder it is to combine them. In chapter 6 I tell you about the huge conflict I lived through by not respecting this rule.

How to keep branches short:

  • Split big work into small pieces. Instead of one branch called "full website redesign", make one for the header, another for the form, another for the footer.

  • Merge often. Each finished and reviewed piece goes into main.

  • Bring main into your branch frequently if your work drags on.

  • One branch, one task. Don't use the form branch to "while I'm at it" fix something else.

Branches in GitLab

In the menu Code > Branches you see all the branches of the project. For each one, GitLab shows you:

  • Its last commit and who made it.

  • How many commits it is ahead of main (changes it has and main doesn't) and how many behind (changes from main it is missing).

  • A button to create a Merge Request.

  • Whether it is protected (chapter 10).

You can also create branches from there with New branch, although then you will need to bring it to your computer:

git fetch
git switch branch-name

git fetch brings the new information from GitLab without combining it with your work. It is like checking the mailbox without opening the letters.

Seeing branches as a drawing

To view the history with its branches drawn in the terminal:

git log --oneline --graph --all

You will see lines and asterisks that show where each branch split off and where it merged back. At first it looks like a tangle, but with practice it reads like a subway map. In GitLab you have the same view, prettier, under Code > Repository graph.

Real example: an urgent bug in the middle of your work

Ana is on the branch feature/contact-form, halfway through the redesign. Suddenly she is told that the phone number in the footer is wrong and it has to be fixed today.

  1. Ana commits what she has on her branch: git commit -m "Progress: structure of the new form".

  2. She goes back to main and updates it: git switch main and git pull.

  3. She creates a branch for the fix: git switch -c fix/footer-phone.

  4. She corrects the phone number, commits, pushes, and asks for review.

  5. The fix is merged into main and published the same day.

  6. Ana returns to her branch: git switch feature/contact-form.

  7. She brings the fix into her branch: git merge main.

The urgent bug was resolved without publishing the half-finished form. And Ana's branch is up to date. This is impossible to do cleanly if everyone works on main.

Practical exercise

Use your practice-git project.

  1. Make sure you are on main and up to date: git switch main and git pull.

  2. Create a branch called feature/about-me-section.

  3. Create a file about-me.md with three lines about yourself. Commit it.

  4. Add one more line and make another commit.

  5. Publish your branch with git push -u origin feature/about-me-section.

  6. Go back to main with git switch main and look for the file about-me.md with ls. It isn't there. Go back to your branch: it is there.

  7. Open GitLab, go to Code > Branches and find your branch. How many commits is it ahead of main?

  8. Run git log --oneline --graph --all and find your two commits.

  9. Extra challenge: from main, create fix/readme-typo, correct or add something in the README, commit and push. Now you have two independent branches.

Don't delete these branches yet: you will use them in chapter 5.

Chapter 5. Merge Requests: Ask Permission to Integrate

A Merge Request is a formal request to combine your branch with main. It is the moment when another person looks at your work before it enters the version the whole team uses. Here you will learn to create it, describe it well, receive comments without taking them personally, and complete the merge.

On GitHub it is called… a Pull Request (PR). It works exactly the same. When you hear "open a PR" or "open an MR", it is the same thing.

Why not simply merge

Technically you could combine your branch with main from the terminal, without asking anyone. But you would lose three very valuable things:

  1. Another pair of eyes. Whoever writes a change almost never sees their own mistakes. Someone who arrives fresh finds the detail you missed.

  2. A record of the decision. The Merge Request keeps what changed, why, who reviewed it and what was discussed. A year from now, someone can understand why the system works the way it does.

  3. Team learning. By reviewing other people's work you learn how they think and get to know parts of the project you don't touch.

In many teams, moreover, main is protected: nobody can merge without an approved Merge Request. We look at this in chapter 10.

If you want to go deeper into how to review code well, I have a book dedicated only to that. Here we focus on the process inside GitLab.

The full path of a Merge Request

  1. You work on your branch and push.

  2. You open the Merge Request: "I want to merge feature/x into main".

  3. You assign one or more people to review it.

  4. They review it and leave comments.

  5. You respond and fix things with new commits on the same branch.

  6. They approve.

  7. It is merged and the branch is deleted.

  8. Everyone updates their main with git pull.

Let's go step by step.

Step 1: create the Merge Request

There are three ways, all of them lead to the same form:

From the terminal. When you push a new branch, GitLab answers with a link like this one:

remote: To create a merge request for feature/contact-form, visit:
remote:   https://gitlab.com/your-username/project/-/merge_requests/new?...

Copy the link and open it in the browser.

From the GitLab notice. When you open the project after a push, GitLab shows a notice with your branch and a Create merge request button.

From the menu. Go to Code > Merge requests > New merge request. Choose your branch as the source (source branch) and main as the target (target branch).

Always check the source and the target before going on. A common mistake is opening the Merge Request toward the wrong branch.

Step 2: describe the change well

This is the part people neglect most and the one that helps the reviewer the most. A good description saves your teammate from guessing what you did.

The title. Like a good commit: start with a verb and say what the change does.

Confusing titleClear title
Form changesAdd email validation to the contact form
fixFix wrong phone number in the footer
Ana's branchUpdate installation instructions for Windows

The description. Use this template. You can copy it as it is:

## What changes
Adds email validation to the contact form.
Before, it was possible to send it with a misspelled email.

## Why
We were receiving messages we could not reply to.
Related to issue #42.

## How to test it
1. Open the contact page.
2. Type an email without @ and press Send.
3. The message "Invalid email" should appear.

## Screenshots
(before / after, if applicable)

## Pending or doubts
I did not validate specific domains. Is it needed?

Not every section always applies. But what changes, why, and how to test it should be in almost every Merge Request.

If you write Closes #42 in the description, GitLab will close issue 42 automatically when it is merged. We see this in chapter 8.

Step 3: the rest of the form

FieldWhat it isRecommendation
AssigneeThe person responsible for the Merge RequestUsually you
ReviewerWho should review itSomeone who knows that part of the project
LabelsTags to classify itThe ones your team uses: bug, documentation, etc.
MilestoneWhich delivery it belongs toIf your team works in deliveries
Delete source branchDelete your branch when mergingCheck it. It avoids old branches piling up
Squash commitsCombine all your commits into one when mergingDepends on your team's habit

What is squash? If your branch has ten commits like "progress", "more progress", "fix typo", squash turns them into one clean commit when it enters main. That way the main history stays tidy. Some teams always use it; others prefer to keep every commit.

Merge Requests in draft

If your work is not finished but you want to show it or ask for an early opinion, mark it as a draft (Draft). You can do it with the Mark as draft checkbox or by starting the title with Draft:.

A draft Merge Request cannot be merged. It is a clear way of saying: "it is not ready yet, but take a look". When you finish, remove the mark with Mark as ready.

Opening a Merge Request early, as a draft, is a very good practice. You get feedback before going too far in a wrong direction.

Step 4: review your own Merge Request first

Before asking someone to review, review it yourself. Go to the Changes tab and read your changes as if they were someone else's. Look for:

  • Files that shouldn't be there.

  • Test text, forgotten comments or unfinished things.

  • Spelling mistakes in texts the user will see.

  • Changes that have nothing to do with the task.

You will be surprised how many things you find. And each one you fix yourself is one your teammate doesn't have to point out.

How to review in GitLab (if you are asked to review)

When someone assigns you as a reviewer:

  1. Read the description first. Understand what it is trying to solve before looking at the changes.

  2. Open the Changes tab. You will see each file with added lines in green and removed lines in red.

  3. Comment on a line. Hover over the line number and click the comment icon. Write your observation.

  4. Suggest a concrete change. In the comment, use the Insert suggestion button. You write how the line should look and the author can apply it with one click.

  5. Group your comments. Use Start a review instead of Add comment now. That way your comments are published together at the end, instead of sending the author ten notifications.

  6. Decide. If everything is fine, press Approve. If there are things to correct, submit your review and wait for the changes.

How to write good comments

The review is about the code, not the person. A few guidelines:

Instead ofTry
"This is wrong.""Here we need to validate that the date is not empty. If it arrives empty, the form fails."
"Why did you do it this way?""What led you to this approach? I ask because X could be simpler."
"Change the name.""Suggestion: monthly_total would be clearer than tm."
(silence about what is good)"I liked how you separated this part, it reads very clearly."

It also helps to mark how important each comment is:

  • Blocking: it must be fixed before merging.

  • Suggestion: it would improve things, but it is not mandatory.

  • Nit (in Spanish you will see detalle): something minor, like a space or a word.

  • Question: it is not a request for a change, you just want to understand.

Step 5: respond to feedback

Receiving comments about your work can feel uncomfortable at first. Remember that review improves the result and protects you: it is better for a teammate to see the mistake today than for a user to see it tomorrow.

For each comment:

  1. Read it in full and make sure you understand it. If not, ask.

  2. If you agree, make the fix in your branch, on your computer:

git switch feature/contact-form
# you make the fix
git add fixed-file
git commit -m "Validate that the date is not empty"
git push

You don't need to open a new Merge Request. When you push to the same branch, the Merge Request updates itself with your new commits.

  1. Reply in the thread with something brief: "Fixed in the latest commit". If the reviewer used a suggestion, you can apply it directly with Apply suggestion.

  2. If you disagree, explain your reason respectfully. A good technical discussion is healthy. If you can't agree, ask for a third opinion.

  3. Mark the thread as resolved (Resolve thread) when it has been addressed. Some teams prefer that the person who wrote the comment resolves it: follow your team's habit.

  4. Let them know it is ready for another review. In GitLab you can request the review again with the icon next to the reviewer's name.

Step 6: complete the merge

When the Merge Request is ready, you will see the Merge button. GitLab may require some conditions before enabling it:

  • The necessary approvals.

  • All comment threads resolved.

  • The pipeline green (chapter 9).

  • No conflicts with main.

If everything is met, press Merge. Your changes enter main.

If GitLab says there are conflicts, you have to resolve them first. Chapter 6 shows you how.

Step 7: after the merge

Your branch is now in main, but your computer doesn't know it yet. Bring everything up to date:

git switch main
git pull
git branch -d feature/contact-form

Over time, your computer accumulates references to branches that were already deleted in GitLab. To clean them up:

git fetch --prune

What makes a good Merge Request big or small

Small Merge Requests are reviewed better and faster. One of 50 lines is reviewed carefully in ten minutes. One of 2,000 lines is hardly ever really reviewed: it gets approved out of exhaustion.

  • One Merge Request, one task. Same as branches.

  • If it is big, split it. Several small Merge Requests that are merged one after another.

  • Separate the mechanical from the important. If you renamed many files and also changed the logic, make two Merge Requests. That way the reviewer can focus on what matters.

Real example: a Merge Request that improves thanks to review

Luis opens the Merge Request Add email validation to the contact form. In the description he explains what changes, why, and how to test it.

Ana reviews it. She leaves three comments: one blocking (the error message doesn't appear if the field is empty), one suggestion (a clearer function name, with the suggestion button) and one nit (a missing accent in a text).

Luis applies the suggestion with one click, fixes the empty field and the accent in a new commit, pushes and replies in each thread. Ana tests again, resolves the threads and approves. Luis merges, and the branch deletes itself.

Result: the empty-field bug never reached users. And there is a record of everything in GitLab.

Practical exercise

Use the branches you created in chapter 4. If you can, do it with another person as the reviewer; if not, play both roles yourself.

  1. Open a Merge Request from feature/about-me-section into main.

  2. Write a clear title and use the description template.

  3. Mark it as a draft. Then remove the mark with Mark as ready.

  4. Check the box to delete the branch when merging.

  5. Review it yourself first in the Changes tab.

  6. Leave a comment on one line, as if you were the reviewer. Use Insert suggestion to propose a change.

  7. Apply the suggestion, or fix it on your computer, commit and push. Verify that the Merge Request was updated.

  8. Reply to the comment and mark the thread as resolved.

  9. Merge.

  10. On your computer: git switch main, git pull and git branch -d feature/about-me-section.

  11. Repeat with the branch fix/readme-typo, this time trying the squash option.
