Chapter 8. Organize Your Work in GitLab

GitLab doesn't only store code: it is also where the team decides what to do, who does it and by when. With issues, labels, milestones, boards and the wiki, all the work stays connected: from the task to the commit that solved it. In this chapter you will learn to use those tools.

The problem with organizing through chat and email

Without a central place, tasks live in loose messages: "did anyone see the form thing?", "I think Luis was going to do it", "was that already fixed?". The questions repeat, tasks get lost and nobody knows what is pending.

With GitLab, each task has its own card, an owner and a status. And every change in the code can be linked to the task that asked for it. Six months later, anyone can see why a change exists and what discussion came before it.

Issues: a card for every task

An issue is a work card. It can be a bug to fix, a new feature, an improvement, a question or a documentation task. You create it in Plan > Issues > New issue.

The parts of an issue

FieldWhat it is for
TitleWhat needs to be done, in one line
DescriptionThe detail: context, steps, criteria for calling it done
AssigneeWho is responsible
LabelsTags to classify: type, priority, area
MilestoneWhich delivery or cycle it belongs to
Due dateDeadline
CommentsThe conversation about the task

Each issue gets an automatic number, such as #42. That number is its identity: you will use it to link it from commits, branches and Merge Requests.

How to write a good issue

A good issue can be picked up by another person without having to ask you anything. To report a bug, use this structure:

## What happens
When sending the contact form without a date, a blank page appears.

## Steps to reproduce
1. Go to the contact page.
2. Fill in name and email, leave the date empty.
3. Press Send.

## What should happen
The message "The date is required" should appear.

## Where
Chrome browser, production version from October 8.

## Screenshots
(attach)

To request something new:

## What is needed
A date filter in the document search.

## Why
Users take a long time to find documents from the current month.

## When we consider it done
- [ ] You can choose a start and end date.
- [ ] If no date is chosen, all results are shown.
- [ ] It works on mobile.

That last section, when we consider it done, is the most valuable. It avoids the argument "I thought it also included…". The - [ ] boxes can be ticked directly in GitLab as you progress.

Templates so you don't start from scratch

If your team always uses the same structure, save it as a template. Create the folder .gitlab/issue_templates/ in the repository and, inside it, one file per template, for example Bug.md and New-feature.md. When you create an issue, GitLab lets you choose it from a menu. The same works for Merge Requests in .gitlab/merge_request_templates/.

Working on an issue

  • Assign it to yourself before starting, so nobody does the same thing in parallel.

  • Comment progress and questions on the issue, not in chat. That way there is a record for whoever comes later.

  • Mention people with @username when you need their opinion.

  • Close it when it is finished, or let it close on its own with the Merge Request (we see this below).

Labels: classify to find

Labels are colored tags you put on issues and Merge Requests to classify and filter them. They are created in Manage > Labels.

A simple set that works in many teams:

GroupLabels
Typebug, new feature, improvement, documentation
Priorityhigh priority, medium priority, low priority
Statusto do, in progress, in review, blocked
Areaform, reports, database, server

Tips:

  • Few and clear. With a hundred labels nobody knows which to use.

  • One color per group. For example, reds for priority and blues for type. They can be read at a glance.

  • Write a description for each label, so everyone uses it the same way.

  • Agree on them as a team. Labels only work if everyone applies them with the same criteria.

With labels you can filter the issue list and answer questions like "which high-priority bugs are still open?" in two clicks.

Connecting commits, branches and Merge Requests to an issue

Here is the magic: GitLab links everything automatically if you mention the issue number.

In the branch name. Include the number, as you saw in chapter 4: fix/42-empty-date-form.

In the commit message. Add the reference:

git commit -m "Validate required date in contact form (#42)"

The commit will appear mentioned inside issue 42.

In the Merge Request description. Use a closing keyword:

Closes #42

When the Merge Request is merged into the main branch, GitLab closes issue 42 automatically. Fixes #42 and Resolves #42 work too. If you only want to link it without closing it, write Related to #42 or simply #42.

The most convenient shortcut: create the branch from the issue. Inside an issue you will see the Create merge request button (or Create branch). GitLab creates a branch with the issue's number and title, and a draft Merge Request already linked. You only need to bring it to your computer:

git fetch
git switch 42-empty-date-form

The result is a complete, traceable chain: issue → branch → commits → Merge Request → closed issue.

Milestones: group work by deliveries

A milestone is a goal with a date: a version, a two-week cycle or a delivery to a client. It groups the issues and Merge Requests that must be ready by that date. It is created in Plan > Milestones.

Examples:

  • Version 1.5 — from November 1 to 15.

  • Sprint 23 — two weeks of work.

  • Reports module delivery — for the date agreed with the user department.

When you open a milestone, GitLab shows a progress bar: how many issues are closed and how many are left. It is the fastest way to answer "are we going to make the date?".

Tip: if a milestone has too many open issues close to its date, it is better to consciously move some to the next one than to pretend everything will get done.

Boards: see the work at a glance

A board shows issues as cards in columns, in Kanban style. You find it in Plan > Issue boards.

By default it has two columns, Open and Closed. You can add columns based on labels. A typical board:

To doIn progressIn reviewClosed
#45 Date filter#42 Empty date in form#40 Phone in footer#38 New logo
#47 Export to Excel

When you drag a card from one column to another, GitLab changes its label automatically. If you drag it to Closed, the issue closes.

How to use it well:

  • Review it together in the team meeting, instead of asking one by one "how is it going?".

  • Limit what is "in progress". If one person has six cards in that column, something isn't working.

  • Keep it up to date. An outdated board is worse than no board, because it misleads.

  • Filter. You can view the board of a single milestone, a single person or a single label.

The wiki: the project's memory

The wiki is a documentation space inside the project, with pages written in Markdown (chapter 13). It is under Plan > Wiki.

What usually goes in the wiki:

  • User guides for the people who use the product.

  • Team procedures: how to publish a version, how to handle an emergency.

  • Important decisions and their reasons.

  • The project glossary and contacts.

  • Minutes or summaries of technical meetings.

Creating a page is simple: New page, write the title, the content in Markdown and save. To link another wiki page, use [text](page-name). Pages with names like guides/installation are organized into folders.

A useful fact: inside, the wiki is another Git repository. It has a change history, and you can clone it and edit it on your computer. The address to clone it appears in the wiki itself.

Wiki or a docs/ folder in the repository?

Wikidocs/ folder
How it is editedFrom the browser, easyWith commits and Merge Requests
Review before publishingNoYes, like the code
Goes along with each version of the codeNoYes
Ideal forGeneral guides, processes, team notesTechnical instructions that change with the code

Many teams use both: the wiki for general matters and docs/ for what must stay in sync with each version of the system.

Note about GitLab versions. Some advanced organization features (such as multiple boards per project, issue weights or epics) depend on the GitLab plan your organization uses. Everything in this chapter works on the free version, although the menus may vary a little.

On GitHub it is called… Issues and labels exist in the same way. Milestones too. Boards are called Projects. The wiki is in the Wiki tab. To close issues from a Pull Request you use the same words: Closes #42.

Real example: from report to closure

A user reports by email that the form shows a blank page. Ana doesn't leave it in the email: she creates the issue #42 Blank page when sending form without a date, with the steps to reproduce it, the labels bug and high priority, and assigns it to the milestone Version 1.5.

Luis assigns it to himself and moves it to In progress on the board. From the issue he presses Create merge request, brings the branch to his computer, fixes it and commits with (#42) in the message. The Merge Request already says Closes #42.

Ana reviews, approves, and Luis merges. The issue closes on its own and the card moves to Closed. The next day, Ana replies to the user with the link to the issue. If someone asks in six months why that validation exists, everything is there: the report, the discussion, the change and the review.

Practical exercise

In your practice-git project:

  1. Create four labels: bug, improvement, documentation and in progress, each with a color and a description.

  2. Create a milestone called Practice week 1 with a date seven days from now.

  3. Create three issues: an invented bug (using the bug template), an improvement (with done criteria as checkboxes) and a documentation task. Assign them to the milestone and add labels.

  4. Open the board and add the in progress column. Move an issue to that column and check that its label changed.

  5. From the documentation issue, use Create merge request. Bring the branch to your computer, make a change to the README with a commit that mentions the issue, and publish it.

  6. Check that the Merge Request description has Closes #number. Merge it and verify that the issue closed on its own and the milestone advanced.

  7. Create a wiki page called How we work with your branch naming convention and commit message convention.

  8. Challenge: create the folder .gitlab/issue_templates/ with a template Bug.md and use it to create a new issue.

Chapter 9. CI/CD: Learn to Read the Traffic Light

CI/CD is a set of automatic checks and tasks that GitLab runs every time you publish changes. Its result is a traffic light: green if everything passed, red if something failed. In this book we will not configure or create pipelines. The goal of this chapter is for you to understand what they are, know how to read their result, and know what to do when something turns red.

Important clarification. Configuring CI/CD is a full topic on its own and is usually done by someone with infrastructure experience. Here you will learn to recognize it and read it, which is what you need to work on a team that already uses it. You will not modify pipeline configuration files in any exercise.

What CI/CD means

They are two related ideas:

CI: continuous integration. Every time someone publishes changes, an automatic system checks that the project still works: that it can be built, that the tests pass, that the code follows the team's rules. The idea is to detect errors in minutes, not days later.

CD: continuous delivery or deployment. When changes pass the checks, the system automatically prepares a version ready to publish (continuous delivery) or even publishes it to the server (continuous deployment).

What it doesWho decides to publish
Continuous integrationChecks every change automaticallyNobody publishes yet
Continuous deliveryLeaves a version ready to publishA person presses the button
Continuous deploymentPublishes automaticallyNobody: if everything passes, it is published by itself

A comparison: quality control

Think of a bread factory. Before a tray leaves for the store, it goes through several stations: the dough is checked, it is baked, the temperature is measured, it is packed and labeled. If one station detects a problem, the tray does not move on.

A pipeline does the same with your code. Each station is an automatic check. If one fails, it stops and warns you. That way errors stay in the factory and don't reach the users.

What pipelines are for

A pipeline is the list of automatic tasks that run with your changes. The most common tasks:

  • Building the project, to check that nothing was left broken.

  • Running automatic tests, which verify that what worked still works.

  • Checking the style of the code, according to the team's rules.

  • Looking for security problems, such as passwords left in the code or libraries with known flaws.

  • Publishing to a test or production server.

The benefit for you: you don't have to remember to check everything by hand before each Merge Request. And the team has a minimum guarantee that what enters main works.

How a pipeline is built

A pipeline is organized into stages, and each stage has one or more jobs:

Stage: build   →   Stage: test              →   Stage: publish
  [compile]          [unit tests]                 [deploy to test]
                     [style check]

  • Stages run in order: if "test" fails, "publish" does not run.

  • The jobs of the same stage usually run at the same time.

The jobs are run by machines called runners. You don't need to know more about them for now: just that they are the "stations" where the work is done.

Where the configuration lives

All of this is defined in a file called .gitlab-ci.yml, at the root of the repository. If a project has that file, it has pipelines.

Just so you recognize it if you see it, a very simple example:

stages:
  - test

tests:
  stage: test
  script:
    - echo "Running tests"

You don't need to understand or modify it. If one of your Merge Requests changes that file by accident, let the person responsible know before merging.

Where to see the result

GitLab shows you the pipeline status in several places:

  1. In the Merge Request. Below the description there is a box with the pipeline status. It is where you will look at it most.

  2. In the commit list. Each commit shows a small icon with its status.

  3. In the Build > Pipelines menu. The complete list of all the project's pipelines, with date, branch, author and duration.

  4. On the project's main page, next to the last commit.

When you click a pipeline, you will see a diagram with its stages and jobs, each with its own status icon.

How to tell whether a pipeline passed or failed

Icon and statusMeaningWhat to do
Green, passedEverything passedYou can continue with the review and the merge
Red, failedAt least one job failedDon't merge. Check what failed
Blue, runningIt is runningWait
Gray, pending / createdWaiting for a free runnerWait. If it takes long, let someone know
Orange, warningA job marked as "allowed to fail" failedReview it, although it does not block
Crossed-out gray, canceledSomeone canceled itRun it again if needed
skippedIt did not run because an earlier stage failedFix the stage that failed
manual (gear or play icon)Waits for a person to start itOnly the person with that responsibility starts it

If the project is set up that way, GitLab won't let you merge a Merge Request with a red pipeline. It is a protection, not an obstacle.

What to do when a pipeline fails

A red pipeline is not a scolding: it is information. This is the process:

1. Identify which job failed. Open the pipeline and look for the job with the red X.

2. Read the log. Click the job to see its log: everything the machine wrote while working. The error is almost always at the end. Scroll to the last lines and look for words like Error, FAILED or failed, usually in red.

3. Relate it to your change. Ask yourself: what did I change that could have caused this? Often the message mentions a specific file or test.

4. Fix it on your branch. Make the fix, commit and push. The pipeline runs again automatically.

5. If it has nothing to do with your change, it may be a passing fault (for example, a network problem on the runner). You can retry the job with the Retry button. If it fails the same way again, it is not a passing fault.

6. If you don't understand the error, ask. Write in the Merge Request with the link to the failed job and mention the person responsible for the pipeline. Copying the last lines of the log into your message helps a lot.

What you should never do

  • Merge with the pipeline red "because it's surely nothing".

  • Delete or disable a test so the pipeline passes.

  • Modify .gitlab-ci.yml to skip a check.

  • Press Retry many times, hoping it passes by luck.

All these actions hide the problem instead of solving it, and the problem ends up reaching production.

What a green pipeline does and doesn't mean

A green pipeline means that the checks that exist passed. It does not mean the change is perfect. If the project has no tests for a certain part, an error there will not be detected by anyone.

That is why the pipeline does not replace the human review from chapter 5. They are complementary: the machine checks what is repetitive and measurable; people check the logic, the clarity and whether the change really solves what was requested.

On GitHub it is called… GitHub Actions. The configuration lives in the folder .github/workflows/. The traffic light works the same way: a green check or a red X next to each commit and in each Pull Request.

Real example: the red that saved a release

Luis opens a Merge Request that changes the date format in a report. A few minutes later, the pipeline turns red.

He opens the tests job and scrolls to the end of the log. He sees that a test called "monthly report shows correct totals" failed: the format change broke the way the report grouped months. Luis wouldn't have noticed by testing by hand, because he only checked the daily report screen.

He fixes it, pushes, and the pipeline turns green. Ana reviews the logic and approves. The error never reached the people who use the report.

Practical exercise

Your practice project has no pipelines, and in this book we won't configure them. To practice reading them, use a public project:

  1. Find an active open source project on GitLab.com and go to Build > Pipelines.

  2. Find one green pipeline and one red one. Note their branch, author and duration.

  3. Open the red pipeline and identify which stage and which job failed.

  4. Open the log of the failed job, scroll to the end and copy the line that explains the error. Try to describe in your own words what happened.

  5. Check whether the later stages ended up as skipped.

  6. Open a recent Merge Request of the project and find the pipeline box.

  7. Look for the .gitlab-ci.yml file at the root of the repository and count how many stages it has. Just look at it.

  8. Write a practice message (without publishing it) as if you were asking for help with a failed pipeline: which job failed, the link and the error lines.

  • I can explain what continuous integration is and what continuous delivery or deployment is.

  • I know what a pipeline, a stage and a job are.

  • I know that the configuration lives in .gitlab-ci.yml and that I must not modify it without the person responsible.

  • I find the pipeline status in the Merge Request, in the commits and in Build > Pipelines.

  • I recognize the statuses: passed, failed, running, pending, skipped, canceled and manual.

  • I know what to do when it fails: fix it, retry if it is a passing fault, or ask for help.

Chapter 10. Security and Good Practices

A repository stores much more than code: it stores the work of a whole team and, sometimes, the entry door to important systems. This chapter covers the five protections every team should have: well-granted permissions, protected branches, secrets kept out of the repository, secure accounts, and a review before merging or publishing.

Why security starts in Git

Three real situations that repeat in many organizations:

  • Someone accidentally uploads a file with the database password. The repository is internal, but dozens of people can see it, and any cloned copy keeps it.

  • A person who no longer works at the organization still has access to the project months later.

  • An unreviewed change is merged straight into main and published, with a bug that takes the service down for users.

None of them requires a sophisticated attack. All of them are avoided with basic configuration and good habits.

Roles and permissions

In GitLab, each person who takes part in a project has a role. The role decides what they can see and what they can do. They are managed in Manage > Members.

RoleWhat it can do, in shortFor whom
GuestSee the project (depending on its visibility) and create issuesUsers who report bugs
ReporterRead the code, comment, manage issuesAnalysts, managers who follow progress
DeveloperCreate branches, push, open Merge RequestsThe team that develops
MaintainerMerge on protected branches, configure the projectTechnical leads, project owners
OwnerFull control, including deleting the projectVery few people

The exact names and details may vary depending on your organization's GitLab version, which may even have an additional role. The idea is the same everywhere.

The principle of least privilege

Each person should have the minimum role they need for their work, and nothing more. Not because you distrust anyone, but because it reduces the possible damage from a mistake or a stolen account.

Good practices with permissions:

  • Don't give Maintainer "just in case". Start with Developer and raise the role when needed.

  • Use expiration dates for temporary access: consultants, interns, one-off support. GitLab lets you set a date on which access is removed automatically.

  • Review the member list periodically, for example every three months. Remove anyone who no longer participates.

  • Remove access the same day someone leaves the organization or the project.

  • Use groups when several projects share the same team. That way you manage permissions in one place.

  • Never share accounts. Each person uses their own. Otherwise the history loses its meaning: you don't know who did what.

Protected branches

A protected branch has special rules about who can change it and how. It is configured in Settings > Repository > Protected branches. In most projects, main comes protected by default.

What you can define:

OptionWhat it controlsRecommended setting for main
Allowed to mergeWho can merge Merge RequestsMaintainers
Allowed to push and mergeWho can push directlyNobody (No one)
Allowed to force pushWhether history can be rewrittenDisabled

With that setting, the only way to change main is with a Merge Request that someone with permission merges. It is exactly the flow from chapters 4 and 5, but now it is mandatory, not just good intention.

Other protections worth knowing:

  • Required approvals. Requiring one or more people to approve before merging. Depending on your organization's GitLab plan, it may be mandatory or just informative.

  • Successful pipeline to merge. In Settings > Merge requests, the option Pipelines must succeed prevents merging on red (chapter 9).

  • All threads resolved. The option All threads must be resolved prevents merging with pending comments.

  • Protected tags. Just like branches, you can protect version tags (v*) so that only certain people can create them (chapter 13).

If you try to push directly to a protected branch, you will see an error like You are not allowed to push code to protected branches. It is not a failure: it is the protection working. Create a branch and open a Merge Request.

Never store secrets in the repository

A secret is any piece of data that gives access to something:

  • Passwords for databases, servers or services.

  • API tokens and keys.

  • Private SSH keys or certificates.

  • Email or cloud service credentials.

  • Connection strings that include a username and password.

Why it is so serious

Remember that Git stores the whole history. If you upload a password and in the next commit you delete it, the password is still there, in the previous commit. Anyone who has a copy of the repository can find it with git log -S (chapter 12).

Also:

  • Every person who cloned the project has a copy of that history.

  • Forks have it too.

  • In public repositories there are automated programs that constantly search the internet for exposed secrets. A published key can be used by third parties in very little time.

How to keep them out

1. Use environment variables and an ignored .env file. Secrets go in a local file, for example .env, which never enters the repository:

# .env  (NOT uploaded)
DB_PASSWORD=the-real-password
API_TOKEN=the-real-token

And in .gitignore:

.env
*.pem
*.key

2. Upload a template without real values. Create a .env.example with the variable names and example values, so the team knows what to configure:

# .env.example  (YES, uploaded)
DB_PASSWORD=write-the-password-here
API_TOKEN=write-the-token-here

3. For pipelines, use GitLab variables. The secrets the CI/CD needs are stored in Settings > CI/CD > Variables, marked as Masked (hidden in logs) and Protected (only available on protected branches). Usually the person responsible for the pipelines configures them.

4. Review before every commit. Here the rule from chapter 3 returns: look before you save. A git status and a git diff --staged catch most accidents. Be wary of any file you didn't expect to see.

5. Turn on automatic detection if your team can. There are tools that check every commit for secrets before they enter: GitLab's secret detection analysis in pipelines, or programs that run on your computer before each commit (called pre-commit hooks). Ask whether your team uses one.

If you uploaded a secret: what to do, in this order

  1. Change or revoke the secret immediately. Change the password, revoke the token, generate a new key. This step is the only one that really protects you. Do it even if the repository is private, and even if you think nobody saw it.

  2. Notify the person responsible for security or your technical manager. No shame: it is a common accident, and reporting it quickly is the professional thing to do.

  3. Check whether the secret was used, with help from whoever manages that system (access logs, unusual activity).

  4. Remove the secret from the code with a new commit and move the value to .env or to GitLab variables.

  5. Cleaning up the history (deleting the secret from all old commits) is possible with specialized tools, but it rewrites the history of the whole team. Do it only with support from someone experienced, and remember that it does not replace step 1.

Protect your account

Your GitLab account is the key to every project you take part in:

  • Turn on two-step verification (2FA) in your profile, under Preferences > Account. If someone obtains your password, they still won't be able to get in.

  • Tokens with expiration and minimum permissions (chapter 2). Delete the ones you no longer use.

  • Put a passphrase on your SSH key and never share the private key.

  • Lock your computer when you step away. An open session is an open account.

  • Be wary of emails asking for your credentials, even if they look like they come from GitLab. Always log in by typing the address yourself.

What to check before merging

Whether you are merging your own Merge Request or someone else's:

  • The source branch and the target branch are the right ones.

  • The description explains what changes and why.

  • I reviewed all the files in the Changes tab.

  • There are no secrets, .env files, keys or personal data.

  • There are no files unrelated to the task, temporary or test files.

  • There are no forgotten <<<<<<< conflict markers.

  • The pipeline is green.

  • All comments are addressed and the threads resolved.

  • It has the required approvals.

  • It does not modify .gitlab-ci.yml or sensitive settings without the knowledge of the person responsible.

What to check before deploying

Publishing to production is the moment of greatest risk. Even if a designated person usually does it, it helps that the whole team knows the list:

  • Everything to be published is merged into the right branch and has a green pipeline.

  • There is a version tag and its notes (chapter 13).

  • It is known exactly which changes go in, by comparing with the previous version (chapter 12).

  • There is a plan to roll back if something fails: which version to restore and how.

  • If there are database changes, a recent backup exists.

  • A low-usage time was chosen and users are warned if there will be an interruption.

  • Someone is available to check that everything works after publishing.

  • Nothing is published on a Friday afternoon, except in emergencies. If something fails, nobody wants to fix it over the weekend.

Good practices for teamwork

Technical security is of little use if the team has no clear agreements. These practices summarize the book:

  1. Nobody works directly on main. Branches for everything.

  2. Short branches. Days, not weeks.

  3. Small commits, with clear messages. One commit, one idea.

  4. git pull when starting the day and before creating a branch.

  5. Every change goes through a Merge Request and review. Including urgent ones.

  6. Every task has its issue. Important conversations happen there, not in chat.

  7. Look before you save and before you merge.

  8. Comments about the code, not about the person.

  9. Conflicts: understand both sides. Never delete the other person's work.

  10. What is published is not rewritten. It is corrected with a new commit.

  11. Secrets never enter the repository. And if they do, they are changed immediately.

  12. Document your agreements in the wiki: conventions for branches, commits and labels, and who to ask.

This last one is key. A new team doesn't need to guess its rules if they are written down.

Real example: the password uploaded on a Monday

Luis is setting up the connection to the test database and, in a hurry, commits the config.py file with the password written in it. He pushes to his branch and opens a Merge Request.

Ana reviews the Changes tab and sees the password. She doesn't approve. She messages Luis privately and he acts in order: he asks the database administrator to change the password immediately, notifies the technical management, moves the configuration to environment variables with an ignored .env and a .env.example, and makes a new commit.

Since the branch only existed in the internal project and the password had already been changed, the team decides with management how to clean up that branch's history. The incident was resolved within an hour. The next day, the team adds automatic secret detection to its improvement list and the .env rule to the wiki.

  2. In Settings > Repository > Protected branches, configure main: merge only by Maintainers, direct push No one, force push disabled.

  4. In Settings > Merge requests, enable All threads must be resolved.

  5. Create a .env file with an invented value, for example TEST_KEY=12345. Check that your .gitignore excludes it with git status. If it appears, add .env to .gitignore.

  6. Create and upload a .env.example with the same variable and an example value.

  7. Turn on two-step verification in your GitLab account.

  8. Review your access tokens and delete the ones you don't use.

  9. Write a wiki page Team rules with your 12 good practices, adapted to your way of working.
