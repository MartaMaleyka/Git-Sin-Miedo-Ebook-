7-Day Action Plan

This plan turns the book into daily practice. Each day has a goal, concrete tasks, an approximate time and a small test to find out whether you got it. Spend between one and two hours a day. If a day doesn't fit, nothing happens: continue the next day from where you left off. What matters is not skipping steps.

Day 1: get everything ready and understand the why

Goal: have Git ready and understand what problem it solves.

Chapters: 0, 1 and 2. Time: 1 to 2 hours.

  • Read chapters 0 and 1.

  • Review a folder of yours full of manual versions (exercise from chapter 0).

  • Install Git and configure your name and email.

  • Create your GitLab account and set up SSH (or a token).

  • Create and clone your practice-git project.

Test of the day: explain to someone, in two minutes and without technical words, what Git is and what GitLab is.

Day 2: the basic cycle

Goal: save and publish changes, always looking first.

Chapter: 3. Time: 1 to 2 hours.

  • Make at least five small commits in practice-git, each one with git status and git diff before.

  • Create your .gitignore.

  • Practice git add -p on a file with two different changes.

  • Publish your commits and find them in GitLab.

  • Fix a message with git commit --amend before pushing.

Test of the day: write from memory, in order, the commands of the cycle: status, diff, add, commit, log, pull, push.

Day 3: branches and Merge Requests

Goal: work without touching main and ask for review.

Chapters: 4 and 5. Time: 2 hours.

  • Create two branches with the convention type/description.

  • Bring main into one of them with git merge main.

  • Open a Merge Request with the description template.

  • Comment on a line, use a suggestion and resolve the thread.

  • Merge, update main and delete the local branch.

Test of the day: without looking at the book, go through the full path of a new branch until it is merged.

Day 4: conflicts and mistakes

Goal: lose your fear of conflicts and of making mistakes.

Chapters: 6 and 7. Time: 2 hours.

  • Cause a conflict on purpose and resolve it by combining both changes.

  • Cancel a merge with git merge --abort.

  • Do the full first-aid exercise: restore, reset, stash, revert and reflog.

  • Write your personal first-aid sheet.

Test of the day: answer without looking: "I already pushed a commit with a mistake. Which command do I use, and why don't I use reset?".

Day 5: organization, pipelines and security

Goal: work like on a real team, with order and protections.

Chapters: 8, 9 and 10. Time: 2 hours.

  • Create labels, a milestone and three issues with templates.

  • Create a branch from an issue and close it with Closes #number.

  • Read a failed pipeline in a public project and explain the error.

  • Protect main in your project and check that you can't push to it directly.

  • Create .env and .env.example, and turn on two-step verification.

Test of the day: go through in GitLab the full chain of a task: issue, branch, commits, Merge Request and closed issue.

Day 6: extra tools and automation

Goal: investigate the history, mark versions and use an agent with control.

Chapters: 11, 12 and 13. Time: 2 hours.

  • Use git log -S and git blame to investigate a change.

  • Create a tag v0.1.0 and a release with notes.

  • Improve your README with Markdown.

  • Write the rules for your agent or prepare the publish.sh script.

  • Make a full change with the help of the agent or the script, and verify it manually in GitLab.

Test of the day: explain five things you would never let an agent do on its own.

Day 7: final project and agreements

Goal: do the whole flow from start to finish and write your rules down.

Chapter: 14. Time: 2 to 3 hours.

  • Complete the seven phases of the final project, preferably in pairs.

  • Fill in the final assessment table and review what ended up as "not yet".

  • Answer the reflection questions.

  • Write the page "Team rules" in the wiki, with your agreements on branches, commits, reviews and security.

Test of the day: the final project was merged, with the issue closed and no work lost.

After the 7 days: habits for every working day

What you learned is kept by using it. These habits turn the book into your way of working:

When you start the day

  • git switch main and git pull.

  • Review the board and choose your task.

  • Create the branch from the issue.

During the day

  • Small commits, looking first with git status and git diff.

  • Bring main into your branch if the work drags on.

  • Comment progress and questions on the issue.

When you finish the day

  • Push your branch, even if the work isn't finished: that way it is backed up.

  • Open the Merge Request as a draft if you need an early opinion.

  • Leave your folder clean: nothing half-done without a commit or a named stash.

Every week

  • Review your open Merge Requests and the ones you have to review.

  • Delete local branches already merged and run git fetch --prune.

  • Learn one new GitLab command or feature and try it in practice-git.

If at any point you feel lost, go back to the command sheet that comes next. And remember the promise from the beginning: almost everything in Git can be undone.

Appendix. Funny, Curious and Rarely Used Commands

You already know the essentials. This appendix is the drawer of surprises: commands almost nobody teaches, some funny, some curious and some rarely used but very powerful on the day you need them. You don't have to memorize them. Read them, try them in practice-git, and keep the ones that make your life easier.

The ones marked with ⚠ are for when you already feel confident with the whole book.

To start with a laugh: curious facts about Git

The name. Linus Torvalds joked that he names his projects after himself, first Linux and then Git. In British slang, git is an unpleasant way to call someone. Git's original README played with that: depending on the mood of the day, the name could mean "global information tracker" or something much less polite.

The official description. If you type man git on Mac or Linux, the first line describes Git as "the stupid content tracker". Stupid because it does something very simple (saving snapshots of the project), but does it very well.

The first commit in Git's history was made by Torvalds in April 2005, and its message called Git "the information manager from hell". Within a few days, Git was already being used to store its own code.

Those strange codes like a3f9c21 are the short version of a 40-character identifier, calculated from the content of the commit. That is why two different commits never have the same code, and why changing an old commit changes its identity.

Commands that bring a smile

Git corrects your spelling

Do you type git stauts instead of git status more times than you would admit? Turn on autocorrection:

git config --global help.autocorrect 20

Now, if you make a mistake, Git tells you what you meant, waits 2 seconds (the number is in tenths of a second) and runs the correct command. It gives you time to cancel with Ctrl + C if that wasn't what you wanted.

Git knows what time it is for tea

Git understands dates in almost human language, in English. Try:

git log --oneline --since="yesterday"
git log --oneline --since="noon"
git log --oneline --since="midnight"
git log --oneline --since="tea"

Yes: tea is teatime, 5:00 p.m. Git takes British customs seriously. It also understands things like "2 weeks ago" or "last monday".

The empty commit

git commit --allow-empty -m "Empty commit to run the pipeline again"

A commit with no changes. It seems useless, but it has real uses: triggering a pipeline again without touching files, or marking a moment ("Start of sprint 24"). It is also the easiest commit to review in the world.

The team ranking

git shortlog -sn HEAD

It shows how many commits each person made, from highest to lowest. Fun for the end-of-year meeting, but don't use it to measure anyone: a one-line commit and a full day's commit count the same.

Back to the previous branch, like a remote control

git switch -

The dash takes you to the last branch you were on. Use it twice and you go back. It is Git's "previous channel" button.

Shortcuts that save you time: aliases

An alias is a nickname for a long command. You create them once and use them forever. And yes, they can be in Spanish:

git config --global alias.st "status"
git config --global alias.mapa "log --oneline --graph --all"
git config --global alias.ups "commit --amend --no-edit"
git config --global alias.deshacer "reset --soft HEAD~1"
git config --global alias.ramas "branch --sort=-committerdate"
git config --global alias.quien "shortlog -sn HEAD"

Now you can type:

You typeEquivalent toWhat for
git stgit statusSee the state in two letters
git mapagit log --oneline --graph --allSee all the branches drawn
git upsgit commit --amend --no-edit"Oops, I forgot a file" (only before push)
git deshacergit reset --soft HEAD~1Undo the last commit without losing anything
git ramasgit branch --sort=-committerdateSee your branches, most recent first
git quiengit shortlog -sn HEADThe team ranking

To see all your aliases:

git config --global --get-regexp alias

A tip: learn the full commands first. Aliases are a reward, not a replacement. If one day you use someone else's computer, your aliases won't be there.

Curious ones to investigate

The history of a single function

git log -L :calculate_total:reports.py

It shows all the commits that changed the function calculate_total inside reports.py, with the exact change each time. It is like a biography of the function. It works in the languages Git knows how to recognize; otherwise you can give line numbers: git log -L 10,30:file.

When was this file born?

git log --oneline --diff-filter=A -- contacts.md

--diff-filter=A filters only the commits that added the file. That way you find its "birth certificate".

The first commit of the project

git log --oneline --reverse | head -1

--reverse shows the history backward, from the oldest to the newest. On Windows without Git Bash, head may not be available: use Git Bash.

How many commits does the project have?

git rev-list --count HEAD

A single number. Ideal for saying "this project has 1,284 commits" in a presentation.

See changes word by word

git diff --word-diff
git diff --color-words

Instead of marking the whole line as changed, they highlight only the words that changed. Perfect for texts, documentation and Markdown files, where one line can be a whole paragraph.

Your own history format

git log --pretty=format:"%h · %an · %ar · %s"
a3f9c21 · Ana Pérez · 2 hours ago · Fix contact phone number

%h is the short code, %an the author, %ar the relative date ("2 hours ago") and %s the message. Combine it with an alias and you have your history tailored to you.

Search text across the whole project

git grep -n "500-0000"

It searches all the files Git tracks and tells you the file and the line number. Faster than the system search, and it doesn't get lost in folders you ignore.

How much does the repository weigh?

git count-objects -vH

The size-pack line tells you how much space the stored history takes. Useful when someone asks why the project takes so long to clone.

Rarely used, but life-saving

Bring a single commit from another branch: cherry-pick

Someone fixed a bug on their branch, but their branch hasn't been merged yet and you need that fix right now:

git cherry-pick commit-code

It copies that single commit to your current branch, like picking a single cherry from the tree. Use it sparingly: if you do it a lot, the same change ends up repeated across several branches.

Two branches open at once: worktree

You are halfway through something and you are asked to review another branch. Instead of a stash, open the other branch in another folder:

git worktree add ../urgent-review fix/phone

Now you have the folder urgent-review with that branch, and your original folder stays intact. When you are done:

git worktree list
git worktree remove ../urgent-review

It is one of the least known and most useful commands. It is also very handy if you work with AI agents: each one can have its own folder without stepping on the others.

Find the guilty commit automatically: bisect ⚠

In chapter 12 you saw the idea of splitting history in half. git bisect does it for you. And you can give it your own words:

git bisect start --term-old=worked --term-new=broken
git bisect broken                    # The current commit is broken
git bisect worked v1.0.0             # In v1.0.0 it worked

Git takes you to a commit in the middle. You test and tell it git bisect broken or git bisect worked. Repeat a few times and Git will tell you exactly which commit broke it. When you finish:

git bisect reset

If you have a script that tests automatically, Git can do everything alone with git bisect run ./test.sh.

Make Git remember how you resolved a conflict: rerere ⚠

The name is almost a tongue twister: reuse recorded resolution.

git config --global rerere.enabled true

From that moment on, when you resolve a conflict, Git remembers it. If the same conflict comes back (it happens when you bring main into a long branch several times), Git resolves it the same way you did the first time. Always check the result before committing.

Notes attached to a commit

git notes add -m "This change was tested with September data" a3f9c21
git log --oneline --notes

It adds a note to a commit without modifying it, like a sticky note. A curious detail: notes don't travel with a normal push, so almost nobody sees them. They are more useful for you than for the team.

Export the project without its history

git archive --format=zip -o project.zip HEAD

It creates a .zip with the project's files as they are in the latest commit, without the .git folder and without ignored files. Perfect for handing a clean copy to someone who doesn't use Git.

Clone only the latest

git clone --depth 1 address

It downloads only the latest commit, without the whole history. Much faster for enormous projects. In exchange, you can't investigate the history until you bring in the rest with git fetch --unshallow.

A branch with no past ⚠

git switch --orphan new-page

It creates a branch with no previous commits, as if it were another project inside the same repository. It is used, for example, to keep a documentation website separate from the code. When you create it, it removes from that branch the files you don't need before the first commit.

A more polite force push ⚠

If you really need to force a push on your own branch (for example, after a rebase), use this version:

git push --force-with-lease

Unlike --force, it refuses to overwrite if someone else published something to that branch that you don't have. It is a force push that knocks on the door first. Even so: never on shared branches.

Search for lost commits in limbo ⚠

git fsck --lost-found

When not even the reflog helps, this command looks for "orphaned" commits that no branch or record remembers. It is the last resort of the first-aid kit, before giving up.

The hidden help

git help -g
git help everyday

The first lists the guides that Git has installed. The second is an official guide with the minimum commands for everyday use, by role. They are in English, but surprisingly good.

Challenges for the appendix

To close with fun, in your practice-git project:

  1. Turn on autocorrection and deliberately type git stauts. What happened?

  2. Create three aliases in English that really help you and use them for a week.

  3. Find all the commits you made "since teatime" yesterday: git log --since="yesterday tea".

  4. Find the "birth certificate" of your README.md and count how many commits your project has.

  5. Use git worktree to open another branch in a separate folder, make a change there and then delete that folder with git worktree remove.

  6. Copy one commit from one branch to another with git cherry-pick and look at it with git mapa (your alias).

  7. Advanced challenge: cause a bug on purpose a few commits back and find it with git bisect, using the words worked and broken.
