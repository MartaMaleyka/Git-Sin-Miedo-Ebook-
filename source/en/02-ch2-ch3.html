Chapter 2. Set Up Your Computer

By the end of this chapter you will have Git installed, your identity configured, a secure connection to GitLab, and your first project downloaded. It is the most "technical" chapter in the book, but you only do it once. Go step by step and don't skip anything.

Step 1: open the terminal

The terminal is a window where you type orders and the computer carries them out. It looks like something from a hacker movie, but it is just another way of using your computer.

SystemHow to open it
WindowsAfter installing Git (step 2), search for Git Bash in the Start menu. Use that one.
MacPress Cmd + Space, type Terminal and press Enter.
LinuxSearch for Terminal in your applications, or press Ctrl + Alt + T.

Three rules so you don't get scared:

  • You type the order and press Enter to run it.

  • If no message appears, it almost always means everything went well.

  • If you make a typing mistake, nothing happens: you get an error and you try again.

Step 2: install Git

On Windows. Go to git-scm.com, download Git for Windows and install it. You can accept the options that come selected by default. This also installs Git Bash, the terminal we will use.

On Mac. Open Terminal and type:

git --version

If Git is not installed, the Mac will offer to install the "command line tools". Accept and wait until it finishes. If you use Homebrew, you can also install it with brew install git.

On Linux (Ubuntu or Debian). Type:

sudo apt update
sudo apt install git

Check that it worked. On any system, type:

git --version

If you see something like git version 2.x.x, Git is ready. The exact number doesn't matter.

Step 3: tell Git who you are

Every commit you make will carry your name and your email. That way the team knows who made each change. This is configured only once:

git config --global user.name "Your Name Surname"
git config --global user.email "your-email@example.com"

Use the same email you use on GitLab. That way GitLab recognizes your commits and links them to your profile.

I recommend two more settings:

git config --global init.defaultBranch main
git config --global core.editor "nano"

The first makes the main branch of your new projects be called main, which is the name used today. The second chooses a simple editor for when Git asks you to write something. If you use VS Code or Cursor, you can replace nano with code --wait or cursor --wait.

To review what you configured:

git config --global --list

What does --global mean? It means the setting applies to all your projects on this computer. If you need a different email in a specific project (for example, your work one), go into that folder and repeat the command without --global.

Step 4: connect your computer to GitLab

To send and bring in changes, GitLab needs to know that it is you. There are two ways to do it: HTTPS and SSH.

HTTPSSSH
How it worksUsername + a token (a special key)A pair of keys stored on your computer
Difficulty at the startEasierA few more steps
Day to dayIt may ask you for the token againIt doesn't ask you for anything else
When to use itNetworks that block SSH, or to start quicklyIf you work every day: it is the recommended option

Option A: HTTPS with a token

A personal access token is like a special password you create only for Git. You can give it an expiration date and delete it whenever you want, without changing your real password.

  1. In GitLab, click your profile picture and go to Preferences (or Edit profile).

  2. Look for Access tokens.

  3. Create a new token. Give it a name like "My laptop", an expiration date, and check the permissions read_repository and write_repository.

  4. Copy the token right then. GitLab will not show it to you again.

  5. When Git asks for a password when cloning or pushing, paste the token instead of your password.

Store the token the way you store a password. Never paste it into a project file or into a chat.

Option B: SSH with keys (recommended)

SSH works with a pair of keys: a public one and a private one. Think of a padlock and its key. You give the padlock (the public key) to GitLab. The private key stays on your computer and you never share it. When you connect, GitLab checks that your key opens its padlock.

1. Create your keys:

ssh-keygen -t ed25519 -C "your-email@example.com"

It will ask you a few questions. Press Enter to accept the default location. Then it will ask for a passphrase: it is optional, but recommended.

2. Copy your public key (the one that ends in .pub):

cat ~/.ssh/id_ed25519.pub

You will see a long line that starts with ssh-ed25519. Copy it in full.

3. Add it in GitLab: profile picture > Preferences > SSH Keys > Add new key. Paste the key, give it a title like "My laptop" and save.

4. Check the connection:

ssh -T git@gitlab.com

The first time it will ask whether you trust the server. Type yes. If you see a welcome message with your username, you are connected. If your organization has its own GitLab, replace gitlab.com with that server's address.

Golden rule: the file that ends in .pub can be shared. The one that does not end in .pub is your private key and never leaves your computer. Not by email, not by chat, not inside a repository.

Step 5: clone your first repository

Cloning means downloading a project from GitLab to your computer, with its whole history. You do it once per project.

  1. In GitLab, open the project.

  2. Click the blue Code button (or Clone).

  3. Copy the address under Clone with SSH (or the HTTPS one if you chose that option).

  4. In the terminal, go to the folder where you keep your projects and clone:

cd Documents
git clone git@gitlab.com:your-username/practice-git.git

  1. Enter the project folder:

cd practice-git

Done: you have the project on your computer. From now on, all Git commands run inside that folder.

What does cd do? It means "change directory": it is like double-clicking a folder. cd .. takes you back to the previous folder. And ls (or dir on Windows without Git Bash) shows you what is in the current folder.

Clone or start from scratch: git clone vs git init

There are two ways to have a repository on your computer:

git clonegit init
What it doesDownloads a project that already exists on GitLabTurns one of your folders into a new repository
Brings historyYes, all of itNo, it starts empty
Already connected to GitLabYesNo, you have to connect it
When to use itAlmost always, when joining a projectWhen you start something from your computer

If you already have a folder with files and want to bring it to GitLab:

cd my-folder
git init
git add README.md
git commit -m "First commit of the project"
git remote add origin git@gitlab.com:your-username/my-folder.git
git push -u origin main

Before the last step, create an empty project in GitLab (without a README) with that same name. origin is the nickname Git gives to the copy on GitLab. The -u is only used the first time: it tells Git that from now on, git push should always go to that place.

To see which remote a project is connected to:

git remote -v

Git inside your editor

If you use VS Code or Cursor, open the project folder (File > Open Folder). You will see:

  • A branch icon in the side bar: it is the source control panel. Modified files appear there.

  • When you click a modified file, a side-by-side view opens with what changed.

  • At the bottom left, the name of the branch you are on.

  • A built-in terminal (Terminal > New Terminal) that already opens inside the project folder. Very handy: you don't have to navigate with cd.

I recommend using the built-in terminal for the commands in this book and the visual panel to review changes. It is the best combination of both worlds.

If you use a work account and a personal one

This is very common: GitLab with your company email and GitHub with your personal email. So that each commit comes out with the right email:

  1. Keep the email you use most as the global setting (step 3).

  2. In each project that uses the other email, go into its folder and type:

git config user.email "other-email@example.com"

Without --global, the change only applies to that project. Check with git config user.email inside the folder.

For SSH you can use the same public key on GitLab and on GitHub. Just add it to both accounts.

A detail for Windows. Windows and Mac/Linux mark the end of each line of text differently. If you work in a mixed team, Git can show files as modified even though you didn't change anything. To avoid it, on Windows run this once:

git config --global core.autocrlf true

And on Mac or Linux:

git config --global core.autocrlf input

Real example: the most common mistake in this chapter

You make your first commits and in GitLab they appear with a strange name, or without your profile picture. Almost always it is because the email configured in Git does not match the email on your GitLab account.

Check it like this:

git config user.email

If it is not the right one, change it with the command from step 3. New commits will come out right. The old ones stay as they are, and that's fine.

Practical exercise

You will use this practice project throughout the book.

  1. Install Git and check the version with git --version.

  2. Configure your name and email, and review them with git config --global --list.

  3. Set up SSH (or create a token if you prefer HTTPS) and test the connection.

  4. In GitLab, create a new blank project called practice-git. Check the option Initialize repository with a README.

  5. Clone it to your computer.

  6. Enter the folder with cd practice-git and type ls. You should see the README.md file.

Chapter 3. Your First Cycle: Look Before You Save

Daily work with Git is a six-step cycle: review, choose, save, view the history, bring in, and publish. The most important rule of this chapter is simple: look before you save. If you learn it now, you will save yourself many headaches.

My story: saving everything without looking

When I learned Git on my own, with tutorials, I got stuck on a shortcut: saving everything at once. I changed things, typed the command to include everything, made the commit, and that was it. Fast and convenient.

The problem showed up later. When I reviewed the history, I found commits that mixed things that had nothing to do with each other. There were changes I didn't want to save yet and files that should never have entered the project. And when I wanted to undo just one thing, I couldn't, because it was tangled up with everything else.

From that I took the rule I repeat in every chapter: before saving, look at what you are saving. It takes ten seconds and saves you hours.

Git's three areas

To understand the cycle, imagine you are preparing a mail shipment:

  1. The work table (in Git: working directory). It is your folder, where you edit files. Everything is messy here, and that's fine.

  2. The open box (in Git: staging area). Here you put only what you want to send in this package. You can take things out and put them back in before you close it.

  3. The sealed, labeled package (in Git: commit). You closed the box and put a label on it saying what it contains. It is saved in your history.

And there is a fourth place: the post office, which is GitLab. The package doesn't get there until you send it with push.

The open box exists precisely so that you can choose what to save. Skipping that step is what used to happen to me.

Step 1: git status, what is going on?

It is the command you will use most. It tells you the state of each file. Use it before and after every step, without fear: it only looks, it doesn't change anything.

git status

A typical answer:

On branch main
Changes not staged for commit:
        modified:   README.md

Untracked files:
        personal-notes.txt

Translated:

  • On branch main: you are on the main branch.

  • Changes not staged: you modified README.md, but it is not in the box yet.

  • Untracked files: personal-notes.txt is a new file that Git is not tracking yet.

Step 2: git diff, what exactly did I change?

git diff

It shows you, line by line, what you changed and is not in the box yet. Lines with - were removed and lines with + were added:

- Hours: Monday to Friday, 8:00 to 4:00
+ Hours: Monday to Friday, 8:00 to 5:00

This is where you discover the change you didn't want, the extra space, or the test text you forgot to delete. To leave this view, press the q key.

Step 3: git add, choose what goes in the box

Add the files by name:

git add README.md

Look again with git status. Now you will see README.md in a new section, Changes to be committed: it is already in the box. And personal-notes.txt stays out, as you wanted.

If you want to review what is already in the box before closing it:

git diff --staged

About git add . This command puts everything that changed in the folder into the box. It is not forbidden, but use it only after looking at git status and being sure that everything that appears should go in. That was my mistake: using it without looking.

Did you put something in the box by mistake? Take it out without losing the change:

git restore --staged personal-notes.txt

Step 4: git commit, close and label the package

git commit -m "Update opening hours to 5:00 p.m."

The text in quotes is the commit message. It is the note your teammates will read, and you yourself will read six months from now.

How to write clear commits

A good message answers the question: what does this change do?

Confusing messageClear message
changesFix contact phone number on the home page
misc fixesFix error when saving a form without a date
works now!!!Validate that the email has the correct format
updateUpdate installation instructions in the README

Five simple rules:

  1. Start with a verb: Add, Fix, Update, Remove, Improve.

  2. Be specific: say what you changed and where.

  3. Keep it short: one line of under 70 characters.

  4. One commit, one idea. If your message needs the word "and" for two different things, they should probably be two commits.

  5. If the reason is not obvious, explain the why. Use git commit without -m so the editor opens, and write a summary line, a blank line, and then the details.

Step 5: git log, view the history

git log --oneline

It shows one commit per line, from newest to oldest:

a3f9c21 Update opening hours to 5:00 p.m.
7b2e104 Add contact section
1c8d3aa Initial commit

That code at the start (a3f9c21) is the unique identifier of each commit. You will use it later to go back or review changes. Without --oneline you will also see the author and the date. Press q to exit.

Step 6: git pull and git push, bring in and publish

Before publishing, always bring in what is new from the team:

git pull

This downloads the changes others published and combines them with yours. If nobody changed anything, it will tell you Already up to date.

Now yes, publish:

git push

Your commits travel to GitLab. Open the project in the browser and you will see your message in the list of commits.

Why pull before push? If someone published something after your last pull, GitLab will reject your push with an error message. It is not serious: run git pull and try again. But it is cleaner to do it beforehand.

.gitignore: what must never enter

There are files that should never be saved in the repository: files with passwords or keys, folders that are generated automatically, system temporary files, or your personal notes.

That is what .gitignore is for: a text file at the root of the project with the list of things Git must ignore. Example:

# Configuration with sensitive data
.env

# System files
.DS_Store
Thumbs.db

# Personal notes
personal-notes.txt

# Folders generated automatically
node_modules/
__pycache__/

Anything listed in .gitignore stops appearing in git status. That way you can't add it by accident, not even with git add ..

Careful: .gitignore only works with files that have not yet been saved. If a file already entered a commit, adding it to .gitignore later does not remove it from the history. That is why it is best to create it at the start of the project. And if you ever push a password, change it immediately: we cover this in chapter 10.

Cycle summary

git status                 # 1. What changed?
git diff                   # 2. What exactly did I change?
git add file               # 3. I choose what goes in
git diff --staged          #    I review the box
git commit -m "Message"    # 4. I save with a good message
git log --oneline          # 5. I look at the history
git pull                   # 6. I bring in what is new
git push                   #    I publish

Choosing parts of a file: git add -p

Sometimes you changed two different things in the same file: a correction and a test. With git add file both would go in. To choose piece by piece:

git add -p README.md

Git shows you each block of changes and asks what to do. The answers you will use most:

  • y (yes): this block goes into the box.

  • n (no): this block stays out.

  • q (quit): ends without reviewing the rest.

  • ? (help): shows all the options.

It is the perfect tool to follow the "one commit, one idea" rule. In VS Code and Cursor you can do the same with the mouse: select lines in the changes view and choose Stage Selected Ranges.

Viewing a commit in detail: git show

git show a3f9c21

It shows the author, the date, the message, and exactly which lines that commit changed. If you don't give a code, it shows the last commit. It is useful to answer "what did I do yesterday?" or "what did Ana change in that commit?".

Other uses of git log that will help you:

git log --oneline -5              # Only the last 5 commits
git log --oneline --author="Ana"  # Only Ana's commits
git log --oneline -- README.md    # Only the commits that touched that file

I made a mistake in the last commit (and I haven't pushed)

If you wrote the message wrong or forgot to add a file, you can fix the last commit:

git add forgotten-file.txt
git commit --amend -m "Corrected message"

Warning: use --amend only if you have not pushed yet. If you already published the commit, correcting it this way changes the history your teammates already downloaded and causes them problems. In that case, make a new commit with the correction.

How often should I commit?

There is no magic number, but these signals help:

  • Commit when you finish a complete idea, even a small one: you fixed a mistake, added a section, changed a text.

  • Commit before something risky, like reorganizing folders. If it goes wrong, you return to that point.

  • Don't wait for days. If you have gone a week without a commit, you have too many mixed changes and they will be hard to explain or undo.

  • Don't commit something broken to the main branch. If you need to save something half-finished, do it on your own branch (chapter 4).

A good test: if you can describe the change in one clear line, it is a good time to commit.

The same cycle from VS Code or Cursor

Everything in this chapter can also be done with buttons:

  1. Open the source control panel. That is your git status: the list of changed files.

  2. Click a file to see its git diff side by side.

  3. Press the + next to the file to put it in the box (git add).

  4. Write the message at the top and press Commit.

  5. Press Sync Changes or the arrow buttons to pull and push.

Be careful with the commit button when nothing is in the box: some editors offer to save all changes at once. It is the equivalent of git add . without looking. Read the message before accepting.

Real example: a clean commit versus a tangled one

Luis fixes a bug in the contact form. Meanwhile, he also changes some colors to test and leaves a test file in the folder.

Tangled commit. Luis uses git add . and writes git commit -m "fixes". Everything goes in together: the correction, the test colors and the junk file. Two weeks later, the team wants to undo the colors. They can't do it without also undoing the correction.

Clean commit. Luis looks at git status and git diff. He sees the three changes. He adds only the form file and runs git commit -m "Fix email validation in the contact form". He discards the test colors and adds the test file to .gitignore. The history is clear and each change can be undone separately.

Practical exercise

Use your practice-git project.

  1. Open README.md and add a line with your name and today's date.

  2. Create a new file called personal-notes.txt with any text.

  3. Run git status and explain in your own words what you see.

  4. Run git diff and find your new line with the +.

  5. Create a .gitignore file and write personal-notes.txt inside it. Run git status again: your notes should no longer appear.

  6. Add README.md and .gitignore by name. Review the box with git diff --staged.

  7. Make a commit with a clear message, for example: Add my name to the README and ignore personal notes.

  8. Run git log --oneline, then git pull and git push.

  9. Open GitLab in the browser and find your commit in the history.
