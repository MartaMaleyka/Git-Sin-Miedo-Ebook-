Nada de esto pasa porque la gente sea descuidada. Pasa porque nadie les explicó Git con calma, con ejemplos reales y sin palabras raras. Eso es lo que intento hacer aquí.

Capítulo 0. El caos antes de Git

Guardar versiones a mano funciona cuando trabajas sola y con pocos archivos. En cuanto entra otra persona, o el proyecto crece, se vuelve un desorden imposible de controlar. Este capítulo te muestra por qué, y qué problema viene a resolver Git.

La carpeta que todos hemos tenido

Seguro reconoces algo así:

Informe/
├── informe.docx
├── informe_v2.docx
├── informe_v2_revisado.docx
├── informe_final.docx
├── informe_final_AHORA_SI.docx
└── informe_final_v3_DEFINITIVO_Carlos.docx

Ahora respóndete con honestidad:

  • ¿Cuál es la versión buena?

  • ¿Qué cambió entre informe_v2 e informe_final?

  • ¿Quién hizo cada cambio, y por qué?

  • Si Carlos y tú editaron al mismo tiempo, ¿cómo juntas lo de los dos?

Nadie lo sabe con certeza. Y eso que es un solo documento. Imagina un sistema con cientos de archivos y cinco personas trabajando a la vez.

Los cuatro problemas de guardar a mano

1. No sabes qué cambió. Tienes dos archivos casi iguales y tendrías que leerlos línea por línea para encontrar la diferencia.

2. No sabes quién ni por qué. Aunque encuentres el cambio, no hay ninguna nota que diga quién lo hizo ni qué buscaba resolver.

3. No puedes volver atrás con seguridad. Si algo se rompe, ¿a cuál copia regresas? ¿Y qué pierdes al hacerlo?

4. Trabajar en equipo es una lotería. Dos personas editan el mismo archivo, se lo mandan por correo o por chat, y uno termina sobrescribiendo lo del otro sin darse cuenta.

Qué es el control de versiones

El control de versiones es un sistema que guarda la historia completa de tu proyecto por ti. Piensa en él como un cuaderno de bitácora automático.

Cada vez que terminas un avance, le dices al sistema: "guarda este momento". Y el sistema anota:

  • Qué cambió, exactamente, línea por línea.

  • Quién lo cambió.

  • Cuándo lo cambió.

  • Por qué, con un mensaje corto que escribes tú.

En vez de tener seis copias del informe, tienes un solo archivo con toda su historia guardada detrás. Puedes ver cualquier versión pasada cuando quieras, sin llenar la carpeta de copias.

Una comparación que ayuda: los puntos de guardado

Si has jugado videojuegos, conoces los puntos de guardado. Antes de enfrentar al jefe final, guardas la partida. Si pierdes, vuelves a ese punto sin empezar desde cero.

Git funciona igual. Cada "guardado" es una foto de tu proyecto en ese momento. Si algo sale mal, regresas a la foto anterior. La diferencia es que en Git cada foto lleva una nota explicando qué hiciste.

Y el trabajo en equipo

La parte más poderosa no es guardar tu historia. Es que varias personas pueden trabajar sobre el mismo proyecto al mismo tiempo sin pisarse.

Cada persona trabaja en su propia copia. Cuando termina, el sistema ayuda a juntar los cambios. Si dos personas tocaron la misma línea, el sistema no decide solo: te avisa y te pide que elijas. Eso se llama un conflicto, y le dedicamos el capítulo 6 completo.

No es solo para programadores

Git nació para el código, pero sirve para cualquier trabajo hecho con archivos de texto:

  • Documentación técnica y manuales.

  • Sitios web.

  • Archivos de configuración de servidores.

  • Libros y documentos escritos en formato de texto.

  • Scripts de análisis de datos.

Si trabajas en tecnología, en cualquier rol, tarde o temprano vas a tocar un repositorio. Mejor que sea sin miedo.

Un poco de historia: de dónde salió Git

Git lo creó Linus Torvalds en 2005, la misma persona que creó Linux. Miles de personas en todo el mundo trabajaban en el código de Linux y necesitaban una herramienta rápida para juntar sus cambios sin depender de un servidor central. Como la que usaban dejó de estar disponible para ellos, Torvalds escribió la suya en pocas semanas.

Hoy Git es el estándar. Lo usan desde estudiantes con su primer proyecto hasta bancos, gobiernos y las empresas de tecnología más grandes del mundo. Aprenderlo no es aprender una herramienta de moda: es aprender el idioma común del trabajo en tecnología.

Centralizado o distribuido: por qué importa

Antes de Git existían otros sistemas de control de versiones. Muchos eran centralizados: la historia vivía en un solo servidor. Si el servidor se caía, nadie podía guardar nada. Y si se dañaba sin copia, se perdía todo.

Git es distribuido: cada persona que descarga el proyecto tiene una copia completa de toda la historia. Eso tiene tres ventajas muy prácticas:

  1. Puedes trabajar sin internet. Guardas tus avances en tu computadora y los compartes cuando vuelves a conectarte.

  2. Es rápido. Ver la historia o comparar versiones no depende de la red.

  3. Hay muchas copias. Si el servidor tiene un problema, cualquier copia de un miembro del equipo puede ayudar a recuperar el proyecto.

Lo que Git no es

Para no llevarte sorpresas, aclaremos algunas confusiones comunes:

  • Git no es una copia de seguridad automática. Solo guarda lo que tú le dices que guarde, y solo comparte lo que tú publicas. Si nunca haces push, tu trabajo vive solo en tu computadora.

  • Git no es Google Drive ni Dropbox. Esos programas sincronizan tus archivos solos, a cada momento. Git guarda momentos que tú eliges, con una explicación. Es más trabajo, pero te da control total.

  • Git no es ideal para archivos pesados como videos o bases de datos. Funciona de maravilla con archivos de texto. Con archivos grandes o binarios (Word, Excel, imágenes) puede guardarlos, pero no te mostrará qué cambió por dentro.

  • Git no decide por ti. Si dos personas cambian lo mismo, no elige una versión al azar: te pregunta. Eso es una ventaja, aunque al principio asuste.

Mitos que frenan a la gente

"Git es solo para programadores expertos." Falso. Lo básico se aprende en una tarde. Lo avanzado lo aprendes cuando lo necesitas.

"Si uso Git, puedo romper el proyecto de todos." Muy difícil, si sigues las prácticas de este libro. Trabajarás en tu propia copia y en tu propia rama, y los cambios se revisan antes de entrar a la versión principal.

"La terminal es peligrosa." La mayoría de los comandos que usarás solo miran o guardan. Los pocos que pueden borrar algo los marcaré con una advertencia.

"Si me equivoco, pierdo todo." Al contrario. Git guarda tanta historia que casi todo se puede recuperar. Es más difícil perder trabajo con Git que sin él.

Lo que cuesta no tener control de versiones

En equipos e instituciones donde no se usa control de versiones, se repiten las mismas escenas:

  • Un sistema deja de funcionar después de un cambio y nadie sabe qué se tocó.

  • La única persona que sabía dónde estaba la versión buena se fue de vacaciones, o renunció.

  • Se publica en producción una versión vieja porque alguien subió la copia equivocada.

  • Para auditar quién hizo un cambio, hay que revisar correos y mensajes de chat de hace meses.

Nada de eso es culpa de las personas. Es falta de herramienta y de proceso. Git más una plataforma como GitLab resuelven las dos cosas.

Ejemplo real: el mismo problema, con y sin Git

Sin Git. Ana y Luis mantienen la página web de su oficina. Ana cambia el horario de atención. Luis, al mismo tiempo, corrige el teléfono. Luis sube su versión al servidor después que Ana. Resultado: el teléfono quedó bien, pero el horario volvió a ser el viejo. Nadie se da cuenta hasta que un usuario llega a una oficina cerrada.

Con Git. Ana guarda su cambio con el mensaje "Actualiza horario de atención". Luis guarda el suyo: "Corrige teléfono de contacto". Cuando Luis intenta publicar, Git le avisa que hay cambios nuevos de Ana. Luis los trae primero, Git junta los dos cambios porque tocan partes distintas, y se publica todo junto. Además, cualquiera puede ver después quién cambió el horario y cuándo.

Capítulo 1. Git, GitLab y GitHub sin enredos

Git es la herramienta que guarda la historia de tu proyecto en tu computadora. GitLab y GitHub son sitios web donde guardas una copia de ese proyecto para compartirla con tu equipo. Confundirlos es el error número uno al empezar, así que vamos a separarlos bien.

Una comparación: el cuaderno y la biblioteca

Imagina que Git es tu cuaderno. En él anotas cada avance de tu trabajo, con fecha y explicación. El cuaderno es tuyo, vive en tu computadora y funciona aunque no tengas internet.

GitLab y GitHub son la biblioteca. Es un lugar compartido donde dejas una copia de tu cuaderno para que tu equipo la vea, la copie y le agregue cosas. La biblioteca además tiene salas de reunión, tablones de anuncios y personas que revisan lo que entra.

Las palabras que vas a escuchar todo el tiempo

Repositorio (o "repo"). Es la carpeta de tu proyecto con toda su historia guardada. Por fuera se ve como una carpeta normal. Por dentro tiene una carpeta oculta llamada .git donde Git guarda el cuaderno de bitácora. Nunca toques esa carpeta a mano.

Repositorio local. La copia del proyecto que está en tu computadora.

Repositorio remoto. La copia que está en GitLab o GitHub. Es la que comparte todo el equipo.

Commit. Un punto de guardado. Una foto del proyecto en un momento, con un mensaje que explica qué cambiaste. Es la unidad básica de Git.

Historial. La lista de todos los commits, del más reciente al más antiguo. Es la historia completa del proyecto.

Rama. Una línea de trabajo paralela. Te permite probar cosas sin tocar la versión principal. Lo vemos a fondo en el capítulo 4.

Local y remoto: la idea que más confunde

Aquí está la clave que a mucha gente le cuesta al principio: guardar un cambio en tu computadora no es lo mismo que publicarlo para el equipo.

El recorrido de un cambio es así:

  1. Editas un archivo en tu computadora.

  2. Haces un commit: el cambio queda guardado en tu cuaderno, solo en tu computadora.

  3. Haces un push (empujar): envías tus commits a GitLab. Ahora el equipo los puede ver.

  4. Tus compañeros hacen un pull (jalar): traen tus cambios a sus computadoras.

Si haces commit pero nunca haces push, tu trabajo existe solo en tu computadora. Si tu disco se daña, se pierde. Y tu equipo nunca lo vio. Este malentendido causa muchísimos problemas de "pero yo sí lo guardé".

Por qué esto hace posible el trabajo en equipo

Cada persona del equipo tiene su propia copia completa del proyecto, con toda la historia. Trabajan tranquilas en su computadora. Cuando terminan algo, lo envían a la copia compartida en GitLab.

GitLab actúa como punto de encuentro. Ahí se juntan los cambios de todos, se revisan antes de aceptarse y queda registro de cada decisión. Nadie le manda archivos a nadie por correo.

Qué hay dentro de un commit

Cada commit guarda cinco cosas. Conocerlas te ayuda a leer cualquier historial:

ParteQué esEjemplo
IdentificadorUn código único, generado por Gita3f9c21 (versión corta)
AutorNombre y correo de quien hizo el cambioAna Pérez ana@ejemplo.com
FechaCuándo se hizo8 de octubre, 10:42 a.m.
MensajeLa explicación del cambioCorrige teléfono de contacto
Commit anteriorEl commit del que parte7b2e104

Ese último punto es clave: cada commit apunta al anterior. Así se forma una cadena, como los eslabones de una cadena o las páginas numeradas de un diario. Gracias a esa cadena, Git puede reconstruir el proyecto tal como estaba en cualquier momento.

También por eso un commit no se puede "editar" en secreto. Si cambias algo de un commit viejo, su identificador cambia, y todos los que vienen después también. Es una protección: la historia es confiable.

Otras plataformas que vas a escuchar

GitLab y GitHub son las más conocidas, pero no las únicas. Todas usan Git por debajo, así que lo que aprendas aquí te sirve en cualquiera:

  • Bitbucket: común en empresas que usan otras herramientas de Atlassian, como Jira.

  • Azure DevOps: muy usada en organizaciones que trabajan con tecnologías de Microsoft.

  • Gitea y Forgejo: opciones ligeras para instalar en un servidor propio.

Cambian los menús y algunos nombres. Git es el mismo.

Terminal o botones: ¿qué conviene usar?

Puedes usar Git de tres formas, y no son excluyentes:

  1. La terminal. Escribes los comandos. Es lo que más usaremos en el libro, porque te obliga a entender qué pasa y funciona igual en cualquier computadora.

  2. Tu editor de código. VS Code y Cursor traen un panel de Git con botones para ver cambios, hacer commit, push y pull. Es cómodo y visual.

  3. La web de GitLab. Puedes editar archivos y hacer commits directamente en el navegador. Sirve para cambios pequeños, como corregir un texto en el README.

Mi recomendación: aprende con la terminal y luego usa lo que te resulte más cómodo. Cuando algo falle, saber qué hace cada comando te va a sacar del problema. Los botones del editor solo ejecutan esos mismos comandos por ti.

Ante la duda, empieza en privado. Siempre puedes abrirlo después. Lo contrario es más delicado: lo que estuvo público pudo haber sido copiado.

Preguntas frecuentes

¿Git es gratis? Sí. Git es software libre. GitLab y GitHub tienen planes gratuitos más que suficientes para aprender y para equipos pequeños.

¿Necesito internet para usar Git? Para guardar commits, no. Para compartirlos (push) o traer los de otros (pull), sí.

¿Puedo usar Git con documentos de Word o Excel? Puedes guardarlos, pero Git no podrá mostrarte qué cambió por dentro, ni ayudarte a juntar cambios de dos personas. Funciona mejor con archivos de texto plano: código, Markdown, configuraciones.

¿Qué pasa si borro la carpeta del proyecto en mi computadora? Si habías hecho push, nada grave: lo vuelves a clonar desde GitLab. Lo que no habías publicado sí se pierde.

Ejemplo real: leer el historial de un proyecto

Entra a cualquier proyecto público de GitLab o GitHub y abre la sección de commits. Verás algo así:

Corrige el cálculo de totales en el reporte mensual
Ana Pérez · hace 2 horas

Agrega filtro por fecha en la búsqueda
Luis Gómez · ayer

Actualiza instrucciones de instalación en el README

Sin abrir un solo archivo ya sabes qué ha pasado en el proyecto, quién lo hizo y cuándo. Si haces clic en un commit, GitLab te muestra exactamente qué líneas se agregaron (en verde) y cuáles se quitaron (en rojo).

  6. Recorre el menú de la izquierda y localiza: Issues, Merge requests y Pipelines. Solo míralos, no toques nada.

Capítulo 2. Prepara tu computadora

Al terminar este capítulo tendrás Git instalado, tu identidad configurada, una conexión segura con GitLab y tu primer proyecto descargado. Es el capítulo más "técnico" del libro, pero solo se hace una vez. Ve paso a paso y no te saltes nada.

Paso 1: abre la terminal

La terminal es una ventana donde escribes órdenes y la computadora las ejecuta. Parece de película de hackers, pero solo es otra forma de usar tu computadora.

SistemaCómo abrirla
WindowsDespués de instalar Git (paso 2), busca Git Bash en el menú de inicio. Usa esa.
MacPulsa Cmd + Espacio, escribe Terminal y pulsa Enter.
LinuxBusca Terminal en tus aplicaciones, o pulsa Ctrl + Alt + T.

Tres reglas para no asustarte:

  • Escribes la orden y pulsas Enter para ejecutarla.

  • Si no aparece ningún mensaje, casi siempre significa que todo salió bien.

  • Si te equivocas al escribir, no pasa nada: te sale un error y vuelves a intentar.

Paso 2: instala Git

En Windows. Entra a git-scm.com, descarga Git para Windows e instálalo. Puedes aceptar las opciones que vienen marcadas por defecto. Esto también instala Git Bash, la terminal que usaremos.

En Mac. Abre la Terminal y escribe:

git --version

Si Git no está instalado, el Mac te ofrecerá instalar las "herramientas de línea de comandos". Acepta y espera a que termine. Si usas Homebrew, también puedes instalarlo con brew install git.

En Linux (Ubuntu o Debian). Escribe:

sudo apt update
sudo apt install git

Comprueba que funcionó. En cualquier sistema, escribe:

git --version

Si ves algo como git version 2.x.x, Git está listo. El número exacto no importa.

Paso 3: dile a Git quién eres

Cada commit que hagas llevará tu nombre y tu correo. Así el equipo sabe quién hizo cada cambio. Esto se configura una sola vez:

git config --global user.name "Tu Nombre Apellido"
git config --global user.email "tu-correo@ejemplo.com"

Usa el mismo correo que usas en GitLab. Así GitLab reconoce tus commits y los conecta con tu perfil.

Te recomiendo dos configuraciones más:

git config --global init.defaultBranch main
git config --global core.editor "nano"

La primera hace que la rama principal de tus proyectos nuevos se llame main, que es el nombre que se usa hoy. La segunda elige un editor sencillo para cuando Git te pida escribir algo. Si usas VS Code o Cursor, puedes cambiar nano por code --wait o cursor --wait.

Para revisar lo que configuraste:

git config --global --list

¿Qué significa --global? Que la configuración aplica a todos tus proyectos en esta computadora. Si necesitas otro correo en un proyecto específico (por ejemplo, el del trabajo), entra a esa carpeta y repite el comando sin --global.

Paso 4: conecta tu computadora con GitLab

Para enviar y traer cambios, GitLab necesita saber que eres tú. Hay dos formas de hacerlo: HTTPS y SSH.

Opción A: HTTPS con un token

Un token de acceso personal es como una contraseña especial que creas solo para Git. Puedes darle fecha de vencimiento y borrarlo cuando quieras, sin cambiar tu contraseña real.

  1. En GitLab, haz clic en tu foto de perfil y entra a Preferences (o Edit profile).

  2. Busca Access tokens (tokens de acceso).

  3. Crea un token nuevo. Ponle un nombre como "Mi laptop", una fecha de vencimiento y marca los permisos read_repository y write_repository.

  4. Copia el token en ese momento. GitLab no te lo vuelve a mostrar.

  5. Cuando Git te pida contraseña al clonar o hacer push, pega el token en lugar de tu contraseña.

Guarda el token como guardas una contraseña. Nunca lo pegues en un archivo del proyecto ni en un chat.

Opción B: SSH con llaves (recomendada)

SSH funciona con un par de llaves: una pública y una privada. Piensa en un candado y su llave. Le das el candado (llave pública) a GitLab. La llave privada se queda en tu computadora y nunca la compartes. Cuando te conectas, GitLab comprueba que tu llave abre su candado.

1. Crea tus llaves:

ssh-keygen -t ed25519 -C "tu-correo@ejemplo.com"

Te hará algunas preguntas. Pulsa Enter para aceptar la ubicación por defecto. Después te pedirá una frase de seguridad (passphrase): es opcional, pero recomendable.

2. Copia tu llave pública (la que termina en .pub):

cat ~/.ssh/id_ed25519.pub

Verás una línea larga que empieza con ssh-ed25519. Cópiala completa.

3. Agrégala en GitLab: foto de perfil > Preferences > SSH Keys > Add new key. Pega la llave, ponle un título como "Mi laptop" y guarda.

4. Comprueba la conexión:

ssh -T git@gitlab.com

La primera vez te preguntará si confías en el servidor. Escribe yes. Si ves un mensaje de bienvenida con tu usuario, ya estás conectada o conectado. Si tu organización tiene su propio GitLab, cambia gitlab.com por la dirección de ese servidor.

Regla de oro: el archivo que termina en .pub se puede compartir. El que no termina en .pub es tu llave privada y nunca sale de tu computadora. Ni por correo, ni por chat, ni dentro de un repositorio.

Paso 5: clona tu primer repositorio

Clonar es descargar un proyecto de GitLab a tu computadora, con toda su historia. Se hace una sola vez por proyecto.

  1. En GitLab, abre el proyecto.

  2. Haz clic en el botón azul Code (o Clone).

  3. Copia la dirección de Clone with SSH (o la de HTTPS si elegiste esa opción).

  4. En la terminal, ve a la carpeta donde guardas tus proyectos y clona:

cd Documentos
git clone git@gitlab.com:tu-usuario/practica-git.git

  1. Entra a la carpeta del proyecto:

cd practica-git

Listo: tienes el proyecto en tu computadora. Desde ahora, todos los comandos de Git se ejecutan dentro de esa carpeta.

¿Qué hace cd? Significa "cambiar de directorio": es como hacer doble clic en una carpeta. cd .. te devuelve a la carpeta anterior. Y ls (o dir en Windows sin Git Bash) te muestra lo que hay en la carpeta actual.

Clonar o empezar de cero: git clone vs git init

Hay dos formas de tener un repositorio en tu computadora:

Si ya tienes una carpeta con archivos y quieres llevarla a GitLab:

cd mi-carpeta
git init
git add README.md
git commit -m "Primer commit del proyecto"
git remote add origin git@gitlab.com:tu-usuario/mi-carpeta.git
git push -u origin main

Antes del último paso, crea en GitLab un proyecto vacío (sin README) con ese mismo nombre. origin es el apodo que Git le da a la copia en GitLab. El -u solo se usa la primera vez: le dice a Git que de ahora en adelante git push vaya siempre a ese lugar.

Para ver a qué remoto está conectado un proyecto:

git remote -v

Git dentro de tu editor

Si usas VS Code o Cursor, abre la carpeta del proyecto (File > Open Folder). Verás:

  • Un ícono de ramas en la barra lateral: es el panel de control de código fuente. Ahí aparecen los archivos modificados.

  • Al hacer clic en un archivo modificado, se abre una vista lado a lado con lo que cambió.

  • Abajo a la izquierda, el nombre de la rama en la que estás.

  • Una terminal integrada (Terminal > New Terminal) que ya se abre dentro de la carpeta del proyecto. Muy práctico: no tienes que navegar con cd.

Te recomiendo usar la terminal integrada para los comandos del libro y el panel visual para revisar cambios. Es la mejor combinación de los dos mundos.

Si usas una cuenta del trabajo y otra personal

Es muy común: GitLab con el correo de la empresa y GitHub con tu correo personal. Para que cada commit salga con el correo correcto:

  1. Deja tu correo más usado como configuración global (paso 3).

  2. En cada proyecto que use el otro correo, entra a su carpeta y escribe:

git config user.email "correo-del-otro@ejemplo.com"

Sin --global, el cambio solo aplica a ese proyecto. Comprueba con git config user.email dentro de la carpeta.

Para SSH puedes usar la misma llave pública en GitLab y en GitHub. Solo agrégala en ambas cuentas.

Capítulo 3. Tu primer ciclo: mira antes de guardar

El trabajo diario con Git es un ciclo de seis pasos: revisar, elegir, guardar, ver la historia, traer y publicar. La regla más importante de este capítulo es simple: mira antes de guardar. Si la aprendes ahora, te vas a ahorrar muchos dolores de cabeza.

Mi historia: guardar todo sin mirar

Cuando aprendí Git sola, con tutoriales, me quedé con un atajo: guardar todo de golpe. Cambiaba cosas, escribía el comando para incluir todo, hacía el commit y listo. Rápido y cómodo.

El problema apareció después. Al revisar el historial, encontraba commits que mezclaban cosas que no tenían nada que ver entre sí. Había cambios que no quería guardar todavía y archivos que nunca debieron entrar al proyecto. Y cuando quería deshacer una sola cosa, no podía, porque estaba revuelta con todo lo demás.

De ahí saqué la regla que repito en cada capítulo: antes de guardar, mira qué estás guardando. Toma diez segundos y te salva horas.

Las tres zonas de Git

Para entender el ciclo, imagina que preparas un envío por correo:

  1. La mesa de trabajo (en Git: directorio de trabajo). Es tu carpeta, donde editas archivos. Aquí todo está en desorden, y está bien.

  2. La caja abierta (en Git: área de preparación o staging). Aquí metes solo lo que quieres enviar en este paquete. Puedes sacar y meter cosas antes de cerrarla.

  3. El paquete cerrado y etiquetado (en Git: commit). Cerraste la caja y le pusiste una etiqueta que dice qué lleva. Queda guardado en tu historial.

Y hay un cuarto lugar: la oficina de correos, que es GitLab. El paquete no llega ahí hasta que lo envías con push.

La caja intermedia existe justo para que elijas qué guardar. Saltarte ese paso es lo que me pasaba a mí.

Paso 1: git status, ¿qué está pasando?

Es el comando que más vas a usar. Te dice en qué estado está cada archivo. Úsalo antes y después de cada paso, sin miedo: solo mira, no cambia nada.

git status

Una respuesta típica:

On branch main
Changes not staged for commit:
        modified:   README.md

Untracked files:
        notas-personales.txt

Traducido:

  • On branch main: estás en la rama principal.

  • Changes not staged: modificaste README.md, pero todavía no está en la caja.

  • Untracked files: notas-personales.txt es un archivo nuevo que Git todavía no está siguiendo.

Paso 2: git diff, ¿qué cambié exactamente?

git diff

Te muestra línea por línea lo que cambiaste y todavía no está en la caja. Las líneas con - se quitaron y las que tienen + se agregaron:

- Horario: lunes a viernes, 8:00 a 4:00
+ Horario: lunes a viernes, 8:00 a 5:00

Aquí es donde descubres el cambio que no querías, el espacio de más o el texto de prueba que olvidaste borrar. Para salir de esta vista, pulsa la tecla q.

Paso 3: git add, elegir qué entra en la caja

Agrega los archivos por su nombre:

git add README.md

Vuelve a mirar con git status. Ahora verás README.md en una sección nueva, Changes to be committed: ya está en la caja. Y notas-personales.txt sigue fuera, como querías.

Si quieres revisar lo que ya está en la caja antes de cerrarla:

git diff --staged

Sobre git add . Este comando mete en la caja todo lo que cambió en la carpeta. No está prohibido, pero úsalo solo después de mirar git status y estar segura o seguro de que todo lo que aparece debe entrar. Ese fue mi error: usarlo sin mirar.

¿Metiste algo por error en la caja? Sácalo sin perder el cambio:

git restore --staged notas-personales.txt

Paso 4: git commit, cerrar y etiquetar el paquete

git commit -m "Actualiza horario de atención a 5:00 p.m."

El texto entre comillas es el mensaje del commit. Es la nota que leerán tus compañeros, y tú misma o tú mismo dentro de seis meses.

Cómo escribir commits claros

Un buen mensaje responde a la pregunta: ¿qué hace este cambio?

Mensaje confusoMensaje claro
cambiosCorrige teléfono de contacto en la página de inicio
arreglos variosCorrige error al guardar formulario sin fecha
ya funciona!!!Valida que el correo tenga formato correcto

Cinco reglas sencillas:

  1. Empieza con un verbo: Agrega, Corrige, Actualiza, Elimina, Mejora.

  2. Sé específica o específico: di qué cambiaste y dónde.

  3. Mantenlo corto: una línea de menos de 70 caracteres.

  4. Un commit, una idea. Si tu mensaje necesita la palabra "y" para dos cosas distintas, probablemente deberían ser dos commits.

  5. Si el motivo no es obvio, explica el porqué. Usa git commit sin -m para que se abra el editor y escribe una línea de resumen, una línea en blanco y luego el detalle.

Paso 5: git log, ver la historia

git log --oneline

Muestra un commit por línea, del más nuevo al más viejo:

a3f9c21 Actualiza horario de atención a 5:00 p.m.
7b2e104 Agrega sección de contacto
1c8d3aa Initial commit

Ese código del inicio (a3f9c21) es el identificador único de cada commit. Lo usarás más adelante para volver atrás o revisar cambios. Sin --oneline verás también el autor y la fecha. Pulsa q para salir.

Paso 6: git pull y git push, traer y publicar

Antes de publicar, trae siempre lo nuevo del equipo:

git pull

Esto descarga los cambios que otros publicaron y los junta con los tuyos. Si nadie cambió nada, te dirá Already up to date.

Ahora sí, publica:

git push

Tus commits viajan a GitLab. Abre el proyecto en el navegador y verás tu mensaje en la lista de commits.

¿Por qué pull antes de push? Si alguien publicó algo después de tu último pull, GitLab va a rechazar tu push con un mensaje de error. No es grave: haz git pull y vuelve a intentar. Pero es más ordenado hacerlo antes.

.gitignore: lo que nunca debe entrar

Hay archivos que nunca deben guardarse en el repositorio: archivos con contraseñas o claves, carpetas que se generan solas, archivos temporales del sistema o tus notas personales.

Para eso existe .gitignore: un archivo de texto en la raíz del proyecto con la lista de lo que Git debe ignorar. Ejemplo:

# Configuración con datos sensibles
.env

# Archivos del sistema
.DS_Store
Thumbs.db

# Notas personales
notas-personales.txt

# Carpetas que se generan solas
node_modules/
__pycache__/

Lo que aparece en .gitignore deja de salir en git status. Así no lo puedes agregar por accidente, ni siquiera con git add ..

Ojo: .gitignore solo funciona con archivos que todavía no se han guardado. Si un archivo ya entró en un commit, agregarlo después a .gitignore no lo borra del historial. Por eso conviene crearlo al inicio del proyecto. Y si alguna vez subes una contraseña, cámbiala de inmediato: lo vemos en el capítulo 10.

Resumen del ciclo

git status                 # 1. ¿Qué cambió?
git diff                   # 2. ¿Qué cambié exactamente?
git add archivo            # 3. Elijo qué entra
git diff --staged          #    Reviso la caja
git commit -m "Mensaje"    # 4. Guardo con un buen mensaje
git log --oneline          # 5. Veo la historia
git pull                   # 6. Traigo lo nuevo
git push                   #    Publico

Elegir partes de un archivo: git add -p

A veces cambiaste dos cosas distintas en el mismo archivo: una corrección y una prueba. Con git add archivo entrarían las dos. Para elegir pedazo por pedazo:

git add -p README.md

Git te muestra cada bloque de cambios y te pregunta qué hacer. Las respuestas que más usarás:

  • y (sí): este bloque entra en la caja.

  • n (no): este bloque se queda fuera.

  • q (salir): termina sin revisar el resto.

  • ? (ayuda): muestra todas las opciones.

Es la herramienta perfecta para cumplir la regla de "un commit, una idea". En VS Code y Cursor puedes hacer lo mismo con el ratón: selecciona líneas en la vista de cambios y elige Stage Selected Ranges.

Ver un commit en detalle: git show

git show a3f9c21

Muestra el autor, la fecha, el mensaje y exactamente qué líneas cambió ese commit. Si no pones el código, te muestra el último commit. Es útil para responder "¿qué hice ayer?" o "¿qué cambió Ana en ese commit?".

Otros usos de git log que te van a servir:

git log --oneline -5              # Solo los últimos 5 commits
git log --oneline --author="Ana"  # Solo los commits de Ana
git log --oneline -- README.md    # Solo los commits que tocaron ese archivo

Me equivoqué en el último commit (y no he hecho push)

Si escribiste mal el mensaje o olvidaste agregar un archivo, puedes corregir el último commit:

git add archivo-olvidado.txt
git commit --amend -m "Mensaje corregido"

Advertencia: usa --amend solo si todavía no hiciste push. Si ya publicaste el commit, corregirlo así cambia la historia que tus compañeros ya descargaron y les causa problemas. En ese caso, haz un commit nuevo con la corrección.

¿Cada cuánto hago commit?

No hay un número mágico, pero estas señales ayudan:

  • Haz commit cuando terminas una idea completa, aunque sea pequeña: corregiste un error, agregaste una sección, cambiaste un texto.

  • Haz commit antes de algo arriesgado, como reorganizar carpetas. Si sale mal, vuelves a ese punto.

  • No esperes días. Si llevas una semana sin commit, tienes demasiados cambios mezclados y será difícil explicarlos o deshacerlos.

  • No hagas commit de algo roto en la rama principal. Si necesitas guardar algo a medias, hazlo en tu propia rama (capítulo 4).

Una buena prueba: si puedes describir el cambio en una línea clara, es buen momento para el commit.

  4. Escribe el mensaje arriba y pulsa Commit.

  5. Pulsa Sync Changes o los botones de flechas para hacer pull y push.

Cuidado con el botón de commit cuando no hay nada en la caja: algunos editores te ofrecen guardar todos los cambios de golpe. Es el equivalente a git add . sin mirar. Lee el mensaje antes de aceptar.

Ejemplo real: un commit limpio contra uno revuelto

Luis corrige un error en el formulario de contacto. Mientras tanto, también cambia unos colores para probar y deja un archivo de pruebas en la carpeta.

Commit revuelto. Luis usa git add . y escribe git commit -m "arreglos". Entra todo junto: la corrección, los colores de prueba y el archivo basura. Dos semanas después, el equipo quiere deshacer los colores. No puede hacerlo sin deshacer también la corrección.

Commit limpio. Luis mira git status y git diff. Ve los tres cambios. Agrega solo el archivo del formulario y hace git commit -m "Corrige validación del correo en el formulario de contacto". Descarta los colores de prueba y añade el archivo de pruebas a .gitignore. El historial queda claro y cada cambio se puede deshacer por separado.

  3. Ejecuta git status y explica con tus palabras qué ves.

Capítulo 4. Ramas: trabaja sin miedo

Una rama es una copia de trabajo paralela dentro del mismo proyecto. Te deja probar, equivocarte y terminar un cambio sin tocar la versión principal, que es la que usa todo el equipo. Si aprendes una sola costumbre de este capítulo, que sea esta: nunca trabajes directo en main.

Por qué existen las ramas

Imagina que tu equipo mantiene el sitio web de la oficina. La versión que está en main es la que funciona y la que se publica. Ahora te piden rediseñar el formulario de contacto, algo que te tomará tres días.

Si trabajas directo en main:

  • Durante tres días, la versión principal tiene un formulario a medio hacer.

  • Si mientras tanto alguien necesita corregir un error urgente, tiene que publicar también tu trabajo incompleto.

  • Si a mitad de camino decides que tu idea no funciona, deshacerla es complicado.

Con una rama, haces todo el rediseño aparte. main sigue intacta y estable. Cuando terminas y alguien revisa tu trabajo, lo juntas con main. Si tu idea no funcionó, borras la rama y nadie se enteró.

Una comparación: el borrador

Piensa en main como el documento oficial que está publicado. Una rama es un borrador que sacas a partir de ese documento. Escribes, tachas y reescribes en tu borrador todo lo que quieras. El documento oficial no cambia.

Cuando tu borrador está listo, pides que lo revisen. Si lo aprueban, sus cambios pasan al documento oficial. Eso se llama fusionar (en inglés, merge).

Y lo mejor: cada persona del equipo puede tener sus propios borradores al mismo tiempo, cada uno para una tarea distinta.

Cómo se ve una rama por dentro

Recuerda del capítulo 1 que cada commit apunta al anterior, formando una cadena. Una rama es simplemente una etiqueta que apunta al último commit de una línea de trabajo. Cuando haces un commit en esa rama, la etiqueta avanza.

main:            A --- B --- C
                        \
formulario-nuevo:        D --- E

Aquí, main tiene los commits A, B y C. La rama formulario-nuevo salió del commit B y tiene sus propios commits, D y E. Las dos líneas avanzan sin estorbarse. Cuando fusiones, los cambios de D y E entran a main.

Por eso crear una rama es instantáneo y no ocupa espacio: Git no copia archivos, solo crea una etiqueta nueva.

Los comandos de ramas

Ver las ramas

git branch

Muestra tus ramas locales. La que tiene un asterisco (*) es en la que estás ahora. Para ver también las ramas que existen en GitLab:

git branch -a

Las que empiezan con remotes/origin/ son las de GitLab.

Crear una rama y cambiarte a ella

Primero, asegúrate de partir de la versión más reciente de main:

git switch main
git pull

Ahora crea tu rama y entra en ella con un solo comando:

git switch -c feature/formulario-contacto

La -c significa create (crear). Desde este momento, todos tus commits van a esta rama.

¿Y git checkout? En tutoriales viejos verás git checkout -b nombre-rama. Hace lo mismo. git switch es la forma moderna y más clara, porque checkout hace demasiadas cosas distintas. En este libro usamos switch.

Cambiar de rama

git switch main
git switch feature/formulario-contacto

Al cambiar de rama, los archivos de tu carpeta cambian para mostrar el estado de esa rama. No te asustes si un archivo "desaparece": sigue guardado en la otra rama.

Publicar tu rama en GitLab

La primera vez que haces push de una rama nueva:

git push -u origin feature/formulario-contacto

Después de esa primera vez, basta con git push. Publicar tu rama tiene dos ventajas: tu trabajo queda respaldado en GitLab y tus compañeros pueden verlo.

Mantener tu rama al día con main

Mientras trabajas en tu rama, otros siguen fusionando cambios en main. Si tu rama se queda atrás mucho tiempo, juntarla al final será más difícil. Por eso conviene traer lo nuevo de main a tu rama cada cierto tiempo:

git switch main
git pull
git switch feature/formulario-contacto
git merge main

Esto mete en tu rama los cambios nuevos de main. Si nadie tocó lo mismo que tú, se junta solo. Si hubo cambios en las mismas líneas, aparecerá un conflicto, y lo resolvemos en el capítulo 6. Mejor resolver un conflicto pequeño hoy que uno enorme en un mes.

Vas a escuchar de rebase. Es otra forma de poner tu rama al día que deja un historial más lineal. Es útil, pero tiene más riesgos para quien empieza. Quédate con merge hasta que te sientas segura o seguro con todo lo de este libro.

Borrar una rama

Cuando tu rama ya se fusionó en main, ya no la necesitas:

git switch main
git branch -d feature/formulario-contacto

Si Git se niega con un mensaje como not fully merged, te está protegiendo: esa rama tiene commits que no están en main. Revisa antes de borrar. Si estás totalmente segura o seguro de que quieres perder ese trabajo, se usa -D en mayúscula. Úsala con mucho cuidado.

Para borrar la rama en GitLab:

git push origin --delete feature/formulario-contacto

Normalmente no hace falta: GitLab puede borrarla sola al completar la Merge Request (lo vemos en el capítulo 5).

Qué pasa con tus cambios sin guardar al cambiar de rama

Esta es una duda muy común. Si tienes archivos modificados sin commit y cambias de rama, puede pasar una de dos cosas:

  1. Los cambios viajan contigo a la nueva rama, si no chocan con nada. Esto confunde, porque parece que el cambio "se pasó" de rama.

  2. Git no te deja cambiar y te dice que tus cambios se sobrescribirían. Te está protegiendo.

La regla sencilla: antes de cambiar de rama, deja tu carpeta limpia. Haz commit de lo que tengas, o guárdalo temporalmente con git stash (lo vemos en el capítulo 7). Revisa siempre con git status antes de cambiar.

Cómo nombrar las ramas

Un buen nombre dice qué tipo de cambio es y de qué se trata. La convención más usada es tipo/descripcion-corta:

PrefijoPara quéEjemplo

hotfix/Corrección urgente para producciónhotfix/caida-login

Reglas para el nombre:

  • Todo en minúsculas.

  • Palabras separadas con guiones, sin espacios.

  • Sin tildes ni eñes: escribe instalacion, no instalación.

  • Corto pero claro: tres o cuatro palabras bastan.

  • Si trabajas con issues (capítulo 8), incluye su número: fix/42-telefono-pie-de-pagina. Así cualquiera sabe a qué tarea pertenece.

Lo más importante es que todo el equipo use la misma convención. Si tu equipo ya tiene una, síguela aunque sea distinta a esta.

Ramas cortas: la regla que aprendí a la fuerza

Una rama debería vivir días, no semanas. Mientras más tiempo vive separada de main, más cambios acumulan las dos, y más difícil es juntarlas. En el capítulo 6 te cuento el conflicto gigante que viví por no respetar esta regla.

Cómo mantener las ramas cortas:

  • Divide el trabajo grande en pedazos pequeños. En vez de una rama "rediseño completo del sitio", haz una para el encabezado, otra para el formulario, otra para el pie de página.

  • Fusiona seguido. Cada pedazo terminado y revisado entra a main.

  • Trae main a tu rama con frecuencia si tu trabajo se alarga.

  • Una rama, una tarea. No aproveches la rama del formulario para "de paso" arreglar otra cosa.

Las ramas en GitLab

En el menú Code > Branches ves todas las ramas del proyecto. Para cada una, GitLab te muestra:

  • Su último commit y quién lo hizo.

  • Cuántos commits está adelante de main (cambios que tiene y main no) y cuántos atrás (cambios de main que le faltan).

  • Un botón para crear una Merge Request.

  • Si está protegida (capítulo 10).

También puedes crear ramas desde ahí con New branch, aunque luego tendrás que traerla a tu computadora:

git fetch
git switch nombre-de-la-rama

git fetch trae la información nueva de GitLab sin juntarla con tu trabajo. Es como mirar el buzón sin abrir las cartas.

Ver las ramas como un dibujo

Para ver el historial con sus ramas dibujadas en la terminal:

git log --oneline --graph --all

Verás líneas y asteriscos que muestran dónde se separó cada rama y dónde se juntó. Al principio parece un enredo, pero con práctica se lee como un mapa del metro. En GitLab tienes la misma vista, más bonita, en Code > Repository graph.

Ana está en la rama feature/formulario-contacto, a mitad del rediseño. De pronto le avisan que el teléfono del pie de página está mal y hay que corregirlo hoy.

El error urgente se resolvió sin publicar el formulario a medias. Y la rama de Ana quedó al día. Esto es imposible de hacer limpio si todo el mundo trabaja en main.

Capítulo 5. Merge Requests: pide permiso para integrar

Una Merge Request es una solicitud formal para juntar tu rama con main. Es el momento en que otra persona mira tu trabajo antes de que entre a la versión que usa todo el equipo. Aquí aprenderás a crearla, a describirla bien, a recibir comentarios sin tomártelo personal y a completar la fusión.

En GitHub se llama… Pull Request (PR). Funciona exactamente igual. Cuando escuches "abre un PR" o "abre una MR", es lo mismo.

Por qué no simplemente fusionar

Técnicamente podrías juntar tu rama con main desde la terminal, sin preguntarle a nadie. Pero perderías tres cosas muy valiosas:

  1. Otro par de ojos. Quien escribe un cambio casi nunca ve sus propios errores. Alguien que llega fresco encuentra el detalle que a ti se te pasó.

  2. Un registro de la decisión. La Merge Request guarda qué se cambió, por qué, quién lo revisó y qué se discutió. Dentro de un año, alguien podrá entender por qué el sistema funciona así.

  3. Aprendizaje en equipo. Al revisar el trabajo de otros aprendes cómo piensan y conoces partes del proyecto que no tocas.

En muchos equipos, además, main está protegida: nadie puede fusionar sin una Merge Request aprobada. Lo vemos en el capítulo 10.

Si te interesa profundizar en cómo revisar código bien, tengo un libro dedicado solo a eso. Aquí nos enfocamos en el proceso dentro de GitLab.

El recorrido completo de una Merge Request

  1. Trabajas en tu rama y haces push.

  2. Abres la Merge Request: "quiero juntar feature/x con main".

  3. Asignas a una o más personas para revisar.

  4. Revisan y dejan comentarios.

  5. Respondes y corriges con nuevos commits en la misma rama.

  6. Aprueban.

  7. Se fusiona y la rama se borra.

  8. Todos actualizan su main con git pull.

Vamos paso a paso.

Paso 1: crear la Merge Request

Hay tres formas, todas llevan al mismo formulario:

Desde la terminal. Cuando haces push de una rama nueva, GitLab responde con un enlace como este:

remote: To create a merge request for feature/formulario-contacto, visit:
remote:   https://gitlab.com/tu-usuario/proyecto/-/merge_requests/new?...

Copia el enlace y ábrelo en el navegador.

Desde el aviso de GitLab. Al abrir el proyecto después de un push, GitLab muestra un aviso con tu rama y un botón Create merge request.

Desde el menú. Ve a Code > Merge requests > New merge request. Elige tu rama como origen (source branch) y main como destino (target branch).

Revisa siempre el origen y el destino antes de seguir. Un error común es abrir la Merge Request hacia la rama equivocada.

Paso 2: describir bien el cambio

Esta es la parte que más se descuida y la que más ayuda a quien revisa. Una buena descripción le ahorra a tu compañero adivinar qué hiciste.

El título. Igual que un buen commit: empieza con un verbo y di qué hace el cambio.

Título confusoTítulo claro
Cambios formularioAgrega validación de correo al formulario de contacto
fixCorrige teléfono incorrecto en el pie de página
Rama de AnaActualiza instrucciones de instalación para Windows

La descripción. Usa esta plantilla. Puedes copiarla tal cual:

## Qué cambia
Agrega validación del correo en el formulario de contacto.
Antes se podía enviar con un correo mal escrito.

## Por qué
Recibíamos mensajes que no podíamos responder.
Relacionado con el issue #42.

## Cómo probarlo
1. Abre la página de contacto.
2. Escribe un correo sin @ y pulsa Enviar.
3. Debe aparecer el mensaje "Correo no válido".

## Capturas
(antes / después, si aplica)

## Pendientes o dudas
No validé dominios específicos. ¿Hace falta?

No todas las secciones aplican siempre. Pero qué cambia, por qué y cómo probarlo deberían estar en casi todas las Merge Requests.

Si escribes Closes #42 en la descripción, GitLab cerrará el issue 42 automáticamente cuando se fusione. Lo vemos en el capítulo 8.

Merge Requests en borrador

Si tu trabajo no está terminado pero quieres mostrarlo o pedir una opinión temprana, márcala como borrador (Draft). Puedes hacerlo con la casilla Mark as draft o empezando el título con Draft:.

Una Merge Request en borrador no se puede fusionar. Es una forma clara de decir: "todavía no está listo, pero mírenlo". Cuando termines, quita la marca con Mark as ready.

Abrir una Merge Request temprano, en borrador, es una muy buena práctica. Recibes comentarios antes de avanzar demasiado en una dirección equivocada.

Paso 4: revisar tu propia Merge Request primero

Antes de pedirle a alguien que revise, revísala tú. Entra a la pestaña Changes y lee tus cambios como si fueran de otra persona. Busca:

  • Archivos que no deberían estar ahí.

  • Texto de prueba, comentarios olvidados o cosas a medias.

  • Errores de ortografía en textos que verá el usuario.

  • Cambios que no tienen que ver con la tarea.

Te sorprenderá cuántas cosas encuentras. Y cada una que corriges tú es una que no tiene que señalar tu compañero.

Cómo se revisa en GitLab (si te toca revisar)

Cuando alguien te asigna como revisora o revisor:

  1. Lee la descripción primero. Entiende qué intenta resolver antes de mirar los cambios.

  2. Abre la pestaña Changes. Verás cada archivo con las líneas agregadas en verde y las quitadas en rojo.

  3. Comenta sobre una línea. Pasa el ratón sobre el número de línea y haz clic en el ícono de comentario. Escribe tu observación.

  4. Sugiere un cambio concreto. En el comentario, usa el botón Insert suggestion. Escribes cómo debería quedar la línea y el autor puede aplicarlo con un clic.

  5. Agrupa tus comentarios. Usa Start a review en vez de Add comment now. Así tus comentarios se publican todos juntos al final, en vez de mandarle diez notificaciones al autor.

  6. Decide. Si todo está bien, pulsa Approve. Si hay cosas por corregir, publica tu revisión y espera los cambios.

Cómo escribir buenos comentarios

La revisión es sobre el código, no sobre la persona. Unas pautas:

En vez dePrueba
"Esto está mal.""Aquí falta validar que la fecha no esté vacía. Si llega vacía, el formulario falla."
"¿Por qué hiciste esto así?""¿Qué te llevó a usar este enfoque? Pregunto porque X podría ser más sencillo."
"Cambia el nombre.""Sugerencia: total_mensual sería más claro que tm."
(silencio sobre lo bueno)"Me gustó cómo separaste esta parte, se entiende muy bien."

También ayuda marcar qué tan importante es cada comentario:

  • Bloqueante: hay que corregirlo antes de fusionar.

  • Sugerencia: mejoraría, pero no es obligatorio.

  • Detalle (en inglés verás nit): algo menor, como un espacio o una palabra.

  • Pregunta: no es un pedido de cambio, solo quieres entender.

Paso 5: responder a las observaciones

Recibir comentarios sobre tu trabajo puede incomodar al principio. Recuerda que la revisión mejora el resultado y te protege: es mejor que un compañero vea el error hoy a que lo vea un usuario mañana.

Para cada comentario:

  1. Léelo completo y asegúrate de entenderlo. Si no, pregunta.

  2. Si estás de acuerdo, corrige en tu rama, en tu computadora:

git switch feature/formulario-contacto
# haces la corrección
git add archivo-corregido
git commit -m "Valida que la fecha no esté vacía"
git push

No tienes que abrir una Merge Request nueva. Al hacer push a la misma rama, la Merge Request se actualiza sola con tus nuevos commits.

  1. Responde en el hilo con algo breve: "Corregido en el último commit". Si el revisor usó una sugerencia, puedes aplicarla directamente con Apply suggestion.

  2. Si no estás de acuerdo, explica tu razón con respeto. Una buena discusión técnica es sana. Si no se ponen de acuerdo, pidan una tercera opinión.

  3. Marca el hilo como resuelto (Resolve thread) cuando quede atendido. Algunos equipos prefieren que lo resuelva quien hizo el comentario: sigue la costumbre del tuyo.

  4. Avisa que está listo para otra revisión. En GitLab puedes volver a solicitar la revisión con el ícono junto al nombre del revisor.

Paso 6: completar el merge

Cuando la Merge Request está lista, verás el botón Merge. GitLab puede exigir algunas condiciones antes de activarlo:

  • Las aprobaciones necesarias.

  • Todos los hilos de comentarios resueltos.

  • El pipeline en verde (capítulo 9).

  • Que no haya conflictos con main.

Si todo se cumple, pulsa Merge. Tus cambios entran a main.

Si GitLab dice que hay conflictos, tienes que resolverlos antes. El capítulo 6 te enseña cómo.

Paso 7: después del merge

Tu rama ya está en main, pero tu computadora todavía no lo sabe. Pon todo al día:

git switch main
git pull
git branch -d feature/formulario-contacto

Con el tiempo se acumulan en tu computadora referencias a ramas que ya se borraron en GitLab. Para limpiarlas:

git fetch --prune

Qué hace grande o pequeña a una buena Merge Request

Las Merge Requests pequeñas se revisan mejor y más rápido. Una de 50 líneas se revisa con atención en diez minutos. Una de 2,000 líneas casi nadie la revisa de verdad: se aprueba por cansancio.

  • Una Merge Request, una tarea. Igual que las ramas.

  • Si es grande, divídela. Varias Merge Requests pequeñas que se fusionan una tras otra.

  • Separa lo mecánico de lo importante. Si renombraste muchos archivos y además cambiaste la lógica, haz dos Merge Requests. Así quien revisa se concentra en lo que importa.

Capítulo 6. Conflictos: no borres el trabajo del otro

Un conflicto aparece cuando dos personas cambiaron la misma parte de un archivo y Git no puede decidir cuál versión es la correcta. No es un error ni una falla: es Git siendo honesto y pidiéndote ayuda. En este capítulo vas a perderles el miedo y a resolverlos sin borrar el trabajo de nadie.

Mi historia: el conflicto gigante

El peor conflicto que he vivido no fue por un cambio complicado. Fue por dejar dos ramas separadas durante semanas. Mientras yo avanzaba en la mía, main también seguía cambiando. Cuando por fin quise juntarlas, Git me marcó conflictos en archivo tras archivo.

Cada conflicto por separado era sencillo. El problema era la cantidad, y que ya no recordaba bien por qué había hecho cada cambio semanas atrás. Tardé mucho más en juntar las ramas que en hacer el trabajo original.

De ahí salió la regla que te di en el capítulo 4: ramas cortas, integra seguido. Un conflicto pequeño hoy se resuelve en cinco minutos. Veinte conflictos acumulados te pueden costar un día entero.

Lo que veo en otros: resolver borrando

Como instructora y en los equipos donde he trabajado, he visto muchas veces la misma escena. Aparece el conflicto, la persona se asusta y elige la salida más rápida: quedarse con su versión y descartar la otra sin leerla.

El conflicto desaparece de la pantalla. Git queda contento. Pero el cambio de un compañero acaba de perderse en silencio. Nadie se entera hasta días después, cuando algo que ya estaba corregido vuelve a fallar.

Por eso este capítulo tiene una regla de oro: un conflicto se resuelve entendiendo los dos cambios, no eligiendo el tuyo por defecto.

Por qué aparecen los conflictos

Git es muy bueno juntando cambios. Si Ana cambia la línea 10 de un archivo y Luis cambia la línea 50, Git junta las dos cosas sin preguntar. Si Ana cambia index.html y Luis cambia contacto.html, tampoco hay problema.

El conflicto aparece solo en estos casos:

SituaciónEjemplo
Dos personas cambian las mismas líneasAna pone el horario hasta las 5:00 y Luis hasta las 4:30
Una persona borra un archivo y otra lo modificaLuis eliminó antiguo.md y Ana le agregó un párrafo
Dos personas crean un archivo con el mismo nombreLos dos agregaron guia.md con contenido distinto

En todos esos casos hay dos decisiones humanas que chocan. Git no puede adivinar cuál es la buena, y hace bien en no adivinar.

Cuándo te puede aparecer un conflicto

  • Al hacer git pull, si alguien publicó cambios en las mismas líneas que tú.

  • Al hacer git merge main en tu rama, para ponerla al día.

  • En una Merge Request, cuando GitLab avisa que tu rama tiene conflictos con main y no deja fusionar.

En todos los casos se resuelve igual. Veamos cómo.

Cómo se ve un conflicto

Cuando hay conflicto, Git te avisa en la terminal:

Auto-merging contacto.md
CONFLICT (content): Merge conflict in contacto.md
Automatic merge failed; fix conflicts and then commit the result.

Y si miras el estado:

git status
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
        both modified:   contacto.md

both modified significa "los dos lados cambiaron este archivo". Ese es el que tienes que revisar.

Al abrir contacto.md verás algo así:

# Contacto

<<<<<<< HEAD
Horario: lunes a viernes, 8:00 a 5:00
=======
Horario: lunes a viernes, 8:00 a 4:30
>>>>>>> fix/horario-viernes

Teléfono: 500-0000

Esas marcas raras las puso Git para mostrarte los dos lados:

  • Entre <<<<<<< HEAD y ======= está tu versión, la de la rama donde estás.

  • Entre ======= y >>>>>>> fix/horario-viernes está la versión que estás trayendo, de la otra rama.

  • Todo lo que está fuera de las marcas (como el teléfono) no tiene conflicto.

Cómo resolverlo paso a paso

1. No entres en pánico, y no borres nada todavía

El conflicto no rompió nada. Tu trabajo y el de tu compañero están a salvo. Si necesitas salir y pensar, puedes cancelar todo y volver a como estaba antes:

git merge --abort

Es tu botón de emergencia. Úsalo sin culpa.

2. Entiende los dos cambios

Antes de tocar el archivo, pregúntate:

  • ¿Qué intentaba hacer mi cambio?

  • ¿Qué intentaba hacer el otro cambio?

  • ¿Son incompatibles, o se pueden combinar?

Para saber quién hizo el otro cambio y por qué:

git log --oneline main -- contacto.md

Lee el mensaje del commit. Si no te queda claro, pregúntale a esa persona. Un mensaje rápido de "Oye, los dos cambiamos el horario, ¿cuál es el correcto?" evita perder trabajo. Esta es la parte que más se salta, y la más importante.

3. Decide cómo debe quedar

Tienes cuatro opciones:

OpciónCuándoResultado en el ejemplo
Quedarte con tu versiónEl otro cambio quedó obsoleto, y lo confirmaste8:00 a 5:00
Quedarte con la otra versiónSu cambio es el correcto8:00 a 4:30
Conservar ambasLas dos líneas deben existirLas dos líneas, una debajo de otra
CombinarCada cambio tiene una parte correctaPor ejemplo: lunes a jueves 8:00 a 5:00, viernes 8:00 a 4:30

En la vida real, la opción correcta muchas veces es combinar. Rara vez uno de los dos cambios sobra por completo.

4. Edita el archivo y quita las marcas

Deja el texto exactamente como debe quedar y borra las tres marcas (<<<<<<<, ======= y >>>>>>>). Por ejemplo:

# Contacto

Horario: lunes a jueves 8:00 a 5:00, viernes 8:00 a 4:30

Teléfono: 500-0000

Un error muy común es olvidar alguna marca. Antes de seguir, busca <<<<<<< en el archivo. No debe quedar ninguna.

5. Marca el conflicto como resuelto y guarda

git add contacto.md
git status

Cuando git status ya no muestre archivos en conflicto:

git commit

Git abre el editor con un mensaje ya escrito, como Merge branch 'main' into fix/horario-viernes. Puedes dejarlo así o agregar una línea explicando cómo resolviste. Guarda y cierra. Luego haz git push.

6. Verifica que todo funciona

Resolver un conflicto es cambiar código. Abre el resultado, pruébalo y asegúrate de que hace lo que los dos cambios buscaban. Si el proyecto tiene pruebas automáticas, el pipeline te ayudará (capítulo 9).

Resolver conflictos en VS Code o Cursor

El editor hace todo esto más visual. Al abrir un archivo con conflicto verás los dos bloques coloreados y, encima, unos enlaces:

  • Accept Current Change: quedarte con tu versión.

  • Accept Incoming Change: quedarte con la versión que llega.

  • Accept Both Changes: conservar las dos.

  • Compare Changes: verlas lado a lado.

También puedes usar el botón Resolve in Merge Editor, que muestra tres paneles: tu versión, la que llega y el resultado final abajo. Puedes marcar casillas y editar el resultado a mano.

Cuidado: estos botones son cómodos, pero hacen fácil el error de "aceptar lo mío" sin leer. Lee los dos bloques antes de hacer clic. Cuando termines, guarda el archivo y sigue con git add y git commit, o usa los botones del panel de Git.

Resolver conflictos en GitLab

Si una Merge Request tiene conflictos sencillos, GitLab muestra un botón Resolve conflicts. Te deja elegir, bloque por bloque, entre tu versión (ours) y la otra (theirs), o editar el archivo directamente en el navegador.

Es útil para conflictos pequeños de texto. Para conflictos más grandes, o si necesitas probar el resultado, es mejor resolverlos en tu computadora:

git switch main
git pull
git switch tu-rama
git merge main
# resuelves los conflictos
git add archivos-resueltos
git commit
git push

Al hacer push, la Merge Request se actualiza y el aviso de conflicto desaparece.

Casos especiales

Un lado borró el archivo y el otro lo modificó. git status dirá deleted by them o deleted by us. Decide si el archivo debe existir. Si debe quedarse, usa git add archivo. Si debe borrarse, usa git rm archivo. Antes de borrarlo, revisa si el cambio del otro lado debía moverse a otro lugar.

Conflictos en archivos que no son de texto (imágenes, Word, PDF). Git no puede mostrarte las diferencias por dentro. Tienes que elegir una versión completa:

git checkout --ours logo.png     # Me quedo con mi versión
git checkout --theirs logo.png   # Me quedo con la otra
git add logo.png

Habla con la otra persona antes de elegir. Uno de los dos va a perder su versión.

Muchísimos conflictos a la vez. Si te pasa lo que me pasó a mí, no intentes resolver todo de un tirón. Haz git merge --abort y busca ayuda: la persona que hizo los otros cambios, o alguien con más experiencia. A veces conviene integrar los cambios por partes, o crear una rama nueva desde main actualizado y traer tus cambios poco a poco.

Cómo prevenir los conflictos

No puedes evitarlos todos, y no está mal que aparezcan. Pero puedes hacer que sean pocos y pequeños:

  • Ramas cortas. Días, no semanas.

  • Trae main a tu rama con frecuencia si tu trabajo se alarga.

  • git pull antes de empezar a trabajar cada día.

  • Commits y Merge Requests pequeños. Menos líneas tocadas, menos choques posibles.

  • Coordina con tu equipo. Si dos personas van a tocar el mismo archivo, que lo sepan. Una línea en el chat del equipo ahorra horas.

  • No reformatees archivos enteros (cambiar espacios, ordenar líneas) mezclado con cambios reales. Genera conflictos en todo el archivo. Si hace falta, hazlo en una Merge Request aparte.

Capítulo 7. Botiquín de emergencias: deshacer sin perder trabajo

Casi todo en Git se puede deshacer. La clave es saber qué quieres deshacer y si ya lo publicaste. Este capítulo te da los cuatro comandos para reparar errores (restore, revert, reset y stash), una red de seguridad para cuando todo parece perdido (reflog) y recetas listas para los accidentes más comunes.

Antes de tocar nada: las dos preguntas

Cuando algo sale mal, respira y respóndete:

1. ¿Dónde está el error?

  • En archivos que cambié pero no he guardado con commit.

  • En la caja (git add), pero sin commit.

  • En un commit que solo está en mi computadora.

  • En un commit que ya publiqué con push.

2. ¿Quiero perder ese cambio o conservarlo?

Con esas dos respuestas, eliges la herramienta. Este es el mapa:

Dónde está el errorHerramienta¿Pierdo el cambio?
Archivo modificado, sin addgit restore archivoSí, se descarta
En la caja, sin commitgit restore --staged archivoNo, solo sale de la caja
Commit local, sin pushgit resetDepende de la opción
Commit ya publicadogit revertNo, se crea un commit que lo anula
Trabajo a medias que quiero apartargit stashNo, queda guardado aparte

Y una regla que te salva de muchos problemas: lo que ya publicaste no se reescribe, se corrige con un commit nuevo.

git restore: descartar cambios que no has guardado

Editaste un archivo, hiciste un desastre y quieres volver a como estaba en el último commit:

git restore contacto.md

El archivo vuelve a su última versión guardada.

Advertencia: este comando descarta tus cambios para siempre. Como nunca hiciste commit, Git no tiene copia de ellos. Antes de usarlo, mira con git diff contacto.md qué vas a perder.

Para descartar los cambios de todos los archivos de la carpeta:

git restore .

Úsalo con todavía más cuidado. Revisa primero con git status.

Para sacar un archivo de la caja sin perder lo que cambiaste (lo viste en el capítulo 3):

git restore --staged contacto.md

Este es inofensivo: el cambio sigue en tu archivo, solo deja de estar preparado para el commit.

También puedes recuperar un archivo tal como estaba en un commit anterior:

git restore --source a3f9c21 contacto.md

El archivo queda como estaba en ese commit. Revisa, y si te sirve, haz un commit nuevo con esa versión.

git revert: deshacer un commit publicado

Ya hiciste push y descubres que un commit tiene un error. Tus compañeros ya lo descargaron. No puedes borrarlo de la historia sin causarles problemas. Lo correcto es crear un commit nuevo que haga lo contrario:

git log --oneline
git revert a3f9c21

Git crea un commit con un mensaje como Revert "Actualiza horario de atención". Si el commit original agregó una línea, el revert la quita. Si la quitó, el revert la vuelve a poner. Luego haces git push como siempre.

Por qué es la opción segura:

  • No borra historia. El commit con error sigue ahí, y también el que lo anuló. Cualquiera puede ver qué pasó.

  • No afecta a tus compañeros. Solo descargan un commit nuevo, como cualquier otro.

  • Se puede deshacer. Si te equivocaste al revertir, puedes revertir el revert.

En GitLab también puedes hacerlo con botones: abre el commit o la Merge Request ya fusionada y usa el botón Revert. GitLab te propone crear una Merge Request con la reversión.

git reset: rehacer commits que solo están en tu computadora

reset mueve tu rama hacia atrás, como si ciertos commits no se hubieran hecho. Es poderoso, y por eso tiene una regla estricta: úsalo solo con commits que no hayas publicado.

HEAD~1 significa "un commit antes del actual". HEAD~2, dos commits antes, y así.

Las tres formas de reset

Imagina que tu último commit se equivocó y quieres deshacerlo. ¿Qué pasa con los cambios que tenía?

OpciónEl commitLos cambiosCuándo usarla
--softSe deshaceQuedan en la caja, listos para otro commitQuiero rehacer el commit con otro mensaje o agregar algo
--mixed (por defecto)Se deshaceQuedan en tus archivos, fuera de la cajaQuiero reorganizar qué va en cada commit
--hardSe deshaceSe borranQuiero tirar todo ese trabajo

Ejemplos:

git reset --soft HEAD~1    # Deshace el commit, conserva todo en la caja
git reset HEAD~1           # Deshace el commit, conserva los cambios en tus archivos
git reset --hard HEAD~1    # Deshace el commit y BORRA sus cambios

Advertencia sobre --hard: borra cambios de tus archivos sin pedir confirmación. Antes de usarlo, ejecuta git status y git log --oneline y asegúrate de lo que vas a perder. Si dudas, usa --soft o --mixed: siempre puedes descartar después.

¿Y si ya hice push?

Si deshaces con reset un commit que ya estaba en GitLab, tu rama local y la de GitLab quedan distintas. Git rechazará tu push. Forzarlo (git push --force) reescribe la historia compartida y puede borrar trabajo de tus compañeros. En ramas protegidas, como main, GitLab ni siquiera lo permite.

Para commits publicados, usa revert. La única excepción razonable es tu propia rama, en la que nadie más trabaja, y aun así es mejor preguntarle al equipo.

revert, reset y restore: la diferencia en una frase

  • restore trabaja con archivos: los devuelve a una versión guardada.

  • reset trabaja con commits locales: mueve tu rama hacia atrás, como si no se hubieran hecho.

  • revert trabaja con commits publicados: crea un commit nuevo que anula a otro.

Si solo vas a recordar una cosa: ¿ya hiciste push? Entonces revert.

git stash: apartar trabajo a medias

Estás a mitad de algo, sin terminar, y necesitas cambiar de rama para atender una urgencia. No quieres hacer commit de algo incompleto. Para eso está el stash: un cajón donde guardas tus cambios temporalmente.

git stash push -m "Formulario a medias"

Tu carpeta queda limpia, como en el último commit. Ya puedes cambiar de rama tranquila o tranquilo.

Cuando vuelvas:

git stash list
stash@{0}: On feature/formulario: Formulario a medias

Para recuperar tus cambios:

git stash pop

pop saca los cambios del cajón y los aplica a tu carpeta. Otras opciones útiles:

ComandoQué hace
git stash applyAplica los cambios pero los deja también en el cajón, por si acaso
git stash dropBorra el último stash del cajón
git stash show -pMuestra qué cambios tiene guardados
git stash push -u -m "…"Incluye también archivos nuevos que Git aún no seguía

Tres consejos:

  • Ponle siempre un mensaje con -m. Con tres stashes sin nombre no sabrás cuál es cuál.

  • No lo uses como almacén. El stash es para minutos u horas, no para semanas. Si el trabajo va a durar, haz commit en una rama.

  • Recuerda en qué rama estabas. Puedes aplicar un stash en otra rama, pero normalmente quieres volver a la misma.

git reflog: la red de seguridad

Aquí está el secreto que tranquiliza a todo el mundo: Git anota cada movimiento que haces, incluso los que "borran" commits. Si hiciste un reset --hard del que te arrepientes, o borraste una rama con commits, casi siempre puedes recuperarlo.

git reflog
7b2e104 HEAD@{0}: reset: moving to HEAD~1
a3f9c21 HEAD@{1}: commit: Actualiza horario de atención
1c8d3aa HEAD@{2}: checkout: moving from main to feature/horario

Cada línea es un momento por el que pasó tu proyecto. Para volver a uno:

git switch -c rescate a3f9c21

Esto crea una rama nueva llamada rescate exactamente en el punto que querías recuperar. Revisa que todo esté ahí y luego decide qué hacer con ella.

Dos límites que debes conocer: el reflog solo existe en tu computadora, y guarda los movimientos durante un tiempo (normalmente varias semanas), no para siempre. Y no puede recuperar cambios que nunca guardaste con commit.

Recetas para los accidentes más comunes

"Hice commit en la rama equivocada" (sin push)

Hiciste commit en main cuando debía ir en una rama nueva:

git branch feature/mi-cambio      # Crea la rama apuntando a tu commit
git reset --hard HEAD~1           # Saca el commit de main
git switch feature/mi-cambio      # Tu commit está a salvo aquí

Si eran dos commits, usa HEAD~2. Revisa con git log --oneline antes del reset.

"Quiero cambiar el mensaje de mi último commit" (sin push)

git commit --amend -m "Mensaje correcto"

"Olvidé agregar un archivo al último commit" (sin push)

git add archivo-olvidado.md
git commit --amend --no-edit

--no-edit conserva el mismo mensaje.

"Quiero deshacer mi último commit pero conservar el trabajo" (sin push)

git reset --soft HEAD~1

"Un commit que ya publiqué rompió algo"

git revert código-del-commit
git push

"Quiero tirar todos mis cambios y quedar como en GitLab"

git fetch
git status                         # Mira qué vas a perder
git reset --hard origin/main       # Tu rama queda idéntica a la de GitLab

Si estás en otra rama, cambia main por su nombre. Todo lo que no estaba publicado se perderá.

"Borré una rama que tenía trabajo"

git reflog                         # Busca el último commit de esa rama
git switch -c nombre-rama código

"Hay archivos nuevos que no sé de dónde salieron y quiero borrarlos"

git clean -n      # Solo muestra qué borraría
git clean -f      # Los borra de verdad

Usa siempre -n primero. git clean borra archivos que Git no sigue, y no se pueden recuperar con reflog.

"Subí una contraseña o un token"

Esto no se arregla con ningún comando de esta lista. Aunque lo borres con un commit nuevo, sigue en la historia. Lo primero es cambiar esa contraseña o revocar el token de inmediato, y avisar a la persona responsable de seguridad. Lo vemos en detalle en el capítulo 10.

Comandos que piden respeto

Estos comandos pueden borrar trabajo. No están prohibidos, pero antes de usarlos detente y revisa con git status y git log:

ComandoQué puede borrar¿Se recupera con reflog?
git restore archivoCambios sin commitNo
git reset --hardCambios sin commit y commits localesLos commits sí; los cambios sin commit no

Ejemplo real: la tarde de los tres sustos

Luis tiene una tarde complicada:

  1. Hace commit en main en lugar de en su rama. No ha hecho push. Crea la rama con git branch, saca el commit de main con reset --hard HEAD~1 y sigue trabajando en su rama.

  2. Mientras trabaja, le piden revisar algo urgente en otra rama. Guarda su trabajo a medias con git stash push -m "Ajustes del reporte", cambia de rama, atiende la urgencia, vuelve y recupera todo con git stash pop.

  3. Al final del día descubre que un commit que publicó en la mañana rompió el cálculo de totales. Como ya está en GitLab, no usa reset: hace git revert, push, y avisa al equipo.

Tres sustos, cero trabajo perdido, y un historial que cuenta exactamente qué pasó.

Ejercicio práctico: rompe cosas a propósito

En tu proyecto practica-git, en una rama nueva llamada practica/botiquin:

  1. Restore. Modifica README.md, mira el cambio con git diff y descártalo con git restore README.md.

  2. Restore --staged. Modifica un archivo, agrégalo con git add y sácalo de la caja con git restore --staged. Comprueba que el cambio sigue en el archivo.

  3. Reset --soft. Haz un commit con un mensaje feo. Deshazlo con git reset --soft HEAD~1 y vuelve a hacerlo con un buen mensaje.

  4. Stash. Haz un cambio sin commit, guárdalo con git stash push -m "prueba", cambia a main, vuelve y recupéralo con git stash pop.

  5. Revert. Haz un commit, publícalo con push y luego anúlalo con git revert. Mira los dos commits en GitLab.

  6. Reflog. Haz un commit, bórralo con git reset --hard HEAD~1 y recupéralo con git reflog y git switch -c rescate código.

  7. Rama equivocada. En main de tu proyecto de práctica, haz un commit sin push y muévelo a una rama nueva con la receta de este capítulo.

Anota en una hoja qué comando usaste en cada caso y por qué. Esa hoja es tu botiquín personal.

Capítulo 8. Organiza el trabajo en GitLab

GitLab no solo guarda código: también es el lugar donde el equipo decide qué hacer, quién lo hace y para cuándo. Con issues, etiquetas, milestones, tableros y la wiki, todo el trabajo queda conectado: desde la tarea hasta el commit que la resolvió. En este capítulo aprenderás a usar esas herramientas.

El problema de organizarse por chat y correo

Sin un lugar central, las tareas viven en mensajes sueltos: "¿alguien vio lo del formulario?", "creo que Luis lo iba a hacer", "¿eso ya se arregló?". Las preguntas se repiten, las tareas se pierden y nadie sabe qué está pendiente.

Con GitLab, cada tarea tiene una ficha propia, un responsable y un estado. Y cada cambio en el código se puede enlazar con la tarea que lo pidió. Seis meses después, cualquiera puede ver por qué existe un cambio y qué discusión hubo antes.

Issues: una ficha para cada tarea

Un issue es una ficha de trabajo. Puede ser un error que corregir, una función nueva, una mejora, una duda o una tarea de documentación. Se crea en Plan > Issues > New issue.

Las partes de un issue

CampoPara qué sirve
TítuloQué hay que hacer, en una línea
DescripciónEl detalle: contexto, pasos, criterios para darlo por terminado
AssigneeQuién es responsable
LabelsEtiquetas para clasificar: tipo, prioridad, área
MilestoneA qué entrega o ciclo pertenece
Due dateFecha límite
ComentariosLa conversación sobre la tarea

Cada issue recibe un número automático, como #42. Ese número es su identidad: lo usarás para enlazarlo desde commits, ramas y Merge Requests.

Cómo escribir un buen issue

Un buen issue lo puede tomar otra persona sin tener que preguntarte nada. Para reportar un error, usa esta estructura:

## Qué pasa
Al enviar el formulario de contacto sin fecha, aparece una página en blanco.

## Pasos para reproducirlo
1. Ir a la página de contacto.
2. Llenar nombre y correo, dejar la fecha vacía.
3. Pulsar Enviar.

## Qué debería pasar
Debería aparecer el mensaje "La fecha es obligatoria".

## Dónde
Navegador Chrome, versión de producción del 8 de octubre.

## Capturas
(adjuntar)

Para pedir algo nuevo:

## Qué se necesita
Un filtro por fecha en la búsqueda de documentos.

## Para qué
Los usuarios tardan mucho en encontrar documentos del mes actual.

## Cuándo lo damos por terminado
- [ ] Se puede elegir fecha de inicio y fin.
- [ ] Si no se elige fecha, se muestran todos.
- [ ] Funciona en celular.

Esa última sección, la de cuándo lo damos por terminado, es la más valiosa. Evita la discusión de "yo pensé que también incluía…". Las casillas - [ ] se pueden marcar directamente en GitLab a medida que avanzas.

Plantillas para no empezar de cero

Si tu equipo siempre usa la misma estructura, guárdala como plantilla. Crea en el repositorio la carpeta .gitlab/issue_templates/ y dentro un archivo por plantilla, por ejemplo Error.md y Funcion-nueva.md. Al crear un issue, GitLab te deja elegirla en un menú. Lo mismo funciona para Merge Requests en .gitlab/merge_request_templates/.

Trabajar en un issue

  • Asígnatelo antes de empezar, para que nadie haga lo mismo en paralelo.

  • Comenta los avances y las dudas en el issue, no por chat. Así queda registro para quien llegue después.

  • Menciona a personas con @usuario cuando necesites su opinión.

  • Ciérralo cuando esté terminado, o deja que se cierre solo con la Merge Request (lo vemos abajo).

Etiquetas: clasificar para encontrar

Las etiquetas (labels) son marcas de colores que pones a issues y Merge Requests para clasificarlos y filtrarlos. Se crean en Manage > Labels.

Un conjunto sencillo que funciona en muchos equipos:

GrupoEtiquetas
Tipoerror, función nueva, mejora, documentación
Prioridadprioridad alta, prioridad media, prioridad baja
Estadopor hacer, en progreso, en revisión, bloqueado
Áreaformulario, reportes, base de datos, servidor

Consejos:

  • Pocas y claras. Con cien etiquetas nadie sabe cuál usar.

  • Un color por grupo. Por ejemplo, rojos para prioridad y azules para tipo. Se leen de un vistazo.

  • Escribe la descripción de cada etiqueta, para que todos la usen igual.

  • Acuérdenlas en equipo. Las etiquetas solo sirven si todos las aplican con el mismo criterio.

Con etiquetas puedes filtrar la lista de issues y responder preguntas como "¿qué errores de prioridad alta siguen abiertos?" en dos clics.

Conectar commits, ramas y Merge Requests con un issue

Aquí está la magia: GitLab enlaza todo automáticamente si mencionas el número del issue.

En el nombre de la rama. Incluye el número, como viste en el capítulo 4: fix/42-fecha-vacia-formulario.

En el mensaje del commit. Agrega la referencia:

git commit -m "Valida fecha obligatoria en formulario de contacto (#42)"

El commit aparecerá mencionado dentro del issue 42.

En la descripción de la Merge Request. Usa una palabra de cierre:

Closes #42

Cuando la Merge Request se fusione en la rama principal, GitLab cerrará el issue 42 automáticamente. También funcionan Fixes #42 y Resolves #42. Si solo quieres enlazarlo sin cerrarlo, escribe Related to #42 o simplemente #42.

El atajo más cómodo: crear la rama desde el issue. Dentro de un issue verás el botón Create merge request (o Create branch). GitLab crea una rama con el número y el título del issue, y una Merge Request en borrador ya enlazada. Solo tienes que traerla a tu computadora:

git fetch
git switch 42-fecha-vacia-formulario

El resultado es una cadena completa y rastreable: issue → rama → commits → Merge Request → issue cerrado.

Milestones: agrupar trabajo por entregas

Un milestone es un objetivo con fecha: una versión, un ciclo de dos semanas o una entrega a un cliente. Agrupa los issues y Merge Requests que deben estar listos para esa fecha. Se crea en Plan > Milestones.

Ejemplos:

  • Versión 1.5 — del 1 al 15 de noviembre.

  • Sprint 23 — dos semanas de trabajo.

  • Entrega del módulo de reportes — para la fecha acordada con el área usuaria.

Al abrir un milestone, GitLab muestra una barra de progreso: cuántos issues están cerrados y cuántos faltan. Es la forma más rápida de responder a la pregunta "¿vamos a llegar a la fecha?".

Consejo: si un milestone tiene demasiados issues abiertos cerca de su fecha, es mejor mover algunos al siguiente de forma consciente que fingir que todo se va a lograr.

Tableros: ver el trabajo de un vistazo

Un tablero (board) muestra los issues como tarjetas en columnas, al estilo Kanban. Lo encuentras en Plan > Issue boards.

Por defecto tiene dos columnas, Open y Closed. Puedes agregar columnas basadas en etiquetas. Un tablero típico:

Por hacerEn progresoEn revisiónCerrado
#45 Filtro por fecha#42 Fecha vacía en formulario#40 Teléfono en pie de página#38 Logo nuevo
#47 Exportar a Excel

Al arrastrar una tarjeta de una columna a otra, GitLab le cambia la etiqueta automáticamente. Si la arrastras a Cerrado, el issue se cierra.

Cómo usarlo bien:

  • Revísenlo juntos en la reunión del equipo, en vez de preguntar uno por uno "¿cómo vas?".

  • Limita lo que está "en progreso". Si una persona tiene seis tarjetas en esa columna, algo no está funcionando.

  • Mantenlo al día. Un tablero desactualizado es peor que no tener tablero, porque engaña.

  • Filtra. Puedes ver el tablero de un solo milestone, una sola persona o una sola etiqueta.

La wiki: la memoria del proyecto

La wiki es un espacio de documentación dentro del proyecto, con páginas escritas en Markdown (capítulo 13). Está en Plan > Wiki.

Qué suele ir en la wiki:

  • Guías de uso para las personas usuarias.

  • Procedimientos del equipo: cómo publicar una versión, cómo atender una emergencia.

  • Decisiones importantes y sus razones.

  • Glosario del proyecto y contactos.

  • Actas o resúmenes de reuniones técnicas.

Crear una página es sencillo: New page, escribes el título, el contenido en Markdown y guardas. Para enlazar otra página de la wiki, usa [texto](nombre-de-la-pagina). Las páginas con un nombre como guias/instalacion quedan organizadas en carpetas.

Un dato útil: la wiki es, por dentro, otro repositorio de Git. Tiene historial de cambios, y puedes clonarla y editarla en tu computadora. La dirección para clonarla aparece en la propia wiki.

¿Wiki o carpeta docs/ en el repositorio?

Muchos equipos usan las dos: la wiki para lo general y docs/ para lo que debe estar sincronizado con cada versión del sistema.

Nota sobre versiones de GitLab. Algunas funciones avanzadas de organización (como varios tableros por proyecto, pesos de issues o épicas) dependen del plan de GitLab que use tu organización. Todo lo de este capítulo funciona en la versión gratuita, aunque los menús pueden variar un poco.

En GitHub se llama… Issues y etiquetas existen igual. Los milestones también. Los tableros se llaman Projects. La wiki está en la pestaña Wiki. Para cerrar issues desde una Pull Request se usan las mismas palabras: Closes #42.

Ejemplo real: del reporte al cierre

Una usuaria reporta por correo que el formulario muestra una página en blanco. Ana no lo deja en el correo: crea el issue #42 Página en blanco al enviar formulario sin fecha, con los pasos para reproducirlo, las etiquetas error y prioridad alta, y lo asigna al milestone Versión 1.5.

Luis se lo asigna y lo mueve a En progreso en el tablero. Desde el issue pulsa Create merge request, trae la rama a su computadora, corrige y hace commit con (#42) en el mensaje. La Merge Request ya dice Closes #42.

Ana revisa, aprueba y Luis fusiona. El issue se cierra solo y la tarjeta pasa a Cerrado. Al día siguiente, Ana responde a la usuaria con el enlace al issue. Si alguien pregunta en seis meses por qué existe esa validación, todo está ahí: el reporte, la discusión, el cambio y la revisión.

Capítulo 9. CI/CD: aprende a leer el semáforo

CI/CD es un conjunto de revisiones y tareas automáticas que GitLab ejecuta cada vez que publicas cambios. Su resultado es un semáforo: verde si todo pasó, rojo si algo falló. En este libro no vamos a configurar ni crear pipelines. El objetivo de este capítulo es que entiendas qué son, que sepas leer su resultado y que sepas qué hacer cuando algo sale en rojo.

Aclaración importante. Configurar CI/CD es un tema completo por sí mismo y normalmente lo hace una persona con experiencia en infraestructura. Aquí aprenderás a reconocerlo y leerlo, que es lo que necesitas para trabajar en un equipo que ya lo usa. No vas a modificar archivos de configuración de pipelines en ningún ejercicio.

Qué significa CI/CD

Son dos ideas relacionadas:

CI: integración continua (Continuous Integration). Cada vez que alguien publica cambios, un sistema automático revisa que el proyecto siga funcionando: que se pueda construir, que pasen las pruebas, que el código cumpla las reglas del equipo. La idea es detectar errores en minutos, no días después.

CD: entrega o despliegue continuo (Continuous Delivery / Deployment). Cuando los cambios pasan las revisiones, el sistema prepara automáticamente una versión lista para publicar (entrega continua) o incluso la publica en el servidor (despliegue continuo).

Qué haceQuién decide publicar
Integración continuaRevisa cada cambio automáticamenteNadie publica todavía
Entrega continuaDeja una versión lista para publicarUna persona pulsa el botón
Despliegue continuoPublica automáticamenteNadie: si todo pasa, se publica solo

Una comparación: el control de calidad

Piensa en una fábrica de pan. Antes de que una bandeja salga a la tienda, pasa por varias estaciones: se revisa la masa, se hornea, se mide la temperatura, se empaca y se etiqueta. Si una estación detecta un problema, la bandeja no sigue avanzando.

Un pipeline hace lo mismo con tu código. Cada estación es una revisión automática. Si una falla, se detiene y te avisa. Así los errores se quedan en la fábrica y no llegan a las personas usuarias.

Para qué sirven los pipelines

Un pipeline es la lista de tareas automáticas que se ejecutan con tus cambios. Las tareas más comunes:

  • Construir el proyecto, para comprobar que no quedó nada roto.

  • Ejecutar pruebas automáticas, que verifican que lo que funcionaba siga funcionando.

  • Revisar el estilo del código, según las reglas del equipo.

  • Buscar problemas de seguridad, como contraseñas olvidadas en el código o librerías con fallas conocidas.

  • Publicar en un servidor de prueba o de producción.

El beneficio para ti: no tienes que acordarte de revisar todo a mano antes de cada Merge Request. Y el equipo tiene una garantía mínima de que lo que entra a main funciona.

Cómo está armado un pipeline

Un pipeline se organiza en etapas (stages), y cada etapa tiene uno o más trabajos (jobs):

Etapa: construir   →   Etapa: probar        →   Etapa: publicar
  [compilar]            [pruebas unitarias]       [desplegar a pruebas]
                        [revisión de estilo]

  • Las etapas se ejecutan en orden: si "probar" falla, "publicar" no se ejecuta.

  • Los trabajos de una misma etapa suelen ejecutarse al mismo tiempo.

Los trabajos los ejecutan unas máquinas llamadas runners. No necesitas saber más de ellas por ahora: solo que son las "estaciones" donde se hace el trabajo.

Dónde vive la configuración

Todo esto se define en un archivo llamado .gitlab-ci.yml, en la raíz del repositorio. Si un proyecto tiene ese archivo, tiene pipelines.

Solo para que lo reconozcas si lo ves, un ejemplo muy simple:

stages:
  - probar

pruebas:
  stage: probar
  script:
    - echo "Ejecutando pruebas"

No necesitas entenderlo ni modificarlo. Si alguna vez una Merge Request tuya cambia ese archivo sin querer, avísale a la persona responsable antes de fusionar.

Dónde ver el resultado

GitLab te muestra el estado del pipeline en varios lugares:

  1. En la Merge Request. Debajo de la descripción aparece un recuadro con el estado del pipeline. Es el lugar donde más lo vas a mirar.

  2. En la lista de commits. Cada commit muestra un ícono pequeño con su estado.

  3. En el menú Build > Pipelines. La lista completa de todos los pipelines del proyecto, con fecha, rama, autor y duración.

  4. En la página principal del proyecto, junto al último commit.

Al hacer clic en un pipeline, verás un diagrama con sus etapas y trabajos, cada uno con su propio ícono de estado.

Cómo reconocer si un pipeline pasó o falló

Ícono y estadoSignificadoQué hacer
Verde, passedTodo pasóPuedes seguir con la revisión y el merge
Rojo, failedAl menos un trabajo fallóNo fusionar. Revisar qué falló
Azul, runningSe está ejecutandoEsperar
Gris, pending / createdEn espera de un runner libreEsperar. Si tarda mucho, avisar
Naranja, warningFalló un trabajo marcado como "puede fallar"Revisar, aunque no bloquea
Gris tachado, canceledAlguien lo cancelóVolver a ejecutarlo si hace falta
skippedNo se ejecutó porque una etapa anterior fallóArreglar la etapa que falló
manual (ícono de engranaje o play)Espera que una persona lo activeSolo lo activa quien tiene esa responsabilidad

Si el proyecto está configurado así, GitLab no deja fusionar una Merge Request con el pipeline en rojo. Es una protección, no un obstáculo.

Qué hacer cuando un pipeline falla

Un pipeline en rojo no es un regaño: es información. Este es el proceso:

1. Identifica qué trabajo falló. Abre el pipeline y busca el trabajo con la X roja.

2. Lee el registro. Haz clic en el trabajo para ver su registro (log): todo lo que la máquina escribió mientras trabajaba. El error casi siempre está al final. Baja hasta las últimas líneas y busca palabras como Error, FAILED o failed, generalmente en rojo.

3. Relaciónalo con tu cambio. Pregúntate: ¿qué cambié que pudo causar esto? Muchas veces el mensaje menciona un archivo o una prueba concreta.

4. Corrige en tu rama. Haz el arreglo, commit y push. El pipeline se ejecuta de nuevo automáticamente.

5. Si no tiene relación con tu cambio, puede ser un fallo pasajero (por ejemplo, un problema de red del runner). Puedes reintentar el trabajo con el botón Retry. Si vuelve a fallar igual, no es pasajero.

6. Si no entiendes el error, pregunta. Escribe en la Merge Request con el enlace al trabajo fallido y menciona a la persona responsable del pipeline. Copiar las últimas líneas del registro en tu mensaje ayuda mucho.

Lo que nunca debes hacer

  • Fusionar con el pipeline en rojo "porque seguro no es nada".

  • Borrar o desactivar una prueba para que el pipeline pase.

  • Modificar .gitlab-ci.yml para saltarte una revisión.

  • Darle Retry muchas veces esperando que pase por suerte.

Todas estas acciones esconden el problema en vez de resolverlo, y el problema termina llegando a producción.

Qué significa un pipeline verde (y qué no)

Un pipeline verde significa que las revisiones que existen pasaron. No significa que el cambio sea perfecto. Si el proyecto no tiene pruebas para cierta parte, un error ahí no lo va a detectar nadie.

Por eso el pipeline no reemplaza la revisión humana del capítulo 5. Son complementarios: la máquina revisa lo repetitivo y medible; las personas revisan la lógica, la claridad y si el cambio realmente resuelve lo que se pidió.

En GitHub se llama… GitHub Actions. La configuración vive en la carpeta .github/workflows/. El semáforo funciona igual: un check verde o una X roja junto a cada commit y en cada Pull Request.

Ejemplo real: el rojo que salvó una publicación

Luis abre una Merge Request que cambia el formato de las fechas en un reporte. A los pocos minutos, el pipeline sale en rojo.

Abre el trabajo pruebas y baja al final del registro. Ve que una prueba llamada "reporte mensual muestra totales correctos" falló: el cambio de formato rompió la forma en que el reporte agrupaba los meses. Luis no lo habría notado probando a mano, porque solo revisó la pantalla del reporte diario.

Corrige, hace push, y el pipeline pasa a verde. Ana revisa la lógica y aprueba. El error nunca llegó a las personas que usan el reporte.

  8. Escribe un mensaje de práctica (sin publicarlo) como si pidieras ayuda por un pipeline fallido: qué trabajo falló, el enlace y las líneas del error.

  • Puedo explicar qué es integración continua y qué es entrega o despliegue continuo.

  • Sé qué es un pipeline, una etapa y un trabajo.

  • Sé que la configuración vive en .gitlab-ci.yml y que no debo modificarla sin la persona responsable.

  • Encuentro el estado del pipeline en la Merge Request, en los commits y en Build > Pipelines.

  • Reconozco los estados: passed, failed, running, pending, skipped, canceled y manual.

  • Sé leer el registro de un trabajo fallido empezando por el final.

  • Sé qué hacer cuando falla: corregir, reintentar si es pasajero o pedir ayuda.

  • Nunca fusiono en rojo ni desactivo pruebas para pasar.

  • Entiendo que un pipeline verde no reemplaza la revisión humana.

  • Tengo claro que en este libro no configuramos pipelines.

Capítulo 10. Seguridad y buenas prácticas

Un repositorio guarda mucho más que código: guarda el trabajo de todo un equipo y, a veces, la puerta de entrada a sistemas importantes. Este capítulo cubre las cinco protecciones que todo equipo debería tener: permisos bien dados, ramas protegidas, secretos fuera del repositorio, cuentas seguras y una revisión antes de fusionar o publicar.

Por qué la seguridad empieza en Git

Tres situaciones reales que se repiten en muchas organizaciones:

  • Alguien sube por error un archivo con la contraseña de la base de datos. El repositorio es interno, pero lo pueden ver decenas de personas, y cualquier copia clonada la conserva.

  • Una persona que ya no trabaja en la organización sigue teniendo acceso al proyecto meses después.

  • Un cambio sin revisar se fusiona directo en main y se publica, con un error que deja fuera de servicio a los usuarios.

Ninguna requiere un ataque sofisticado. Todas se evitan con configuración básica y buenos hábitos.

Roles y permisos

En GitLab, cada persona que participa en un proyecto tiene un rol. El rol decide qué puede ver y qué puede hacer. Se administran en Manage > Members.

RolQué puede hacer, en resumenPara quién
GuestVer el proyecto (según su visibilidad) y crear issuesPersonas usuarias que reportan errores
ReporterLeer el código, comentar, gestionar issuesAnalistas, jefaturas que siguen el avance
DeveloperCrear ramas, hacer push, abrir Merge RequestsEl equipo que desarrolla
MaintainerFusionar en ramas protegidas, configurar el proyectoLíderes técnicos, responsables del proyecto
OwnerControl total, incluido borrar el proyectoMuy pocas personas

Los nombres y detalles exactos pueden variar según la versión de GitLab de tu organización, que incluso puede tener algún rol adicional. La idea es la misma en todas.

El principio del menor privilegio

Cada persona debe tener el rol mínimo que necesita para su trabajo, y nada más. No porque desconfíes de nadie, sino porque reduce el daño posible de un error o de una cuenta robada.

Buenas prácticas con los permisos:

  • No des Maintainer "por si acaso". Empieza con Developer y sube el rol cuando haga falta.

  • Usa fechas de vencimiento para accesos temporales: consultores, practicantes, apoyos puntuales. GitLab permite poner una fecha en la que el acceso se retira solo.

  • Revisa la lista de miembros periódicamente, por ejemplo cada tres meses. Quita a quien ya no participa.

  • Retira el acceso el mismo día en que alguien sale de la organización o del proyecto.

  • Usa grupos cuando hay varios proyectos con el mismo equipo. Así gestionas los permisos en un solo lugar.

  • Nunca compartas cuentas. Cada persona usa la suya. Si no, el historial pierde sentido: no sabes quién hizo qué.

Ramas protegidas

Una rama protegida tiene reglas especiales sobre quién puede cambiarla y cómo. Se configura en Settings > Repository > Protected branches. En la mayoría de proyectos, main viene protegida por defecto.

Lo que puedes definir:

OpciónQué controlaConfiguración recomendada para main
Allowed to mergeQuién puede fusionar Merge RequestsMaintainers
Allowed to push and mergeQuién puede hacer push directoNadie (No one)
Allowed to force pushSi se puede reescribir la historiaDesactivado

Con esa configuración, la única forma de cambiar main es con una Merge Request que alguien con permiso fusiona. Es exactamente el flujo de los capítulos 4 y 5, pero ahora es obligatorio, no solo una buena intención.

Otras protecciones que conviene conocer:

  • Aprobaciones obligatorias. Exigir que una o más personas aprueben antes de fusionar. Según el plan de GitLab de tu organización, puede ser obligatorio o solo informativo.

  • Pipeline exitoso para fusionar. En Settings > Merge requests, la opción Pipelines must succeed impide fusionar en rojo (capítulo 9).

  • Todos los hilos resueltos. La opción All threads must be resolved impide fusionar con comentarios pendientes.

  • Etiquetas protegidas. Igual que con las ramas, puedes proteger las etiquetas de versión (v*) para que solo ciertas personas las creen (capítulo 13).

Si intentas hacer push directo a una rama protegida, verás un error como You are not allowed to push code to protected branches. No es una falla: es la protección funcionando. Crea una rama y abre una Merge Request.

Nunca guardes secretos en el repositorio

Un secreto es cualquier dato que da acceso a algo:

  • Contraseñas de bases de datos, servidores o servicios.

  • Tokens y claves de API.

  • Llaves privadas SSH o certificados.

  • Credenciales de correo o de servicios en la nube.

  • Cadenas de conexión que incluyen usuario y contraseña.

Por qué es tan grave

Recuerda que Git guarda toda la historia. Si subes una contraseña y en el siguiente commit la borras, la contraseña sigue ahí, en el commit anterior. Cualquiera que tenga una copia del repositorio la puede encontrar con git log -S (capítulo 12).

Además:

  • Cada persona que clonó el proyecto tiene una copia de esa historia.

  • Los forks también la tienen.

  • En repositorios públicos existen programas automáticos que buscan secretos expuestos en internet constantemente. Una clave publicada puede ser usada por terceros en muy poco tiempo.

Cómo mantenerlos fuera

1. Usa variables de entorno y un archivo .env ignorado. Los secretos van en un archivo local, por ejemplo .env, que nunca entra al repositorio:

# .env  (NO se sube)
DB_PASSWORD=la-contraseña-real
API_TOKEN=el-token-real

Y en .gitignore:

.env
*.pem
*.key

2. Sube una plantilla sin valores reales. Crea un .env.example con los nombres de las variables y valores de ejemplo, para que el equipo sepa qué configurar:

# .env.example  (SÍ se sube)
DB_PASSWORD=escribe-aqui-la-contraseña
API_TOKEN=escribe-aqui-el-token

3. Para los pipelines, usa las variables de GitLab. Los secretos que necesita el CI/CD se guardan en Settings > CI/CD > Variables, marcadas como Masked (ocultas en los registros) y Protected (solo disponibles en ramas protegidas). Normalmente lo configura la persona responsable de los pipelines.

4. Revisa antes de cada commit. Aquí vuelve la regla del capítulo 3: mira antes de guardar. Un git status y un git diff --staged detectan la mayoría de los accidentes. Desconfía de cualquier archivo que no esperabas ver.

5. Activa detección automática si tu equipo puede. Hay herramientas que revisan cada commit en busca de secretos antes de que entren: el análisis de detección de secretos de GitLab en los pipelines, o programas que se ejecutan en tu computadora antes de cada commit (los llamados pre-commit hooks). Pregunta si tu equipo usa alguna.

Si subiste un secreto: qué hacer, en este orden

  1. Cambia o revoca el secreto de inmediato. Cambia la contraseña, revoca el token, genera una llave nueva. Este paso es el único que realmente te protege. Hazlo aunque el repositorio sea privado, y aunque creas que nadie lo vio.

  2. Avisa a la persona responsable de seguridad o a tu jefatura técnica. Sin vergüenza: es un accidente común, y avisar rápido es lo profesional.

  3. Revisa si el secreto fue usado, con ayuda de quien administra ese sistema (registros de acceso, actividad inusual).

  4. Quita el secreto del código con un commit nuevo y mueve el valor a .env o a las variables de GitLab.

  5. Limpiar la historia (borrar el secreto de todos los commits viejos) es posible con herramientas especializadas, pero reescribe la historia de todo el equipo. Hazlo solo con acompañamiento de alguien con experiencia, y recuerda que no reemplaza el paso 1.

Protege tu cuenta

Tu cuenta de GitLab es la llave de todos los proyectos donde participas:

  • Activa la verificación en dos pasos (2FA) en tu perfil, en Preferences > Account. Si alguien obtiene tu contraseña, igual no podrá entrar.

  • Tokens con vencimiento y con los permisos mínimos (capítulo 2). Borra los que ya no uses.

  • Pon una frase de seguridad a tu llave SSH y nunca compartas la llave privada.

  • Bloquea tu computadora cuando te alejes. Una sesión abierta es una cuenta abierta.

  • Desconfía de correos que piden tus credenciales, aunque parezcan de GitLab. Entra siempre escribiendo la dirección tú misma o tú mismo.

Qué revisar antes de fusionar

Sea que fusiones tu propia Merge Request o la de otra persona:

  • La rama origen y la rama destino son las correctas.

  • La descripción explica qué cambia y por qué.

  • Revisé todos los archivos en la pestaña Changes.

  • No hay secretos, archivos .env, llaves ni datos personales.

  • No hay archivos ajenos a la tarea, temporales o de prueba.

  • No hay marcas de conflicto <<<<<<< olvidadas.

  • El pipeline está en verde.

  • Todos los comentarios están atendidos y los hilos resueltos.

  • Tiene las aprobaciones necesarias.

  • No modifica .gitlab-ci.yml ni configuraciones sensibles sin que lo sepa la persona responsable.

Qué revisar antes de desplegar

Publicar en producción es el momento de mayor riesgo. Aunque normalmente lo haga una persona designada, conviene que todo el equipo conozca la lista:

  • Todo lo que se va a publicar está fusionado en la rama correcta y con pipeline en verde.

  • Existe una etiqueta de versión y sus notas (capítulo 13).

  • Se sabe exactamente qué cambios entran, comparando con la versión anterior (capítulo 12).

  • Hay un plan para volver atrás si algo falla: qué versión restaurar y cómo.

  • Si hay cambios en la base de datos, existe un respaldo reciente.

  • Se eligió un horario de bajo uso y las personas usuarias están avisadas si habrá interrupción.

  • Hay alguien disponible para revisar que todo funcione después de publicar.

  • No se publica un viernes por la tarde, salvo emergencias. Si algo falla, nadie quiere arreglarlo el fin de semana.

Buenas prácticas de trabajo en equipo

La seguridad técnica sirve de poco si el equipo no tiene acuerdos claros. Estas prácticas resumen el libro:

  1. Nadie trabaja directo en main. Ramas para todo.

  2. Ramas cortas. Días, no semanas.

  3. Commits pequeños, con mensajes claros. Un commit, una idea.

  4. git pull al empezar el día y antes de crear una rama.

  5. Todo cambio pasa por Merge Request y revisión. Incluidos los urgentes.

  6. Cada tarea tiene su issue. Las conversaciones importantes, ahí, no en el chat.

  7. Mira antes de guardar y antes de fusionar.

  8. Comentarios sobre el código, no sobre la persona.

  9. Conflictos: entender los dos lados. Nunca borrar el trabajo del otro.

  10. Lo publicado no se reescribe. Se corrige con un commit nuevo.

  11. Los secretos nunca entran al repositorio. Y si entran, se cambian de inmediato.

  12. Documenten sus acuerdos en la wiki: convenciones de ramas, de commits, de etiquetas, y a quién preguntar.

Esta última es clave. Un equipo nuevo no necesita adivinar sus reglas si están escritas.

Ejemplo real: la contraseña que se subió un lunes

Luis está configurando la conexión a la base de datos de pruebas y, con prisa, hace commit del archivo config.py con la contraseña escrita. Hace push a su rama y abre una Merge Request.

Ana revisa la pestaña Changes y ve la contraseña. No aprueba. Le escribe a Luis por privado y él actúa en orden: le pide al administrador de la base de datos cambiar la contraseña de inmediato, avisa a la jefatura técnica, mueve la configuración a variables de entorno con un .env ignorado y un .env.example, y hace un commit nuevo.

Como la rama solo existía en el proyecto interno y la contraseña ya se cambió, el equipo decide con la jefatura cómo limpiar la historia de esa rama. El incidente quedó resuelto en una hora. Al día siguiente, el equipo agrega la detección automática de secretos a su lista de mejoras y la regla del .env a la wiki.

Capítulo 11. Git con un agente: tú decides, la IA ejecuta

Un agente de inteligencia artificial o un script pueden hacer por ti las partes repetitivas de Git: traer cambios, preparar commits, publicarlos y abrir Merge Requests. Bien usado, te ahorra tiempo y errores. Mal usado, puede publicar algo que nadie revisó. La regla de este capítulo es la del título: la automatización ejecuta, pero las decisiones las tomas tú.

Mi flujo de trabajo

Yo trabajo así todos los días: uso Claude para planear el cambio, Cursor para ejecutarlo en el código, y reviso cada commit antes de hacer push. La IA propone y escribe. Yo leo, entiendo, corrijo y decido qué se publica.

Ese último paso no es opcional. Un agente puede escribir código que parece correcto y no lo es, tocar archivos que no le pediste o resolver un problema de una forma que no encaja con el resto del proyecto. Si publicas sin mirar, el responsable del cambio sigues siendo tú, no la herramienta.

Por eso este capítulo está al final del libro, y no al principio. Para supervisar a un agente necesitas entender todo lo anterior: qué hace cada comando, cómo leer un diff, cuándo hay un conflicto y cómo deshacer un error.

Las cinco reglas de una automatización segura

1. Validar antes de actuar

Antes de cualquier comando, la automatización comprueba:

  • Que está dentro de un repositorio Git.

  • En qué rama está, y que no es main ni otra rama protegida.

  • Que no hay un merge o conflicto a medias.

  • Qué archivos cambiaron y si hay alguno sospechoso (.env, llaves, archivos enormes).

Si algo no cuadra, se detiene y avisa. Nunca "lo arregla" sola.

2. Vista previa y confirmación

Antes de hacer commit, push o abrir una Merge Request, la automatización te muestra exactamente qué va a hacer:

  • La lista de archivos y el diff.

  • El mensaje del commit propuesto.

  • La rama a la que va a publicar.

Y espera que confirmes de forma explícita. Un "sí" escrito por ti, no un "continuar automáticamente".

3. Revisión humana obligatoria en los puntos críticos

Hay tres momentos en los que la automatización se detiene siempre y te entrega el control:

  • Conflictos. Te avisa qué archivos chocan y tú los resuelves.

  • Ramas protegidas. Nunca hace push ni merge en ellas.

  • Merge Requests. Las puede abrir, pero la revisión, la aprobación y la fusión son de personas.

4. Registro de cada comando y resultado

Cada acción queda anotada en un archivo de registro: fecha, proyecto, rama, comando y resultado. Así puedes auditar qué hizo la automatización y, si algo salió mal, saber exactamente qué revertir (capítulo 7). Un registro como este:

2026-10-08 10:42:11 | practica-git | git pull (rama feature/sobre-mi) | ok
2026-10-08 10:43:02 | practica-git | commit a3f9c21: Agrega sección sobre mí | ok
2026-10-08 10:43:05 | practica-git | push a origin/feature/sobre-mi | ok

Con el código del commit (a3f9c21) puedes hacer git show para revisarlo o git revert para anularlo.

5. Mínimos permisos

La automatización usa tus credenciales con los permisos justos: puede escribir en ramas, pero no fusionar en main (para eso están las ramas protegidas del capítulo 10). Si usas un token para ella, que tenga fecha de vencimiento y solo los permisos necesarios.

Opción A: un script sencillo con confirmación

Un script es una lista de comandos guardada en un archivo, que se ejecuta de un tirón. No es inteligente: hace siempre lo mismo. Justamente por eso es predecible.

Este script aplica las cinco reglas. Toma lo que tú pusiste en la caja con git add, te lo muestra, busca archivos sensibles, te pide el mensaje y la confirmación, hace commit y push a tu rama, y lo anota todo:

#!/usr/bin/env bash
# publicar.sh: guarda y publica lo que está en la caja, con revisión humana
set -euo pipefail

LOG="$HOME/.git-asistente.log"
log() { echo "$(date '+%Y-%m-%d %H:%M:%S') | $(basename "$PWD") | $*" | tee -a "$LOG"; }

# 1. Validar: repositorio, rama y estado
if ! git rev-parse --is-inside-work-tree >/dev/null 2>&1; then
  echo "No estás dentro de un repositorio Git."; exit 1
fi

RAMA=$(git branch --show-current)
if [[ -z "$RAMA" || "$RAMA" == "main" || "$RAMA" == "master" ]]; then
  echo "Estás en '$RAMA'. Crea una rama antes de publicar."; exit 1
fi

if [[ -f "$(git rev-parse --git-dir)/MERGE_HEAD" ]]; then
  echo "Hay un merge a medias. Resuélvelo tú primero (capítulo 6)."; exit 1
fi

# 2. Traer cambios de GitLab si la rama ya está publicada
if git rev-parse --abbrev-ref '@{u}' >/dev/null 2>&1; then
  if git pull --no-rebase; then
    log "git pull (rama $RAMA) | ok"
  else
    log "git pull (rama $RAMA) | conflicto o error, se detiene"
    echo "Hay conflictos o errores. Resuélvelos tú y vuelve a ejecutar."; exit 1
  fi
fi

# 3. Vista previa de lo que se va a guardar
if git diff --cached --quiet; then
  echo "No hay nada en la caja. Usa git add con los archivos que quieres guardar."; exit 1
fi
echo "===== Archivos que se van a guardar ====="
git --no-pager diff --cached --stat
echo "===== Cambios ====="
git --no-pager diff --cached

# 4. Alerta de archivos sensibles
if git diff --cached --name-only | grep -Eiq '(^|/)\.env$|\.pem$|\.key$|id_rsa|id_ed25519'; then
  log "ALERTA: archivo sensible en la caja, se detiene"
  echo "Hay archivos que parecen secretos. Sácalos de la caja (capítulo 10)."; exit 1
fi

# 5. Mensaje y confirmación humana
read -r -p "Mensaje del commit: " MSG
if [[ -z "$MSG" ]]; then echo "El mensaje no puede estar vacío."; exit 1; fi

read -r -p "¿Guardar y publicar en '$RAMA'? Escribe si para confirmar: " OK
if [[ "$OK" != "si" ]]; then log "cancelado por la persona"; echo "Cancelado."; exit 0; fi

git commit -m "$MSG"
log "commit $(git rev-parse --short HEAD): $MSG | ok"

git push -u origin "$RAMA"
log "push a origin/$RAMA | ok"

echo "Listo. Abre o revisa la Merge Request en GitLab. La fusión la decide una persona."

Cómo usarlo:

  1. Guarda el texto en un archivo publicar.sh, en una carpeta fuera de tus proyectos (por ejemplo, ~/scripts/).

  2. Dale permiso de ejecución una sola vez: chmod +x ~/scripts/publicar.sh.

  3. En tu proyecto, mira y elige tus cambios como siempre: git status, git diff, git add archivo.

  4. Ejecuta ~/scripts/publicar.sh y sigue las preguntas.

  5. Revisa el registro cuando quieras: cat ~/.git-asistente.log.

Fíjate en lo que el script no hace: no elige archivos por ti, no hace merge, no resuelve conflictos, no fuerza nada y no toca main. Esas decisiones siguen siendo tuyas. En Windows, ejecútalo desde Git Bash.

Opción B: un agente de IA con reglas claras

Un agente de IA, como los que vienen integrados en editores como Cursor o en asistentes de código, es más flexible que un script: entiende instrucciones en lenguaje natural ("agrega un filtro por fecha y súbelo a una rama"), escribe código y ejecuta comandos. Esa flexibilidad es justo lo que exige más control.

Dale reglas escritas

La mayoría de los agentes permiten dejar instrucciones permanentes en un archivo del proyecto (según la herramienta, puede llamarse AGENTS.md, un archivo de reglas del editor u otro nombre que indique su documentación). Esas instrucciones las lee el agente antes de trabajar. Un ejemplo que puedes adaptar:

# Reglas para trabajar con Git en este proyecto

## Antes de actuar
- Ejecuta git status y dime en qué rama estás y qué cambió.
- Nunca trabajes en main. Si estás en main, crea una rama con el formato
  tipo/numero-descripcion (por ejemplo fix/42-fecha-vacia) y pídeme confirmación.
- Haz git pull antes de empezar.

## Commits
- Un commit por idea. Mensaje en español, empezando con un verbo.
- Antes de cada commit, muéstrame el diff y el mensaje propuesto, y espera mi "sí".
- Nunca agregues archivos .env, llaves, credenciales ni archivos fuera de la tarea.

## Publicar
- Solo haz push a la rama de trabajo, nunca a main ni a ramas protegidas.
- Antes de hacer push, pídeme confirmación.
- Puedes preparar la descripción de la Merge Request, pero no la fusiones.

## Prohibido sin mi autorización explícita
- git push --force, git reset --hard, git clean, borrar ramas.
- Resolver conflictos: si aparece uno, detente y dime qué archivos chocan.
- Modificar .gitlab-ci.yml o la configuración del proyecto.

## Registro
- Al terminar, dame la lista de comandos que ejecutaste y su resultado.

Cómo pedirle las cosas

Un buen pedido al agente describe qué quieres y cuáles son los límites:

"Agrega validación de fecha obligatoria al formulario de contacto, para el issue #42. Trabaja en una rama nueva. Cuando termines, muéstrame el diff y el mensaje del commit antes de guardar. No hagas push sin mi confirmación."

Compáralo con "arregla el formulario y súbelo". El primero deja claros el alcance, la rama y los puntos de control. El segundo le da al agente demasiada libertad.

Revisa lo que el agente hizo

Cuando el agente te muestra el diff, léelo como si lo hubiera escrito un compañero nuevo en su primer día (capítulo 5):

  • ¿Hizo solo lo que pediste, o tocó otros archivos?

  • ¿Entiendes cada línea que cambió? Si no la entiendes, no la apruebes: pide que te la explique.

  • ¿Funciona? Pruébalo tú, no te quedes con "el agente dice que funciona".

  • ¿El mensaje del commit describe bien el cambio?

  • ¿Hay algo que parezca un secreto, un dato personal o un archivo temporal?

Si algo no te convence, pide el cambio o hazlo tú. Aprobar sin entender es exactamente el error de "guardar todo sin mirar" del capítulo 3, solo que más rápido.

Qué debes entender aunque esté automatizado

La automatización no te libera de saber Git. Te libera de escribir los comandos, no de entenderlos. Antes de usar un agente o un script, deberías poder responder:

  • ¿Qué diferencia hay entre commit y push? (capítulo 1)

  • ¿Cómo leo un diff y qué cambió? (capítulo 3)

  • ¿En qué rama estoy y por qué no debo estar en main? (capítulo 4)

  • ¿Qué pasa en una Merge Request y quién decide la fusión? (capítulo 5)

  • ¿Qué es un conflicto y cómo se resuelve sin perder trabajo? (capítulo 6)

  • ¿Cómo deshago un commit publicado? (capítulo 7)

  • ¿Por qué un secreto nunca entra al repositorio? (capítulo 10)

Si la automatización falla a mitad de camino, y algún día lo hará, eres tú quien tiene que entender en qué estado quedó el repositorio y cómo seguir.

Capítulo 12. Investigar el historial: Git como detective

El historial de Git no es solo un registro: es la herramienta para responder preguntas como "¿quién cambió esto?", "¿cuándo empezó a fallar?" o "¿qué diferencia hay entre mi rama y main?". En este capítulo aprenderás a buscar en la historia, a comparar versiones y a entender cómo se juntan las ramas por dentro.

Por qué vale la pena aprender a investigar

Cuando algo falla en un sistema, la primera pregunta casi nunca es "¿cómo lo arreglo?". Es "¿qué cambió?". Si sabes buscar en el historial, encuentras en minutos el commit responsable, quién lo hizo y por qué. Sin eso, te toca adivinar.

También sirve para cosas tranquilas: entender por qué una parte del proyecto está escrita de cierta forma, recordar qué hiciste la semana pasada o preparar un resumen de cambios para tu jefatura.

Aquí se nota el valor de los buenos mensajes de commit del capítulo 3. Un historial lleno de cambios y arreglos no le sirve a ningún detective.

Filtrar el historial con git log

Ya conoces git log --oneline. Estas variantes te permiten buscar algo concreto:

PreguntaComando
¿Qué hizo Ana?git log --oneline --author="Ana"
¿Qué cambió esta semana?git log --oneline --since="1 week ago"
¿Qué cambió entre dos fechas?git log --oneline --since="2026-09-01" --until="2026-09-30"
¿Qué commits tocaron este archivo?git log --oneline -- contacto.md
¿Qué commits mencionan "horario" en el mensaje?git log --oneline --grep="horario"
¿Qué commit agregó o quitó este texto?git log --oneline -S "500-0000"
¿Cuántos archivos cambió cada commit?git log --stat

Puedes combinarlos. Por ejemplo, los commits de Ana que tocaron contacto.md este mes:

git log --oneline --author="Ana" --since="1 month ago" -- contacto.md

El más poderoso para investigar errores es -S. Busca los commits donde un texto apareció o desapareció. Si un teléfono cambió y nadie sabe cuándo, git log -S "número-viejo" te lleva directo al commit.

Ver un archivo como estaba antes

Para ver un archivo completo tal como estaba en un commit, sin cambiar nada en tu carpeta:

git show a3f9c21:contacto.md

Es como abrir una foto vieja del archivo. Si lo que buscas es recuperarlo, usa git restore --source del capítulo 7.

git blame: ¿quién escribió cada línea?

git blame contacto.md

Muestra el archivo línea por línea y, junto a cada una, el commit, el autor y la fecha del último cambio:

a3f9c21 (Ana Pérez  2026-10-01) Horario: lunes a viernes, 8:00 a 5:00
7b2e104 (Luis Gómez 2026-09-15) Teléfono: 500-0000

Para ver solo unas líneas, por ejemplo de la 10 a la 20:

git blame -L 10,20 contacto.md

En GitLab tienes lo mismo con más comodidad: abre el archivo y pulsa el botón Blame. Puedes hacer clic en cada commit para ver el cambio completo.

Sobre el nombre. Blame significa "culpar" en inglés, pero no lo uses para buscar culpables. Úsalo para encontrar a quién preguntar y entender el contexto. La persona que escribió esa línea es la que mejor puede explicarte por qué está así. Y quizá esa persona eres tú, hace seis meses.

Comparar versiones y ramas

git diff no solo sirve para tus cambios sin guardar. También compara cualquier par de momentos:

git diff a3f9c21 7b2e104                 # Entre dos commits
git diff main feature/formulario         # Entre dos ramas
git diff main feature/formulario --stat  # Solo qué archivos cambian y cuánto
git diff main -- contacto.md             # Un solo archivo frente a main

Para saber qué commits tiene tu rama que main todavía no tiene:

git log --oneline main..feature/formulario

Y al revés, qué tiene main que a tu rama le falta:

git log --oneline feature/formulario..main

Si el segundo comando muestra muchos commits, es señal de que tu rama se está quedando atrás y conviene traer main (capítulo 4).

En GitLab, la opción equivalente está en Code > Compare revisions: eliges dos ramas, etiquetas o commits y ves todas las diferencias.

git fetch y git pull: mirar antes de juntar

Hasta ahora usaste git pull para traer cambios. En realidad pull hace dos cosas seguidas:

  1. git fetch: descarga la información nueva de GitLab, sin tocar tus archivos ni tu rama.

  2. git merge: junta esa información con tu rama.

A veces conviene hacer solo la primera parte, para mirar antes de juntar:

git fetch
git log --oneline main..origin/main     # ¿Qué hay nuevo en GitLab?
git diff main origin/main --stat        # ¿Qué archivos cambiaron?

origin/main es la copia que tu computadora guarda de cómo está main en GitLab. Después de revisar, si todo está bien, haces git pull (o git merge origin/main).

Es como el buzón del capítulo 4: fetch trae las cartas, tú decides cuándo abrirlas.

Cómo se juntan las ramas por dentro

En el capítulo 5 viste la opción de squash. Vale la pena entender las cuatro formas en que Git puede juntar una rama con otra, porque cada una deja un historial distinto.

Fast-forward (avance rápido)

Si main no cambió desde que creaste tu rama, Git solo tiene que mover la etiqueta de main hasta tu último commit. No se crea ningún commit nuevo:

Antes:   main: A --- B
                      \
         rama:         C --- D

Después: main: A --- B --- C --- D

Merge commit (commit de fusión)

Si main sí cambió, Git crea un commit especial que une las dos líneas. Ese commit tiene dos "padres":

main: A --- B --- E ------- M
             \             /
rama:         C --- D ----

Ventaja: el historial muestra exactamente cuándo se trabajó en paralelo y cuándo se juntó. Desventaja: con muchas ramas, el dibujo se vuelve un enredo.

Squash (aplastar)

Todos los commits de tu rama se convierten en uno solo al entrar a main:

main: A --- B --- E --- S     (S contiene C + D juntos)

Ventaja: main queda limpia, un commit por tarea. Desventaja: se pierde el detalle de los pasos intermedios.

Rebase (cambiar la base)

En vez de unir las líneas, Git "reescribe" tus commits como si los hubieras hecho después de los últimos cambios de main:

main: A --- B --- E --- C' --- D'

Ventaja: historial en línea recta, muy fácil de leer. Desventaja: reescribe tus commits (por eso llevan una comilla: son copias nuevas, con otros identificadores).

La regla de oro del rebase: nunca hagas rebase de commits que otras personas ya descargaron. Si lo haces, su historia y la tuya dejan de coincidir y les causas problemas serios. Úsalo solo en tu propia rama, antes de compartirla, y cuando te sientas segura o seguro con todo lo anterior.

¿Cuál usar?

Normalmente no lo decides tú: lo define tu equipo en la configuración del proyecto en GitLab (Settings > Merge requests > Merge method). Lo importante es que entiendas por qué el historial de tu proyecto se ve como se ve.

MétodoHistorial resultanteComún en
Merge commitMuestra ramas y fusionesEquipos que quieren trazabilidad completa
SquashUn commit por tarea en mainEquipos que priorizan un main limpio
Fast-forward / rebaseLínea rectaEquipos con experiencia y ramas cortas

Encontrar cuándo empezó un error

Cuando sabes que algo funcionaba antes y ahora no, puedes buscar el commit culpable por pasos:

  1. Busca un momento en que funcionaba (un commit o una etiqueta vieja).

  2. Revisa los commits intermedios con git log --oneline commit-bueno..main.

  3. Si son pocos, lee sus mensajes y cambios con git show.

  4. Si son muchos, prueba el proyecto en un commit de la mitad. Según funcione o no, sabrás en qué mitad está el error. Repite.

Git automatiza este método de "partir a la mitad" con un comando llamado git bisect. No lo veremos a fondo, pero ya sabes que existe y para qué sirve: cuando un día lo necesites, la idea ya te resultará familiar.

Ana busca el número correcto en la historia:

Aparecen dos commits: el que agregó el número hace meses y uno de la semana pasada que lo quitó, con el mensaje Actualiza pie de página. Ana lo abre con git show y ve que, al reorganizar el pie de página, se copió un teléfono viejo por error.

Con git blame confirma que la línea actual viene de ese commit. Le escribe a la persona que lo hizo, entienden juntas qué pasó y Ana corrige el número en una rama fix/telefono-contacto con su Merge Request. Todo en quince minutos y sin culpar a nadie.

Capítulo 13. Versiones, etiquetas y forks

Las etiquetas marcan momentos importantes del proyecto, como "esta es la versión 1.0 que se publicó". Los forks te permiten contribuir a proyectos que no son tuyos. Y Markdown es el formato con el que vas a escribir README, Merge Requests, issues y la wiki. Son tres herramientas que completan tu trabajo diario con Git.

Por qué marcar versiones

Imagina que el sistema que mantiene tu equipo se publica cada dos semanas. Un día, un usuario reporta un error y dice: "esto funcionaba en la versión del mes pasado". ¿Qué commit era esa versión?

Si nadie lo marcó, toca buscar entre cientos de commits por fecha y adivinar. Si el equipo usó etiquetas, escribes v1.3.0 y llegas directo.

Una etiqueta (en inglés, tag) es un nombre fijo que se le pone a un commit. A diferencia de una rama, no se mueve: siempre apunta al mismo commit. Es como poner un separador en una página del libro.

Cómo numerar versiones: versionado semántico

La convención más usada se llama versionado semántico. El número tiene tres partes: MAYOR.MENOR.PARCHE.

ParteCuándo subeEjemplo
PARCHECorrecciones de errores, sin cambios en cómo se usa1.4.2 → 1.4.3
MENORFunciones nuevas que no rompen lo anterior1.4.3 → 1.5.0
MAYORCambios que obligan a los usuarios a adaptarse1.5.0 → 2.0.0

Cuando sube una parte, las de la derecha vuelven a cero. Y las versiones que empiezan con 0 (como 0.3.1) indican que el proyecto todavía está en desarrollo y puede cambiar mucho.

Por costumbre, las etiquetas llevan una v delante: v1.5.0.

Crear y publicar etiquetas

Hay dos tipos. Usa casi siempre la anotada, que guarda autor, fecha y un mensaje:

git switch main
git pull
git tag -a v1.0.0 -m "Primera versión estable del sitio"

Esto etiqueta el último commit de main. Para etiquetar un commit anterior, agrega su código al final: git tag -a v0.9.0 -m "…" 7b2e104.

Las etiquetas no viajan solas con el push. Tienes que publicarlas:

git push origin v1.0.0     # Una etiqueta
git push origin --tags     # Todas las etiquetas locales

Otros comandos útiles:

ComandoQué hace
git tagLista las etiquetas
git tag -l "v1.*"Lista solo las que empiezan con v1
git show v1.0.0Muestra la etiqueta y su commit
git switch --detach v1.0.0Te lleva a ver el proyecto como estaba en esa versión
git tag -d v1.0.0Borra la etiqueta en tu computadora
git push origin --delete v1.0.0Borra la etiqueta en GitLab

Sobre --detach. Al ir a una etiqueta, Git te avisa que estás en modo detached HEAD: no estás en ninguna rama. Puedes mirar y probar, pero si haces commits ahí se quedan "sueltos". Para volver, haz git switch main. Si necesitas corregir algo de esa versión, crea una rama desde ella: git switch -c hotfix/v1.0.1 v1.0.0.

Una regla importante: no cambies una etiqueta ya publicada. Si la versión v1.0.0 tenía un error, la corrección es v1.0.1. Mover una etiqueta confunde a todos los que ya la descargaron.

Releases en GitLab

Una release es una etiqueta con presentación: un título, notas que explican qué trae la versión y, si hace falta, archivos para descargar. Se crea en Deploy > Releases > New release (o desde Code > Tags).

Unas buenas notas de versión responden lo que le importa a quien la va a usar:

## v1.5.0 — 8 de octubre de 2026

### Nuevo
- Formulario de contacto con validación de correo.
- Filtro por fecha en la búsqueda.

### Corregido
- El teléfono del pie de página mostraba un número antiguo.

### Cambios importantes
- Ninguno. Esta versión es compatible con la anterior.

Muchos proyectos además mantienen un archivo CHANGELOG.md en la raíz del repositorio con estas notas, de la versión más nueva a la más vieja. Si tus Merge Requests tienen buenos títulos (capítulo 5), escribir las notas es casi copiar y ordenar.

Forks: contribuir a proyectos que no son tuyos

Hasta ahora trabajaste en proyectos donde tenías permiso para crear ramas. Pero ¿qué pasa si quieres proponer una mejora a un proyecto público, o a uno de otro departamento, donde no tienes permiso de escribir?

Para eso existe el fork: una copia completa del proyecto en tu propia cuenta de GitLab. En tu copia puedes hacer lo que quieras. Cuando tienes algo listo, abres una Merge Request desde tu fork hacia el proyecto original. Sus responsables deciden si la aceptan.

RamaFork
Dónde viveDentro del mismo proyectoEn tu cuenta, como proyecto aparte
Necesitas permiso de escrituraSíNo
Cuándo se usaTrabajo dentro de tu equipoContribuir a proyectos ajenos o de código abierto

El recorrido de una contribución con fork

  1. En el proyecto original, pulsa Fork y elige tu cuenta.

  2. Clona tu fork, no el original:

git clone git@gitlab.com:tu-usuario/proyecto.git
cd proyecto

  1. Conecta también el proyecto original, para poder traer sus novedades. Por costumbre se le llama upstream:

git remote add upstream git@gitlab.com:equipo-original/proyecto.git
git remote -v

Ahora tienes dos remotos: origin (tu fork) y upstream (el original).

  1. Crea una rama, haz tus cambios y publícalos en tu fork:

git switch -c fix/error-en-documentacion
# haces los cambios y commits
git push -u origin fix/error-en-documentacion

  1. En GitLab, abre una Merge Request desde tu fork hacia el proyecto original. Revisa bien el proyecto y la rama de destino.

  2. Atiende los comentarios igual que en el capítulo 5: cada push a tu rama actualiza la Merge Request.

Mantener tu fork al día

El proyecto original sigue avanzando. Para traer sus cambios a tu fork:

git switch main
git fetch upstream
git merge upstream/main
git push origin main

Hazlo antes de empezar cada contribución nueva, para no partir de una versión vieja.

Etiqueta para contribuir a proyectos ajenos

  • Lee primero el README y el archivo CONTRIBUTING.md, si existe. Ahí explican cómo prefieren recibir cambios.

  • Para cambios grandes, abre antes un issue y pregunta si les interesa. Así no trabajas días en algo que no van a aceptar.

  • Haz Merge Requests pequeñas y bien descritas. Quienes mantienen proyectos abiertos suelen ser voluntarios con poco tiempo.

  • Ten paciencia. Una respuesta puede tardar días. Un recordatorio amable después de una semana está bien.

En GitHub se llama… Igual: Fork. La Merge Request desde un fork es una Pull Request.

Markdown es una forma sencilla de dar formato a un texto usando símbolos. GitLab y GitHub lo convierten en títulos, listas y enlaces. Lo usarás en el README, las descripciones de Merge Requests, los comentarios, los issues y la wiki. Los archivos terminan en .md.

Un buen README

El README es la puerta de entrada al proyecto. Esta estructura funciona para casi todos:

Un README claro ahorra decenas de preguntas repetidas a tu equipo, y a ti misma o a ti mismo dentro de un año.

  2. Haz un commit nuevo en una rama, fusiónalo con una Merge Request y crea la etiqueta v0.2.0.

  3. En GitLab, crea una release para v0.2.0 con notas de versión en Markdown, usando las secciones Nuevo y Corregido.

  4. Usa git switch --detach v0.1.0 para ver cómo era el proyecto. Vuelve con git switch main.

  5. Reescribe el README.md de tu proyecto con la estructura de este capítulo. Incluye al menos un título, una lista, un enlace, un bloque de código y una tabla. Mira cómo se ve en GitLab.

  6. Busca un proyecto público pequeño en GitLab o GitHub y haz un fork. Clónalo, agrega upstream y comprueba los dos remotos con git remote -v. No hace falta que envíes una contribución todavía: lee su README y su CONTRIBUTING.md y anota cómo prefieren recibir cambios.

Checklist del capítulo

  • Sé qué es una etiqueta y en qué se diferencia de una rama.

  • Entiendo el versionado semántico: MAYOR.MENOR.PARCHE.

  • Sé crear una etiqueta anotada y publicarla.

  • Sé ver el proyecto en una versión anterior y volver a main.

  • Nunca muevo una etiqueta ya publicada: saco una versión nueva.

  • Sé crear una release en GitLab con buenas notas de versión.

  • Sé qué es un fork y cuándo usarlo en lugar de una rama.

  • Sé conectar upstream y mantener mi fork al día.

  • Leo el README y el CONTRIBUTING antes de contribuir a un proyecto ajeno.

  • Sé escribir Markdown básico: títulos, listas, enlaces, código y tablas.

  • Sé usar #, ! y @ en GitLab para enlazar issues, Merge Requests y personas.

  • Mi proyecto de práctica tiene un README claro.

Capítulo 14. Proyecto práctico final

En este capítulo vas a recorrer el flujo completo de trabajo en equipo, de principio a fin, como lo harías en un proyecto real: clonar, crear un issue y una rama, hacer cambios, abrir una Merge Request, corregir una observación, revisar el pipeline y completar el merge. No hay temas nuevos. Es el momento de juntar todo lo que aprendiste.

El escenario

Tu equipo mantiene un pequeño sitio de guía interna para personas nuevas: una página con la bienvenida, los contactos del equipo y las preguntas frecuentes. Te piden agregar una sección nueva de preguntas frecuentes sobre Git, porque las personas que llegan siempre preguntan lo mismo.

Es un cambio pequeño a propósito. Lo importante no es el contenido, sino hacer cada paso del proceso bien.

Cómo hacerlo: en pareja o sola o solo

En pareja (recomendado). Una persona es la autora y la otra la revisora. Al terminar, cambian de papel y repiten con otra tarea. Así viven los dos lados de la Merge Request.

Sola o solo. Haces los dos papeles. Para la revisión, deja pasar unas horas entre escribir y revisar: vas a ver tu trabajo con ojos más frescos. Si puedes, pídele a alguien con cuenta en GitLab que haga solo la revisión.

Preparación del proyecto

Necesitas un proyecto que tenga pipeline, para practicar su lectura. Hay tres caminos, en este orden de preferencia:

  1. Tu organización o tu instructor te da un proyecto ya preparado, con pipeline. Úsalo.

  2. Créalo desde una plantilla de GitLab que ya incluye pipeline. En New project > Create from template, elige una plantilla sencilla de sitio web, como Pages/Plain HTML. No tienes que configurar nada: el archivo .gitlab-ci.yml ya viene incluido.

  3. Usa tu proyecto practica-git. No tendrá pipeline, así que en la fase 6 solo verificarás que no hay uno y repasarás cómo se leería.

En GitLab.com, para que los pipelines se ejecuten, la plataforma puede pedirte verificar tu cuenta. Si no puedes o no quieres hacerlo, sigue con el camino 3: el resto del proyecto funciona igual.

Llamaremos al proyecto guia-equipo. Si eres la persona dueña, agrega a tu pareja como Developer (capítulo 10) y protege main: fusionar solo Maintainers, push directo No one.

Fase 1: clonar el proyecto

Objetivo: tener el proyecto en tu computadora, al día.

cd Documentos
git clone git@gitlab.com:tu-usuario/guia-equipo.git
cd guia-equipo
git status
git log --oneline -5

Punto de control:

  • git status dice que estás en main y que todo está limpio.

  • Leíste el README para entender el proyecto.

  • git config user.email muestra el correo de tu cuenta de GitLab.

Si algo falla: revisa la tabla de problemas comunes del capítulo 2.

Fase 2: crear el issue y la rama

Objetivo: que la tarea exista en GitLab antes de tocar el código.

  1. En GitLab, crea un issue (capítulo 8):

Título: Agregar preguntas frecuentes sobre Git a la guía

## Qué se necesita
Una sección de preguntas frecuentes sobre Git para personas nuevas.

## Para qué
Las personas que llegan hacen siempre las mismas preguntas.

## Cuándo lo damos por terminado
- [ ] Hay al menos cinco preguntas con su respuesta.
- [ ] La sección está enlazada desde la página principal.
- [ ] El texto no tiene errores de ortografía.

  1. Ponle la etiqueta documentación, asígnatelo y, si tienes, agrégalo a un milestone.

  2. Anota su número. En los ejemplos usaremos #7.

  3. Crea la rama. Puedes usar el botón Create merge request del issue, o hacerlo desde la terminal:

git switch main
git pull
git switch -c docs/7-preguntas-frecuentes-git

Punto de control:

  • El issue tiene título claro, descripción y criterios de terminado.

  • La rama sigue la convención tipo/numero-descripcion.

  • Partiste de main actualizado.

  • Moviste el issue a En progreso en el tablero, si lo usas.

Fase 3: hacer los cambios y los commits

Objetivo: cambios pequeños, revisados antes de guardar, con mensajes claros.

  1. Crea el archivo de la sección. Si el proyecto es en HTML, crea preguntas-git.html; si es en Markdown, preguntas-git.md. Escribe al menos cinco preguntas con respuestas cortas. Ideas: "¿Qué es un commit?", "¿Por qué no trabajo en main?", "¿Qué hago si aparece un conflicto?", "¿Qué es una Merge Request?", "¿Qué hago si subí una contraseña?".

  2. Mira antes de guardar y haz el primer commit:

git status
git diff
git add preguntas-git.md
git diff --staged
git commit -m "Agrega sección de preguntas frecuentes sobre Git (#7)"

  1. Ahora enlaza la sección desde la página principal (el index.html o el README.md). Es una idea distinta, así que va en otro commit:

git add index.html
git commit -m "Enlaza preguntas frecuentes desde la página principal (#7)"

  1. Revisa tu historial y publica la rama:

git log --oneline -3
git push -u origin docs/7-preguntas-frecuentes-git

Punto de control:

  • Hiciste al menos dos commits, uno por idea.

  • Cada mensaje empieza con un verbo y menciona el issue.

  • Usaste git status y git diff antes de cada commit.

  • No entró ningún archivo ajeno a la tarea.

  • La rama aparece en GitLab, en Code > Branches.

Opcional: si practicas con agente, haz esta fase con él siguiendo las reglas del capítulo 11, y verifica todo manualmente.

Fase 4: abrir la Merge Request

Objetivo: pedir revisión con toda la información que la revisora necesita.

  1. Abre la Merge Request desde el enlace que te dio el push.

  2. Verifica: origen docs/7-preguntas-frecuentes-git, destino main.

  3. Título: Agrega preguntas frecuentes sobre Git a la guía.

  4. Descripción, con la plantilla del capítulo 5:

## Qué cambia
Agrega una sección de preguntas frecuentes sobre Git y la enlaza
desde la página principal.

## Por qué
Las personas nuevas preguntan siempre lo mismo.

## Cómo probarlo
1. Abrir la página principal.
2. Hacer clic en "Preguntas frecuentes sobre Git".
3. Verificar que se ven las preguntas y respuestas.

Closes #7

  1. Asigna a tu pareja como Reviewer, pon la etiqueta documentación y marca Delete source branch.

  2. Antes de avisar, revisa tú la pestaña Changes completa.

Punto de control:

  • Origen y destino son correctos.

  • La descripción explica qué, por qué y cómo probar.

  • Incluye Closes #7.

  • Revisaste tus propios cambios antes de pedir revisión.

Fase 5: revisar y corregir una observación

Objetivo: vivir el ciclo de comentario, corrección y resolución.

Si eres la revisora o el revisor:

  1. Lee la descripción y luego la pestaña Changes.

  2. Deja al menos dos comentarios con Start a review: uno marcado como sugerencia, usando Insert suggestion, y otro que pida un cambio real (por ejemplo, una respuesta que se puede explicar mejor o una pregunta que falta).

  3. Recuerda: comentarios sobre el contenido, con el motivo, y algo positivo si lo hay.

  4. Publica la revisión.

Si eres la autora o el autor:

  1. Lee cada comentario completo.

  2. Aplica la sugerencia con Apply suggestion.

  3. Para el otro comentario, corrige en tu computadora. Como aplicaste una sugerencia en GitLab, primero trae ese cambio:

git pull
# haces la corrección
git status
git diff
git add preguntas-git.md
git commit -m "Aclara la respuesta sobre conflictos (#7)"
git push

  1. Verifica que la Merge Request se actualizó sola con tu nuevo commit.

  2. Responde cada hilo con lo que hiciste y resuélvelos (o deja que los resuelva quien comentó, según el acuerdo de tu equipo).

  3. Vuelve a solicitar la revisión.

Reto extra: un conflicto. Mientras la Merge Request está abierta, que la otra persona haga una Merge Request pequeña que cambie la misma línea del enlace en la página principal, y la fusione primero. Tu Merge Request mostrará un conflicto. Resuélvelo en tu computadora con git merge main (capítulo 6), conservando los dos cambios, y haz push.

Punto de control:

  • Hubo al menos dos comentarios y los dos se atendieron.

  • La corrección llegó con un commit nuevo a la misma rama.

  • Todos los hilos quedaron resueltos.

  • Si hiciste el reto, el conflicto se resolvió sin perder ningún cambio.

Fase 6: revisar el pipeline

Objetivo: leer el semáforo antes de fusionar (capítulo 9). Recuerda: no vas a configurar nada, solo a leer.

  1. En la Merge Request, localiza el recuadro del pipeline. Cada push que hiciste lo ejecutó automáticamente.

  2. Si está en running, espera.

  3. Si está en passed, abre el pipeline y mira sus etapas y trabajos. Abre el registro de un trabajo y lee las últimas líneas.

  4. Si está en failed, aplica el proceso del capítulo 9: identifica el trabajo, lee el final del registro, relaciónalo con tu cambio, corrige y haz push. Si no tiene relación con tu cambio, usa Retry una vez; si sigue fallando, pide ayuda con el enlace y las líneas del error.

  5. Si tu proyecto no tiene pipeline (camino 3), verás que no aparece ningún recuadro. Entra a Build > Pipelines y confirma que está vacío. Luego repasa en un proyecto público cómo se vería.

Punto de control:

  • Sé en qué estado quedó el pipeline y por qué.

  • No avancé a la fusión con el pipeline en rojo.

Fase 7: completar el merge

Objetivo: cerrar el ciclo y dejar todo ordenado.

  1. Revisa la lista "Qué revisar antes de fusionar" del capítulo 10.

  2. La revisora o el revisor aprueba con Approve.

  3. Quien tiene permiso de fusionar pulsa Merge.

  4. Verifica en GitLab:

    • El issue #7 se cerró solo.

    • La rama se borró.

    • En Code > Commits de main aparecen tus commits (o uno solo, si se usó squash).

    • El tablero y el milestone se actualizaron.

  5. Actualiza tu computadora:

git switch main
git pull
git branch -d docs/7-preguntas-frecuentes-git
git fetch --prune
git log --oneline --graph -10

  1. Opcional: crea la etiqueta v1.1.0 con su release y notas de versión (capítulo 13).

Punto de control:

  • La Merge Request se fusionó con aprobación y con todo resuelto.

  • El issue se cerró automáticamente.

  • Tu main local está al día y la rama local se borró.

Fase 8: cambiar de papel

Si trabajas en pareja, repitan todo con los papeles invertidos y una tarea distinta. Ideas:

  • Agregar una sección de contactos del equipo.

  • Corregir errores de ortografía en la página principal (tipo fix/).

  • Crear en la wiki la página "Cómo trabajamos" y enlazarla desde el README.

Plan de acción de 7 días

Este plan convierte el libro en práctica diaria. Cada día tiene un objetivo, las tareas concretas, el tiempo aproximado y una pequeña prueba para saber si lo lograste. Dedica entre una y dos horas al día. Si un día no te alcanza, no pasa nada: sigue al día siguiente desde donde quedaste. Lo importante es no saltarse pasos.

Día 1: prepara todo y entiende el porqué

Objetivo: tener Git listo y entender qué problema resuelve.

Capítulos: 0, 1 y 2. Tiempo: 1 a 2 horas.

  • Lee los capítulos 0 y 1.

  • Revisa una carpeta tuya llena de versiones manuales (ejercicio del capítulo 0).

  • Instala Git y configura tu nombre y tu correo.

  • Crea tu cuenta en GitLab y configura SSH (o un token).

  • Crea y clona tu proyecto practica-git.

Prueba del día: explícale a alguien, en dos minutos y sin palabras técnicas, qué es Git y qué es GitLab.

Día 2: el ciclo básico

Objetivo: guardar y publicar cambios mirando siempre antes.

Capítulo: 3. Tiempo: 1 a 2 horas.

  • Haz al menos cinco commits pequeños en practica-git, cada uno con git status y git diff antes.

  • Crea tu .gitignore.

  • Practica git add -p en un archivo con dos cambios distintos.

  • Publica tus commits y búscalos en GitLab.

  • Corrige un mensaje con git commit --amend antes de hacer push.

Prueba del día: escribe de memoria, en orden, los comandos del ciclo: status, diff, add, commit, log, pull, push.

Día 3: ramas y Merge Requests

Objetivo: trabajar sin tocar main y pedir revisión.

Capítulos: 4 y 5. Tiempo: 2 horas.

  • Crea dos ramas con la convención tipo/descripcion.

  • Trae main a una de ellas con git merge main.

  • Abre una Merge Request con la plantilla de descripción.

  • Comenta una línea, usa una sugerencia y resuelve el hilo.

  • Fusiona, actualiza main y borra la rama local.

Prueba del día: sin mirar el libro, haz el recorrido completo de una rama nueva hasta la fusión.

Día 4: conflictos y errores

Objetivo: perderles el miedo a los conflictos y a equivocarte.

Capítulos: 6 y 7. Tiempo: 2 horas.

  • Provoca un conflicto a propósito y resuélvelo combinando los dos cambios.

  • Cancela un merge con git merge --abort.

  • Haz el ejercicio completo del botiquín: restore, reset, stash, revert y reflog.

  • Escribe tu hoja personal de botiquín.

Prueba del día: responde sin mirar: "Ya hice push de un commit con error. ¿Qué comando uso y por qué no uso reset?".

Día 5: organización, pipelines y seguridad

Objetivo: trabajar como en un equipo real, con orden y protecciones.

Capítulos: 8, 9 y 10. Tiempo: 2 horas.

  • Crea etiquetas, un milestone y tres issues con plantillas.

  • Crea una rama desde un issue y ciérralo con Closes #número.

  • Lee un pipeline fallido en un proyecto público y explica el error.

  • Protege main en tu proyecto y comprueba que no puedes hacer push directo.

  • Crea .env y .env.example, y activa la verificación en dos pasos.

Prueba del día: recorre en GitLab la cadena completa de una tarea: issue, rama, commits, Merge Request e issue cerrado.

Día 6: herramientas extra y automatización

Objetivo: investigar el historial, marcar versiones y usar un agente con control.

Capítulos: 11, 12 y 13. Tiempo: 2 horas.

  • Usa git log -S y git blame para investigar un cambio.

  • Crea una etiqueta v0.1.0 y una release con notas.

  • Mejora tu README con Markdown.

  • Escribe las reglas para tu agente o prepara el script publicar.sh.

  • Haz un cambio completo con ayuda del agente o del script, y verifícalo manualmente en GitLab.

Prueba del día: explica qué cinco cosas nunca dejarías que un agente haga solo.

Día 7: proyecto final y acuerdos

Objetivo: hacer todo el flujo de principio a fin y dejar tus reglas por escrito.

Capítulo: 14. Tiempo: 2 a 3 horas.

  • Completa las siete fases del proyecto final, de preferencia en pareja.

  • Llena la tabla de evaluación final y repasa lo que quedó en "todavía no".

  • Responde las preguntas de reflexión.

  • Escribe en la wiki la página "Reglas del equipo" con tus acuerdos de ramas, commits, revisiones y seguridad.

Prueba del día: el proyecto final quedó fusionado, con el issue cerrado y sin trabajo perdido.

Después de los 7 días: hábitos para cada jornada

Lo que aprendiste se mantiene usándolo. Estos hábitos convierten el libro en tu forma de trabajar:

Al empezar el día

  • git switch main y git pull.

  • Revisar el tablero y elegir tu tarea.

  • Crear la rama desde el issue.

Durante el día

  • Commits pequeños, mirando antes con git status y git diff.

  • Traer main a tu rama si el trabajo se alarga.

  • Comentar avances y dudas en el issue.

Al terminar el día

  • Hacer push de tu rama, aunque el trabajo no esté terminado: así queda respaldado.

  • Abrir la Merge Request en borrador si necesitas opinión temprana.

  • Dejar tu carpeta limpia: nada a medias sin commit o sin stash con nombre.

Cada semana

  • Revisar tus Merge Requests abiertas y las que te tocan revisar.

  • Borrar ramas locales ya fusionadas y hacer git fetch --prune.

  • Aprender un comando o una función nueva de GitLab y probarlo en practica-git.

Si en algún momento te sientes perdida o perdido, vuelve a la hoja de comandos que viene a continuación. Y recuerda la promesa del inicio: casi todo en Git se puede deshacer.

Para empezar con humor: datos curiosos sobre Git

El nombre. Linus Torvalds bromeó con que les pone a sus proyectos su propio nombre, primero Linux y luego Git. En la jerga británica, git es una forma poco amable de llamar a alguien desagradable. El propio README original de Git jugaba con eso: según el humor del día, el nombre podía significar "rastreador global de información" o algo mucho menos educado.

La descripción oficial. Si escribes man git en Mac o Linux, la primera línea describe a Git como "the stupid content tracker": el rastreador de contenido tonto. Tonto porque hace algo muy simple (guardar fotos del proyecto), pero lo hace muy bien.

El primer commit de la historia de Git lo hizo Torvalds en abril de 2005, y su mensaje llamaba a Git "the information manager from hell". A los pocos días, Git ya se usaba para guardar su propio código.

Esos códigos raros como a3f9c21 son la versión corta de un identificador de 40 caracteres, calculado a partir del contenido del commit. Por eso dos commits distintos nunca tienen el mismo código, y por eso cambiar un commit viejo cambia su identidad.

Comandos que te sacan una sonrisa

Git te corrige la ortografía

¿Escribes git stauts en lugar de git status más veces de las que admitirías? Activa la autocorrección:

git config --global help.autocorrect 20

Ahora, si te equivocas, Git te dice qué quisiste escribir, espera 2 segundos (el número va en décimas de segundo) y ejecuta el comando correcto. Te da tiempo de cancelar con Ctrl + C si no era eso.

Git sabe a qué hora es el té

Git entiende fechas en lenguaje casi humano, en inglés. Prueba:

git log --oneline --since="yesterday"
git log --oneline --since="noon"
git log --oneline --since="midnight"
git log --oneline --since="tea"

Sí: tea es la hora del té, las 5:00 p.m. Git se toma en serio las costumbres británicas. También entiende cosas como "2 weeks ago" o "last monday".

El commit vacío

git commit --allow-empty -m "Commit vacío para volver a ejecutar el pipeline"

Un commit sin ningún cambio. Parece inútil, pero tiene usos reales: volver a disparar un pipeline sin tocar archivos, o marcar un momento ("Inicio del sprint 24"). También es el commit más fácil de revisar del mundo.

El ranking del equipo

git shortlog -sn HEAD

Muestra cuántos commits hizo cada persona, de mayor a menor. Divertido para la reunión de fin de año, pero no lo uses para medir a nadie: un commit de una línea y uno de un día entero cuentan igual.

Volver a la rama anterior, como un control remoto

git switch -

El guion te lleva a la última rama donde estuviste. Úsalo dos veces y vuelves. Es el botón "canal anterior" de Git.

Atajos que te ahorran tiempo: los alias

Un alias es un apodo para un comando largo. Los creas una vez y los usas para siempre. Y sí, pueden estar en español:

git config --global alias.ups "commit --amend --no-edit"
git config --global alias.deshacer "reset --soft HEAD~1"

git config --global alias.quien "shortlog -sn HEAD"

Curiosos para investigar

La historia de una sola función

git log -L :calcular_total:reportes.py

Muestra todos los commits que cambiaron la función calcular_total dentro de reportes.py, con el cambio exacto de cada vez. Es como una biografía de la función. Funciona en los lenguajes que Git sabe reconocer; si no, puedes indicar líneas: git log -L 10,30:archivo.

¿Cuándo nació este archivo?

git log --oneline --diff-filter=A -- contacto.md

--diff-filter=A filtra solo los commits que agregaron el archivo. Así encuentras su "acta de nacimiento".

El primer commit del proyecto

git log --oneline --reverse | head -1

--reverse muestra la historia al revés, de lo más viejo a lo más nuevo. En Windows sin Git Bash, el head puede no estar disponible: usa Git Bash.

¿Cuántos commits tiene el proyecto?

git rev-list --count HEAD

Un solo número. Ideal para decir "este proyecto tiene 1,284 commits" en una presentación.

Ver cambios palabra por palabra

git diff --word-diff
git diff --color-words

En vez de marcar la línea completa como cambiada, resaltan solo las palabras que cambiaron. Perfecto para textos, documentación y archivos Markdown, donde una línea puede ser un párrafo entero.

Tu propio formato de historial

git log --pretty=format:"%h · %an · %ar · %s"
a3f9c21 · Ana Pérez · 2 hours ago · Corrige teléfono de contacto

%h es el código corto, %an el autor, %ar la fecha relativa ("hace 2 horas") y %s el mensaje. Combínalo con un alias y tienes tu historial a la medida.

Buscar texto en todo el proyecto

git grep -n "500-0000"

Busca en todos los archivos que Git sigue y te dice archivo y número de línea. Más rápido que el buscador del sistema, y no se pierde en carpetas que ignoras.

¿Cuánto pesa el repositorio?

git count-objects -vH

La línea size-pack te dice cuánto ocupa la historia guardada. Útil cuando alguien pregunta por qué el proyecto tarda tanto en clonarse.

Poco usados, pero salvadores

Traer un solo commit de otra rama: cherry-pick

Alguien corrigió un error en su rama, pero su rama todavía no se fusiona y tú necesitas esa corrección ya:

git cherry-pick código-del-commit

Copia ese único commit a tu rama actual, como quien escoge una sola cereza del árbol. Úsalo con moderación: si lo haces mucho, el mismo cambio termina repetido en varias ramas.

Dos ramas abiertas a la vez: worktree

Estás a mitad de algo y te piden revisar otra rama. En vez de stash, abre la otra rama en otra carpeta:

git worktree add ../revision-urgente fix/telefono

Ahora tienes la carpeta revision-urgente con esa rama, y tu carpeta original sigue intacta. Cuando termines:

git worktree list
git worktree remove ../revision-urgente

Es uno de los comandos menos conocidos y más útiles. También es muy práctico si trabajas con agentes de IA: cada uno puede tener su propia carpeta sin pisarse.

Encontrar el commit culpable automáticamente: bisect ⚠

En el capítulo 12 viste la idea de partir el historial a la mitad. git bisect lo hace por ti. Y puedes ponerle tus propias palabras:

git bisect start --term-old=funcionaba --term-new=roto
git bisect roto                    # El commit actual está roto
git bisect funcionaba v1.0.0       # En la v1.0.0 funcionaba

Git te lleva a un commit de la mitad. Pruebas y le dices git bisect roto o git bisect funcionaba. Repite unas pocas veces y Git te dirá exactamente qué commit lo rompió. Al terminar:

git bisect reset

Si tienes un script que prueba automáticamente, Git puede hacer todo solo con git bisect run ./probar.sh.

Que Git recuerde cómo resolviste un conflicto: rerere ⚠

El nombre es casi un trabalenguas: reuse recorded resolution, reutilizar la resolución grabada.

git config --global rerere.enabled true

Desde ese momento, cuando resuelves un conflicto, Git lo recuerda. Si el mismo conflicto vuelve a aparecer (pasa cuando traes main varias veces a una rama larga), Git lo resuelve igual que tú la primera vez. Revisa siempre el resultado antes del commit.

Notas pegadas a un commit

git notes add -m "Este cambio se probó con datos de septiembre" a3f9c21
git log --oneline --notes

Agrega una nota a un commit sin modificarlo, como un post-it. Detalle curioso: las notas no viajan con el push normal, así que casi nadie las ve. Son más útiles para ti que para el equipo.

Exportar el proyecto sin la historia

git archive --format=zip -o proyecto.zip HEAD

Crea un .zip con los archivos del proyecto tal como están en el último commit, sin la carpeta .git ni los archivos ignorados. Perfecto para entregar una copia limpia a alguien que no usa Git.

Clonar solo lo último

git clone --depth 1 dirección

Descarga solo el último commit, sin toda la historia. Mucho más rápido en proyectos enormes. A cambio, no podrás investigar el historial hasta que traigas el resto con git fetch --unshallow.

Una rama sin pasado ⚠

git switch --orphan pagina-nueva

Crea una rama sin ningún commit anterior, como si fuera otro proyecto dentro del mismo repositorio. Se usa, por ejemplo, para guardar un sitio web de documentación separado del código. Al crearla, borra de esa rama los archivos que no necesitas antes del primer commit.

Un force push más educado ⚠

Si alguna vez de verdad necesitas forzar un push en tu propia rama (por ejemplo, después de un rebase), usa esta versión:

git push --force-with-lease

A diferencia de --force, se niega a sobrescribir si alguien más publicó algo en esa rama que tú no tienes. Es un force push que primero toca la puerta. Aun así: nunca en ramas compartidas.

Buscar commits perdidos en el limbo ⚠

git fsck --lost-found

Cuando ni el reflog te ayuda, este comando busca commits "huérfanos" que ninguna rama ni registro recuerda. Es el último recurso del botiquín, antes de rendirse.

La ayuda escondida

git help -g
git help everyday

El primero lista las guías que trae Git instaladas. El segundo es una guía oficial con los comandos mínimos para el día a día, según tu rol. Están en inglés, pero son sorprendentemente buenas.

Retos del anexo

Para cerrar con diversión, en tu proyecto practica-git:

  1. Activa la autocorrección y escribe a propósito git stauts. ¿Qué pasó?

  2. Crea tres alias en español que te sirvan de verdad y úsalos durante una semana.

  3. Busca todos los commits que hiciste "desde la hora del té" de ayer: git log --since="yesterday tea".

  4. Encuentra el "acta de nacimiento" de tu README.md y cuenta cuántos commits tiene tu proyecto.

  5. Usa git worktree para abrir otra rama en una carpeta aparte, haz un cambio allí y luego elimina esa carpeta con git worktree remove.

  6. Copia un commit de una rama a otra con git cherry-pick y míralo con git mapa (tu alias).

  7. Reto avanzado: provoca un error a propósito unos commits atrás y encuéntralo con git bisect, usando las palabras funcionaba y roto.
